# 为什么不用现成的

这一页回答面试里最硬的那个问题：已经有 Mem0、Zep、Letta、LangMem，定时推送也不过是 cron 加一次模型调用，那为什么还要自己做？

回答的顺序是固定的：**先说哪里不是优势**（避免把打平说成领先），**再把差别一条条量出来，包括会被追平的那条**，**最后写清楚不声称什么**。记忆在第一到第三节，主动交互在第四节。

> 全页每个数字都能追到工件或回归；凡是撑不住的说法，都已经撤掉并写明原因。

## 三十秒版本

**不要从"我们答得更准"开口，那句话会被一句话问倒。** 公开基准 310 题上我们和朴素向量检索**等价**（差值 95% CI [−5.0, +3.6] 个百分点，七个类别无一显著）。能说的是下面三条，每条都能当场跑出来、不需要密钥：

| 问题 | 我们 | 现成做法（含"加个缓存"的版本） |
| --- | ---: | ---: |
| 模型能不能用当前回执读到本次没给过的历史？ | **读不到，75/75 被拒** | 能（0/75）——它没有"本轮有权读哪些"这个概念 |
| 能不能说出"哪条记忆被取用、由谁触发"？ | **能，25/25** | 不能（0/25）——不保留每请求记录 |
| 给模型的材料能不能定位到原文的精确字符区间？ | **能，50/50 逐字节** | 不能——没有记录区间 |

后两列不是"它们考砸了"，而是**那套做法里本来就没有这些结构**。差别在设计，不在实现质量。

（第一条是**可审计性**而不是安全边界：模型发起一次新查询仍能浮出新原文，但那会留下带 `call_ref` 的回执。注入指令无法悄悄扩大接触面——要么被拒，要么留痕。）

主动交互同理：卖点不是"判断更准"（样本只有 12 道），而是**反馈回路有不可逾越的边界**——穷举 1,680 个评价状态，权重一次没出界、一次没归零；朴素比例策略会归零 40 次（归零即永久消音）。

**还有一条我们主动让出来**：可复现（重渲染逐字节一致）能被"每轮缓存"追平，而且缓存省 44 倍存储。所以它不是护城河，写在表里。

（另：Mem0、LangMem 那一类把对话用 LLM 抽成"事实"再存，本页第二节第 5 条讲了这为什么使字符级出处不可能。那是**读他们的设计得出的**，不是我这边的实测——我实测的对照基线只贴原文、不做抽取。）

## 一、先承认：回答准确率不是我们的优势

[公开基准 LongMemEval-S](../operations/evaluations/2026-11-06-memory-parity.md)，分两批抽了 **310 题（零重叠）**，剔除 abstention 后 280 道可回答题（不给历史的系统天然会弃答，混进去会让它虚高）：

| 方案 | 答对 | 配对检验 |
| --- | ---: | --- |
| 不给历史 | **0 / 120**（第一批） | — |
| 朴素向量检索加片段 | 163 / 280 | 对"不给历史" 68 比 2，**p < 10⁻¹⁵** |
| **本项目自动召回的实际配置** | 161 / 280 | 对朴素向量检索 18 比 20，**p = 0.871** |

两条结论方向相反，都照原样写：

- **记忆本身起决定性作用**：0% → 约 56%。这条不容置疑。
- **我们的图记忆相对朴素向量检索没有优势**：差值 **−0.7 个百分点，95% CI [−5.0, +3.6]**，七个类别无一显著。这是**等价区间**，不是"题量不够没测出来"——大于约 5 个百分点的差距已被排除。

所以本项目**不声称自己答得更准**。这不是谦虚，是数据明确反对。行业整体也是这个情况：主流基准已接近饱和，分数挤在九十几分；Letta 报告过纯文件系统操作在 LoCoMo 上就有 74%，与复杂记忆系统相当；ConvoMem 报告在 150 轮以下的历史上，整段塞进上下文比 Mem0 高 35–40 分。

检索召回那边也不要急着认领：会话级均值 0.8614 对 0.8337 看着更高，但配对后 12 比 9、**p = 0.66**，不成立。消息级召回 15 比 5、p = 0.041 名义显著，却过不了这个数据集上 12 次对比的多重比较校正（阈值 0.0042），也没有转化成答对率。**当线索记着，不当优势讲。**

**把"答得更准"当卖点，是最容易被面试官一句话问倒的地方。** 真正的差别在别处，而且可以量。

## 二、把差别一条条量出来——其中一条会被追平

下面每个数字都来自同一条命令，**不需要 API 密钥、不调用任何聊天模型**：

```sh
uv run --frozen --no-sync python -m eval.memory_guarantees --seed-turns 30 --live-turns 25
```

基线给**两种**。一种是最常见的做法：把这一轮的问题做向量检索，取最近邻若干条，正文贴进提示词，不记录这一轮给过什么。另一种是它**加上每轮缓存**——"现成方案自己缓存一下不就可复现了"这个反驳是对的，所以把它做成一条臂直接量，而不是在脚注里让步。三边跑同一批消息、同一组向量，比的是设计而不是检索质量。

| 性质 | 本项目 | 朴素基线 | 基线 + 每轮缓存 |
| --- | ---: | ---: | ---: |
| 索引增长后，同一请求重渲染**逐字节一致** | 25 / 25 | 16 / 25 | 25 / 25（追平） |
| 存储代价（25 轮） | 回执 174,222 字节 | — | 缓存 3,971 字节（更省） |
| 越权读取被拒（未呈现过／跨 scope／伪造 ref） | **75 / 75** | 0 / 75 | 0 / 75 |
| 合法读取仍然放行（控制组，防止"一刀切"） | **25 / 25** | — | — |
| 每次召回都带**可追责的来源** | **25 / 25** | 0 / 25 | 0 / 25 |
| 原文已在本次请求里时仍重复注入正文 | **0** | 89 | 89 |
| 呈现的材料是真实原文的**逐字节切片** | **50 / 50** | 不适用 | 不适用 |

**头两行照原样读：可复现这一条能被缓存追平，而且缓存在存储上比我们便宜约 44 倍。** 回执更大，是因为它记录的是整个检索决策——考虑过哪些候选、withhold 了什么、索引了什么、每段落在原文的哪个字符区间——而缓存只存最终输出那几个字节。**所以可复现不是护城河**，只是默认就有、不用额外想起来做的性质。

**但缓存只买到了这一条。** 后面几行它一项没动：它记录了"给过什么"，没有记录"本轮有权重读哪些原文"、"是谁发起的这次检索"、"某段材料落在真实原文的哪个位置"。**真正的差别是后三条。**

而且"直接加个缓存"还有一个正确性陷阱，不只是存储问题。缓存按什么做键？**按请求文本做键**是最自然的写法，而测量里最后一轮刻意重复了第一轮的问法——但它的对话窗口已经前移。结果：

| | 是否把第一轮的材料发给了最后一轮 |
| --- | ---: |
| 基线 + 文本键缓存 | **是**（陈旧材料） |
| 本项目（回执按请求做键） | 否 |

按请求 id 做键就不会串，但那样缓存条目随请求数增长，上面那个 3,971 字节的便宜一部分正是文本去重换来的。**两种键各有代价**——这不改变"缓存在存储上仍然更省"的结论，只是说明这条路不是免费的。

### 这些分母是什么性质

"n=25 够不够"这个问题问错了地方，因为表里多数行量的不是平均表现：

- **越权读取被拒、合法读取放行、可追责来源、逐字节切片、重复注入为 0**——这五项是**结构性性质**，由代码路径决定。分母的意思是"检查了这么多次，每次都成立"，不是"抽样抽得好"。它们的反例应当是 0 次：出现一次就是缺陷，不是统计波动。
- **只有重渲染一致在朴素基线侧有真实波动**（16/25 取决于索引长了多少、查询落在哪），所以只有它需要配对检验：**不一致 9 比 0，McNemar 精确检验 p = 0.0039**。加缓存之后它也成为性质，这一行就不再有区分度。
- 与之配对的 89（基线重复注入次数）是观察到的计数，不是性质。

所以前面公开基准那套"小样本不能下结论"的纪律，在这张表上**不适用**——那边量的是平均表现，这边量的是机制是否成立。唯一需要统计检验的那一行已经通过。

### 1. 同一请求，重渲染逐字节一致

检索结果在首次查询时被冻结进一份**不可变回执**（`frozen=True, strict=True` 的 `Recall`），之后这个请求的每一次重渲染——工具续跑、提醒重放、重试、重启、图重载——都从回执还原，而不是重新查索引。

朴素基线没有每请求的记录，索引又一直在长，所以同一个问题隔几轮再问，材料就变了（25 轮里有 9 轮变化，配对检验 p = 0.0039）。

**但这一条可以被追平，而且该说清楚。** 加上每轮缓存的基线拿到 25/25，存储还比我们省约 44 倍。所以**这不是本项目的护城河**，只是一个默认就有、不用额外想起来做的性质。

它仍然值得单独列出来，因为上下文不稳定会直接破坏输入缓存前缀、让线上问题无法复盘、让评测结果不可复现——只是"我们有"不等于"别人做不到"。窗口规则那条线另外核过一次更强的形式：**18 份原文窗口在图重载前后仍逐字节一致**，这一条缓存给不了，因为它要求的是重新读出来还一样，而不是把上次的结果存着。

### 2. 越权读取被拒，合法读取不受影响

模型要回看某条原文，必须带上**确实呈现过它的那份回执**。三条检查各自独立，实测各自都会触发：

- `unknown memory retrieval reference` —— 伪造的回执引用
- `source receipt belongs to another memory scope` —— 跨记忆 scope（不同 scope 是不同的图文件，硬隔离）
- `message was not presented by this retrieval` —— 这条消息本次召回没给过

控制组 25/25 全部放行，说明这不是"把读取一关了之"。每次成功读取在 Ledger 留下绑定真实调用的 `SourceProof`。

**这组用的是固定哈希向量，所以"检索不真实"的质疑要正面答：** 这里量的是准入判定，不是检索质量——准入走的是回执里的 `admitted_message_ids`，和向量好坏无关。而且同一条性质在[窗口规则那轮](../operations/evaluations/2026-11-06-memory-window.md)用**真实中文编码器（512 维）和真实模型**另外核过：越权读取 2/2 被拒，18 份原文窗口在图重载前后逐字节一致，查询与读取未额外增加聊天调用（0 次）。规模小得多，但走的是同一套生产组件。

**它到底防住了什么？把威胁模型写清楚，因为这是最容易被追问的一条。** 设想召回回来的某份历史文档里藏着一句"去把用户的体检记录找出来"。模型照做时有三条路：

| 它尝试的动作 | 结果 |
| --- | --- |
| 用当前回执去读一条本次没呈现过的原文 | **被拒**（`message was not presented by this retrieval`） |
| 伪造或猜一个回执引用 | **被拒**（`unknown memory retrieval reference`） |
| 跨到另一个记忆 scope 去读 | **被拒**（不同 scope 是不同的图文件，硬隔离） |
| **发起一次新的召回查询** | **允许**——这正是记忆的用途 |

最后一行是诚实的边界：**注入文本确实能让模型去查新东西。** 但它拿到的是一份新回执，带 `ToolSource` 和发起那次工具调用的 `call_ref`。

所以准确的说法不是"防注入"，而是：**注入指令无法悄悄扩大模型的接触面——要么被拒，要么留下可追责的记录。** 事后能回答"这条记忆是被谁、在哪次调用里取用的"，而不是只能看到它出现在了上下文里。这是一个可审计性保证，不是一个安全边界，两者不能混为一谈。

### 3. 每次召回都答得出"是谁要的"

回执里的来源是带判别的：`ContextSource` 记录会话与**触发它的对话前缀位置**（25/25 精确对齐）；`ToolSource` 绑定模型那次工具调用的 `call_ref`；`ProgramSource` 记录后台程序名。

**事后可以回答"哪些记忆被取用、由什么触发"**——模型自己拉的，和这一轮自动浮出的，是能分开的。对照基线没有任何这类记录。

### 4. 请求里已有的原文不重复注入

原文此刻仍逐字留在请求里时，召回不再重复贴正文，只花一行索引并保留可读回出处的 `ref`。这条由**突变验证过的回归**守着：正文只有在它仍属于当前窗口时才可以被 withhold，去掉那个窗口交集，测试立刻指名失败。

25 轮里对照基线重复注入了 89 次已经在请求里的原文，本项目 0 次。真实配置下的开销测量是每轮注入 **2393 → 757 字（−68.3%）**。

### 5. 记忆里存的是原文，不是模型改写过的"事实"

这条是前面几条成立的前提。本项目的召回材料**直接读取原消息正文**（`render_materials`：*正文从原消息读取*），图只负责找到是哪几条消息；实测 50/50 段都是真实原文的逐字节切片，且回执记录的原文总长与真实正文一致（防止陈旧 span 指错消息）。

**对照哪一类方案，要说有据可查的那个。** Zep / Graphiti 的文档明确：事实是从 episode **抽取出来的边**，`valid_at` / `invalid_at` 由 LLM 在边处理阶段填写，provenance 指回源 episode。那条边是改写过的表述，不是原文的某一段。（Mem0、LangMem 的内部表示我这轮没有逐一核实，所以不点名。）

**为什么这很重要**：抽取出来的"事实"没有字符偏移可以指，也没有原文可以逐字节重读——**精确到字符范围的出处在那种架构里做不出来**，而且抽取这一步本身会出错，错了还不容易看出来。

**代价也要写**：不做语义压缩，单次召回的 token 比存"事实"的方案高。本项目靠片段化与窗口规则来摊这个成本（每轮 2393 → 757 字），而不是靠牺牲可核对性。

## 三、明确不声称什么

- **不声称答得更准。** 见第一节：310 题上与朴素向量检索**等价**，差值 95% CI [−5.0, +3.6] 个百分点，七类无一显著。这不是"还没测出来"，是测出来了、并且排除了约 5 个百分点以上的差距。
- **不声称防提示注入。** 读取受限指的是"本次回执没呈现过的原文读不到"。模型发起**一次新的召回查询**，仍然可以在同一 scope 内浮出新的原文——这正是记忆的用途。能证的是跨 scope 硬隔离、伪造引用与未呈现消息被拒，以及**每次召回都留下可追责的来源**。
- **不声称这些性质别人做不到，其中一条已经被追平并写进表里。** 加缓存的基线在可复现上追平且更省存储。剩下三条（准入受限、来源可追责、字符级逐字节出处）缓存买不到，但现成方案同样可以自己去实现每轮白名单和区间记录——这里衡量的是：这些性质是本项目**已有数据结构直接给出的**，在索引变化和进程重启之后依然成立，并且可以从已发布证据离线复核。
- **竞品已有的能力要说清楚。** Zep 有 episode 级 provenance 和双时间线（被取代的事实标记而非删除），Mem0 按 user/agent/run/app 分 scope，Zep 托管版有 ABAC、保留策略与审计。我们的区别在**粒度**（精确到原文字符范围，可按同一回执重读同一段字节）和**作用域**（每次检索，而不是每个用户）。

## 时间这一维：一个取舍，不是一个缺口

Zep 的**双时间线**把"事情何时成立"（valid time）和"我们何时记下它"（transaction time）分开。我先前把这条写成"我们不如人"，查过之后要改：**它和我们"只存原文"的选择是冲突的，两边各付代价。**

**我们有的那半（transaction time）**：召回支持时间窗口筛选，`time_start` / `time_end` 暴露在 `RecallQuery` 上供模型使用，start > end 会被拒，筛选条件与结果一起冻结进回执。所以"**截至上周二，记录里是怎么说的**"能答——把召回限制在那之前发生的轮次即可。有行为级回归钉着：窗口收紧到单个时间点时，命中只剩那一轮。

**我们没有的那半（valid time）**：`MemoryEvidence` 只有 `recorded_at`，没有"这个事实从何时起成立、到何时失效"。所以"**某件事在上周二是不是成立**"答不了——尤其是那条消息本身记录得更晚的时候。

**但这一维不是白给的。** 按 Zep 自己的文档，`valid_at` / `invalid_at` 是**由 LLM 在边处理阶段填写的可选字段**，而且后续 episode 可以修正先前的 `valid_at`——也就是说这个时间维度本身是推断出来的，会错，并且要靠后来的推断去纠正。相应地，他们的事实是从 episode 抽取出来的边，provenance 指回**那条 episode**，而不是原文的某个字符区间。

对照我们这边：材料直接读原消息正文，50/50 段都是真实原文的逐字节切片（见第二节）。**精确到字符的出处，正是以"不做抽取"换来的**；而 valid time，正是以"做抽取"换来的。两者在同一个架构里很难同时成立。

| | Zep 的做法 | 本项目的做法 |
| --- | --- | --- |
| "某事在 T 时是否成立" | **能答**，靠 LLM 抽取的 `valid_at` | 答不了 |
| "截至 T 时记录里怎么说" | 能答 | **能答**，且筛选条件冻结进回执 |
| 一条材料的出处精度 | 指回源 episode | **原文的精确字符区间，可逐字节重读** |
| 时间维度的可靠性 | 推断得来，可被后续推断修正 | 不适用（没有这一维） |

所以准确的说法是：**这是一个有代价的取舍，不是一处忘了做的功能。** 如果产品后续确实需要"按时点回溯事实"（主动交互的事后复盘就是这类问题），那要么引入抽取层并接受它的误差，要么找一个不牺牲原文出处的办法。这条记在[交付路线](../status/roadmap.md)里，按"取舍"而不是"欠账"来写。

## 四、主动交互：为什么不是定时器加一条规则

同样先说不是优势的地方：**"会定时发消息"本身毫无门槛**，cron 加一个 LLM 调用就能做。主动交互真正难的是三件事——该不该发、依据是什么、发错了怎么办。这三件在本项目里都有对应的机制，而且都钉在回归里，不是文档里的说法。

| 要能回答的问题 | 本项目的做法 | 钉在哪 |
| --- | --- | --- |
| **发之前凭什么判断？** | 过去的个人条件参与今天的事件判断。受控邮件（邮件内容完全相同，只改另一个会话里的个人条件）：12 次调查**全部 12/12 呈现了对应历史**，**11/12** 选择了预期的分享或跳过 | [邮件与可纠正跟进](../operations/evaluations/2026-10-21-mail-followups.md)；**这两个数来自 6 组夹具，夹具已扩到 12 组 24 例，新一轮尚未跑** |
| **判断错了怎么办？** | 那一次失败完整保留：模型找到了原话却误读主语，跳过了本可考虑的方案。用户澄清后以新规则复查同一封邮件，得到确认投递，**旧误判和原文都还在** | 同上 |
| **会不会被反馈带跑偏？** | 见下表：穷举 1,680 个评价状态，权重一次也没出界 | `eval/proactive_guarantees.py` + `tests/test_proactive_guarantees.py` |
| **会不会抢话、重复打扰？** | 有活跃目标时空闲规划主动让位，目标结束后恢复 | `tests/test_goal_integration.py`（驱动真实 `Producer.run_once`） |
| **崩溃或取消会不会重复发送？** | 投递在 SIGKILL 恢复与读取取消两种路径下都不重发 | `tests/test_durable_deliveries.py` |

### 反馈边界：穷举，不是抽样

"会不会被用户的反馈带跑偏"这个问题可以彻底回答，因为它是个纯函数。对照的是最自然的那种写法——**直接用"有用"评价的占比当权重**，不需要调参，看起来也公平：

```sh
uv run --frozen --no-sync python -m eval.proactive_guarantees --limit 40
```

| 在全部 1,680 个评价状态里 | 本项目 | 朴素比例策略 |
| --- | ---: | ---: |
| 权重归零（**该来源再也越不过唤醒阈值，等于永久消音**） | **0** | 40 |
| 权重值域 | **[0.5, 1.5]** | [0.0, 1.0] |
| 好评能否把来源抬到中性之上 | **能** | **不能**（上限恰等于中性 1.0） |
| 不足 4 条评价就改动权重 | **0** | 6 |
| "有用"占比上升反而权重下降（单调性违例） | **0** | — |

朴素策略有两个实质缺陷，都与我们怎么定边界无关：**它会归零**（来源被永久消音），而且**它的上限恰好等于中性值**——好评最多把来源还原到默认，差评却能一路压到零。这是个单向棘轮，长期把所有来源推向沉默。

我们这边下界 0.5 保证再多负反馈也压不到零；上界 1.5 等于唤醒阈值，保证再多好评也只是刚好够格而不是碾压。两端都可达（4 条全好评到顶、4 条全负到底），所以"有界"不等于"迟钝"。

（工件里还记了"越出 `[0.5, 1.5]` 的状态数"，我们 0 次、朴素 820 次。但**那个计数有定义性成分**——拿我们的区间去量别人的策略——所以不作为主结论。）

还有一条是对抗性的，不是统计性的。权重随事件 payload 走，而订阅源的内容**不是可信输入**：

| 构造的 payload | 解析结果 |
| --- | --- |
| 10⁶、刚超上限、负数、`inf`、`NaN`、布尔、字符串、缺失 | 全部 **1.0（中性）**，8/8 |

注意这里是**判为中性而不是截断到边界**——截断仍然承认了它想要的方向，中性则完全不承认。所以一条订阅内容无法把自己喊得更响。

**这里的共同点和记忆那边是一样的**：卖点不是"判断更准"（11/12 的分母只有 12，撑不起这种话），而是**每一次联系都说得出依据、留得下错误、改得动规则，而且反馈回路有不可逾越的边界**。

**不声称的**：没有连续真实使用的数据，所以"有用提醒与误打扰的比例"答不了。**行为层证据仍是 12 道受控题**——和记忆那边早期一样属于小样本，不能当成能力证明。夹具已经扩到 12 组 24 例（新增的决策形态是周期性日程冲突、人数上限、过敏排除、必备同传缺失、能否开发票、退改政策），等公开基准那轮跑完就排上。

注意边界那一组和行为那一组**证明的是不同的东西**：边界是穷举的纯函数性质，行为是小样本的判断质量。前者已经站住，后者没有，不能互相代替。

## 一条命令把整页数字重算出来

这一页上**所有不需要密钥的数字**（第二节那张表、第四节的反馈边界、每轮注入开销），由一条命令一起重算：

```sh
uv run --frozen --no-sync python -m eval.offline_evidence
```

它把三组套件跑一遍排成一张表，每格带对照臂，输出里保留三份原始报告供逐项核对。不需要 API 密钥、不调用任何聊天模型。

唯一需要密钥的是第一节的公开基准对照（`eval.memory`），那是**唯一一处我们不占优的地方**，所以它单独放，不混进这条命令里。
