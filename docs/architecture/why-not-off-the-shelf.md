# 为什么不用现成的记忆方案

这一页用来回答一个具体的问题：已经有 Mem0、Zep、Letta、LangMem，为什么还要自己做一套记忆？

回答分三段：**先说哪里不是优势**（避免把打平说成领先），**再给五条当场能验证的差别**，**最后写清楚不声称什么**。

## 一、先承认：回答准确率不是我们的优势

[公开基准 LongMemEval-S 的 140 题](../operations/evaluations/2026-11-06-memory-parity.md)，120 道可回答题（剔除 abstention，因为不给历史的系统天然会弃答）：

| 方案 | 答对 | 配对检验 |
| --- | ---: | --- |
| 不给历史 | **0 / 120** | — |
| 朴素向量检索加片段 | 68 / 120 | 对"不给历史" 68 比 2，**p < 10⁻¹⁵** |
| **本项目自动召回的实际配置** | 67 / 120 | 对朴素向量检索 8 比 9，**p = 1.00** |

两条结论方向相反，都照原样写：

- **记忆本身起决定性作用**：0% → 约 56%。这条不容置疑。
- **我们的图记忆相对朴素向量检索没有优势**：差值 **−0.8 个百分点，95% CI [−7.6, +5.9]**。这是**等价区间**，不是"题量不够没测出来"——大于约 7 个百分点的差距已被排除。

所以本项目**不声称自己答得更准**。这不是谦虚，是数据明确反对。行业整体也是这个情况：主流基准已接近饱和，分数挤在九十几分；Letta 报告过纯文件系统操作在 LoCoMo 上就有 74%，与复杂记忆系统相当；ConvoMem 报告在 150 轮以下的历史上，整段塞进上下文比 Mem0 高 35–40 分。

有一项确定性测量我们确实略高：**会话级检索召回 0.8614 对 0.8337**，不经过 judge。但它没有变成更高的答对率——覆盖率提升不自动等于回答更好，这一点在[取证深度](../operations/evaluations/2026-10-22-memory-depth.md)那边也是同样的观察。

**把"答得更准"当卖点，是最容易被面试官一句话问倒的地方。** 真正的差别在别处，而且可以量。

## 二、五条当场能验证的差别

下面每个数字都来自同一条命令，**不需要 API 密钥、不调用任何聊天模型**：

```sh
uv run --frozen --no-sync python -m eval.memory_guarantees --seed-turns 30 --live-turns 25
```

对照基线是最常见的那种做法：**把这一轮的问题做向量检索，取最近邻若干条，正文贴进提示词，不记录这一轮给过什么**。两边跑同一批消息、同一组向量，比的是设计而不是检索质量。

| 性质 | 本项目 | 对照基线 |
| --- | ---: | ---: |
| 索引增长后，同一请求重渲染**逐字节一致** | **25 / 25** | 16 / 25 |
| 越权读取被拒（未呈现过／跨 scope／伪造 ref） | **75 / 75** | 0 / 75 |
| 合法读取仍然放行（控制组，防止"一刀切"） | **25 / 25** | — |
| 每次召回都带**可追责的来源** | **25 / 25** | 0 / 25 |
| 原文已在本次请求里时仍重复注入正文 | **0** | 89 |
| 呈现的材料是真实原文的**逐字节切片** | **50 / 50** | 不适用 |

### 1. 同一请求，重渲染逐字节一致

检索结果在首次查询时被冻结进一份**不可变回执**（`frozen=True, strict=True` 的 `Recall`），之后这个请求的每一次重渲染——工具续跑、提醒重放、重试、重启、图重载——都从回执还原，而不是重新查索引。

对照基线没有每请求的记录，索引又一直在长，所以同一个问题隔几轮再问，材料就变了（25 轮里有 9 轮变化）。

**为什么这不是锦上添花**：上下文不稳定会直接破坏输入缓存前缀、让线上问题无法复盘、让评测结果不可复现。窗口规则那条线另外核过一次更强的形式——**18 份原文窗口在图重载前后仍逐字节一致**。

### 2. 越权读取被拒，合法读取不受影响

模型要回看某条原文，必须带上**确实呈现过它的那份回执**。三条检查各自独立，实测各自都会触发：

- `unknown memory retrieval reference` —— 伪造的回执引用
- `source receipt belongs to another memory scope` —— 跨记忆 scope（不同 scope 是不同的图文件，硬隔离）
- `message was not presented by this retrieval` —— 这条消息本次召回没给过

控制组 25/25 全部放行，说明这不是"把读取一关了之"。每次成功读取在 Ledger 留下绑定真实调用的 `SourceProof`。

### 3. 每次召回都答得出"是谁要的"

回执里的来源是带判别的：`ContextSource` 记录会话与**触发它的对话前缀位置**（25/25 精确对齐）；`ToolSource` 绑定模型那次工具调用的 `call_ref`；`ProgramSource` 记录后台程序名。

**事后可以回答"哪些记忆被取用、由什么触发"**——模型自己拉的，和这一轮自动浮出的，是能分开的。对照基线没有任何这类记录。

### 4. 请求里已有的原文不重复注入

原文此刻仍逐字留在请求里时，召回不再重复贴正文，只花一行索引并保留可读回出处的 `ref`。这条由**突变验证过的回归**守着：正文只有在它仍属于当前窗口时才可以被 withhold，去掉那个窗口交集，测试立刻指名失败。

25 轮里对照基线重复注入了 89 次已经在请求里的原文，本项目 0 次。真实配置下的开销测量是每轮注入 **2393 → 757 字（−68.3%）**。

### 5. 记忆里存的是原文，不是模型改写过的"事实"

这条是前面几条成立的前提，也是和 Mem0、LangMem 这类方案最根本的结构差别。它们用 LLM 把对话抽取成"事实"再存起来；本项目的召回材料**直接读取原消息正文**（`render_materials`：*正文从原消息读取*），图只负责找到是哪几条消息。

实测 50/50 段呈现材料都是真实原文的逐字节切片，且回执记录的原文总长与真实正文一致（防止陈旧 span 指错消息）。

**为什么这很重要**：抽取出来的"事实"没有字符偏移可以指，也没有原文可以重读——**精确到字符范围的出处在那种架构里根本无法实现**，而且抽取这一步本身会出错，错了还看不出来。

**代价也要写**：不做语义压缩，单次召回的 token 比存"事实"的方案高。本项目靠片段化与窗口规则来摊这个成本（每轮 2393 → 757 字），而不是靠牺牲可核对性。

## 三、明确不声称什么

- **不声称答得更准。** 见第一段，分不出来。
- **不声称防提示注入。** 读取受限指的是"本次回执没呈现过的原文读不到"。模型发起**一次新的召回查询**，仍然可以在同一 scope 内浮出新的原文——这正是记忆的用途。能证的是跨 scope 硬隔离、伪造引用与未呈现消息被拒，以及**每次召回都留下可追责的来源**。
- **不声称这些性质别人做不到。** 现成方案完全可以自己缓存每轮材料、自己维护每轮白名单。这里衡量的是：这些性质是本项目**已有数据结构直接给出的**，在索引变化和进程重启之后依然成立，并且可以从已发布证据离线复核。
- **竞品已有的能力要说清楚。** Zep 有 episode 级 provenance 和双时间线（被取代的事实标记而非删除），Mem0 按 user/agent/run/app 分 scope，Zep 托管版有 ABAC、保留策略与审计。我们的区别在**粒度**（精确到原文字符范围，可按同一回执重读同一段字节）和**作用域**（每次检索，而不是每个用户）。

## 这里有一处我们确实不如人，应当补上

Zep 的**双时间线**（valid time 与 transaction time 分开）我们没有：本项目的 `MemoryEvidence` 只有 `recorded_at`，也就是"这条消息什么时候被记下"。于是"**某件事在上周二是不是成立**"和"**上周二我们以为它成立**"这两个问题，现在只能答后一个。

目前的更正处理靠按时间顺序解析（召回材料里较晚的消息覆盖较早的），窗口套件的"被取代的决定"题族和邮件实验都测了这条路径，它在当前场景下够用。但一旦要回答"按当时已知信息，这个判断对不对"，缺这一维就会卡住——主动交互的事后复盘恰好是这种问题。这条记在[交付路线](../status/roadmap.md)里，不写成已有能力。

## 四、主动交互：不是定时器

同样的思路：主动交互的卖点不是"会定时发消息"，而是**判断能追溯、会出错、而且错了能改**。

- **过去的条件参与今天的判断。** 六组受控邮件（邮件内容完全相同，只改另一个会话里的个人条件）：12 次调查**全部 12/12 呈现了对应历史**，**11/12** 选择了预期的分享或跳过。
- **误判完整保留。** 那一次失败是模型找到了原话却误读主语，跳过了本可考虑的方案。用户澄清后以新规则复查同一封邮件，得到确认投递，**旧误判和原文都还在**。这是"可纠正"的证据——不是不会错，是错了能查清、能改、能复查。
- **反馈有界。** 投递反馈影响关注权重，但权重被 clamp 在 `[0.5, 1.5]`，且少于 4 条评价时不调整。再多负反馈也压不到零，再多好评也不会无限放大。
- **不抢话。** 有活跃目标时，空闲规划主动让位（`GOAL_STATUS`），目标结束后恢复，避免就同一件事打扰两次。
