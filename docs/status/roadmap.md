# 交付与研究路线

## 当前重点

- 产品定位：陪伴型、助理型、主动交互型的个人 Agent；覆盖日常交流、兴趣、学习、生活与工作。持续跟进和原文取证是具体工作流。
- 个性已支持六个表达维度、支持与建议两个行为偏好，以及补充文字与可选说话示例；继续检验多轮稳定性、隐含追问及缺少素材时的事实克制。实际功能正确、行为符合、风格可辨识和用户喜欢是不同指标；不保留缺乏可观察区别的中间选项。
- 记忆：优先打磨长记录的原文取证、个人历史参与后续行动，以及长期使用中的出处复核。
- 评测：按具体场景证明记忆的价值，记录最终答案或行动、读取开销与失败边界；整体榜单排名不是交付目标。
- 持续工作：任务与工具效果可追溯，重启后接续已有执行状态。
- 双主动：事件调查与有历史依据的空闲规划均沿既有执行链路运行；继续验证日常价值、预算、停止控制与长期时机。

- 已送达反馈已接入有界关注权重：累计 4 条评价后按有用比例给出 0.5—1.5 的权重，参与兴趣池质量累加，明确要求逐条调查的条目不受影响，权重与依据可在跟进详情查看。离线回放 `eval/feedback_replay.py` 可在真实记录上核对会改变哪些联系决定并留出评价；尚未用留出集评分，也未验证真实使用中的有用提醒与误打扰比例，不能把决定翻转当成改善。
- Akasha 引擎已采用上游到 `5ddd5ebb` 的实现（块预留、basin 增量常驻索引、惰性堆 Residual Push 与编译内核、矩阵特征池、检查点原地增量发布与 schema v3、恢复复用缓存、兴趣原型增量）：固定 150 轮各三次，学习中位数 47.66 s → 20.34 s，检索均值 47.96 ms → 11.62 ms，峰值 52 MiB → 77 MiB。`numba` 已纳入 `memory` extra；未安装时退回解释器循环，检索约 35.6 ms，结果相同。v3 之前的检查点在读取时被拒绝并要求显式重建，上游那条重放迁移在本发行版不触发。开销下降不等于检索质量提升，质量仍分开验收。
- 时间维度是一个取舍，不是欠账。transaction time 已具备且有行为级回归：召回支持 `time_start` / `time_end` 窗口筛选，暴露在 `RecallQuery` 上、带 start ≤ end 校验、筛选条件冻结进回执，窗口收紧到单点时命中只剩那一轮，因此"截至某时记录里怎么说"能答。缺的是 valid time（"某事在 T 时是否成立"），而按 Zep 自己的文档，那一维是**由 LLM 在边处理阶段填写 `valid_at` / `invalid_at`**、且可被后续 episode 修正的推断值，其事实也是抽取出的边、provenance 指回源 episode 而非字符区间。本项目的字符级出处恰恰以"不做抽取"换来（50/50 逐字节切片）。若将来确需按时点回溯事实（主动交互的事后复盘属于此类），要么引入抽取层并接受其误差，要么找到不牺牲原文出处的办法——这是设计决策，不要写成"补一个字段"。见[为什么不用现成的](../architecture/why-not-off-the-shelf.md)。
- 公开基准题量：主对比已分两批扩到 LongMemEval-S 的 **310 题（零重叠）**，280 道可回答题给出 **±5 个百分点**的等价区间（161 对 163，p = 0.871），七个类别无一显著。`multi-session` 那条线索已按预先声明的方式了结：留出 30 题未复现（p = 0.6875），合并 50 题 p = 0.146、CI 下界 −25.6 点，所以既不写成短板也不宣布澄清，该类别完整集合有 121 题，若要定论仍需扩量。原始集合 500 题尚未跑完；选择模式与窗口规则两条线仍停在小样本。
- **偏好类问题是两种检索方案共同的短板**，不是设计差异：公开基准 `single-session-preference` 上本项目 5/30、朴素向量检索 2/30，而 `knowledge-update` 分别是 36/50 和 39/50。对一个以长期陪伴为目标的产品，这类"记住我的口味与偏好"恰恰是高频需求，值得单独设计并单独验收，不能靠整体答对率掩盖。
- **架构对齐已动手：Operation Bus 已移植**（`plugins/operations/`，对应上游 `0af31c5c`）。一个领域动作一处 `OperationSpec`，用户与 Agent 用同一个 `actor` 走同一个 handler；`mirrors` 让"界面入口 ↔ Agent 可调用操作"的一对一关系成为可核对的声明。回执绑定调用指纹（actor/session/argv），同 ID 换调用是 `conflict` 而不是拿到别人的结果；handler 在注册者自己的作用域里运行。**没有移植 `stage`**（多 owner 联合事务），因为我们的 ledger 没有 `OwnerWrite`，留一个不能原子提交的联合写入口比没有更危险。8 项回归，突变四向验证。下一步是 `self_cli`（把总线挂成模型可调用的 CLI）与一对一 Parity 门禁（需先有界面入口采集）。
- **维护：锁点摘要门禁此前是红的，已修并补了工具。** `plugins/akasha/plugin.py` 自召回装饰器修复后一直没更新 `sha256`，而补丁产物只能手工重新生成。新增 `scripts/regenerate_upstream_patch.py`，`--update-digests` 与 `--rebuild` 分开；12 个产物里 8 个能用 GNU `diff -u` 从锁点逐字节复现，复现不出来的默认拒绝重写。必须是 `diff -u` 而非 `difflib`——两者 hunk 边界不同，用 difflib 会把几百 KB 补丁改成同义写法。
- **方向已定：跟进上游，先补基本功能对齐。** 清单与进度见[跟进上游：功能对齐清单](../architecture/upstream-alignment.md)，用 `scripts/diff_upstream_tools.py` 按"模型可调用的工具"逐项核对，不凭印象判断落后。已补 `subagent_read`（父 Agent 能读子任务的会话过程，不只是状态与最终结果；父会话归属检查与 `spawn_manage` 共用，突变双向验证）。上游有而我们没有的从 17 降到 16。下一项是 `subagent_send`，它需要先有一个"向运行中的一轮注入消息"的 Steer 原语，会碰 react 循环与效果排空，所以单独排——半成品的注入路径比没有更糟，会在父 Agent 以为插话成功时静默丢消息。明确不跟的是 `watch`（上游用它取代 Wake）、`self` / `codemode` / Operation Bus（11 月新架构，先评估）、`phone_use`（可选硬件）。
- **上游锁点落后 562 个提交，而且上游重构了结构，这是一个待定的产品决定而非一次合并。** 锁的是 `e4ba3e29`（2026-10-21），上游 HEAD 是 `08441729`（2026-11-27）。期间上游把核心收到最小闭环、官方插件移到 `kachofugetsu09/akashic-plugins`（ADR 0167），并**删掉了 Wake（ADR 0149，换成值班）和 Drift**；我们依赖的四个插件里三个已不在上游核心，一个被删。所以选项是"继续跟上游"还是"明确声明在锁点分叉、自己维护这几个插件"，不是 rebase。逐条对照见[这个 fork 相对上游做了什么](../architecture/fork-vs-upstream.md)。
- **架构方向已定：维持"主 Agent + 同账本子会话"，不转向"superagent 做入口 + 一堆只交文本的子 ReAct agent"。** 理由是取舍而非优劣：文本边界让编排层能自由替换子 agent，但出处会在子 agent 边界断掉；本项目要的"每次取用都说得出是谁要的、凭什么能读"要求子会话走同一个账本与同一条 `admitted_message_ids` 准入门，代价是不能随意接第三方 agent。两件事不能同时要，已选前者。没有做过两种拓扑的对照实验，所以不声称任务完成质量更高。见[为什么不用现成的](../architecture/why-not-off-the-shelf.md)第五节。
- **`plugins/wake` 里有一个记而不用的字段**：`_wake_semantic_interest` 被打分、入库（带 CHECK 约束）、读回并挂到事件上，但 `admission_mass = initial**2 * freshness` 从不用它，`_rank_key` 和 `should_wake` 也不用。上游用十四天生产数据（语义分日均 0.03、1659 条无一超过 0.3）把整个池子删了。我们的准入路径结构上就没依赖它，所以上游的否证打不到判断逻辑——但这个字段是债，清理要带数据迁移，单独排。
