# 证据与验证

这一页先说本项目**最值得称道的四件事**，每件都给出具体数字和可复核的记录；随后是全部报告的索引。每项结论的分母和条件写在对应报告里，复现命令见[评测入口](../../eval/README.md)。

## 一、召回能查到底，而且查得到出处

记忆不止"想起来"。每次召回留下**不可变、可重放的回执**：被呈现的消息身份、原文字符范围、来源会话与时间都固定下来；之后可以沿同一回执读回**精确的原文窗口**，而且**只能读这次确实呈现过的消息**——准入由回执决定，不能凭空填一个消息 ID。每次读取在 Ledger 留下绑定真实调用的 `SourceProof`。

真实模型实测：在一份 **10,894 字符**的原文里，模型用 `search_memory_source` 定位到第 8400–9200 字符窗口，答出"预算由 500 更正为 760、必须防水、只在周末"，`tool_source_proofs: 3`、`search_windows: 2`，且 `query_contains_reference_answers: false`、`exact_offset_supplied: false`——没有给任何提示。

固定语料的取证实验里，同一 6000 字符上限下加入按需读取后，参考值原文覆盖由 **4/12 升到 9/12**，末页事实由 **0/4 升到 4/4**，平均保留材料反而**减少 43.78%**。
窗口规则把「原文已在请求里」的候选改成一行索引后，确定性对照给出：初始材料由 2390 字降到 **820 字（−65.7%）**，而 **12/12** 的参考值仍留在回执准入的原文里，一次读取即可取回；同一次运行内 18 份原文窗口在图重载前后均逐字节一致，2 次越权读取被拒绝，32 行可离线复核。

回答质量那一格**本轮判定不了，也照原样写下来**：严格答对正文臂 9/12、索引臂 6/12，看着差三题，但配对数据里两臂只在 7 道题上结果不同（5 比 2），McNemar 精确检验 **p = 0.45**——和掷硬币区分不开，不能说索引臂答得更差。同一组里两臂**没有编造过一个编号**（24 道可回答题无一答错编号，8 道无答案题无一编造），失手都是"没答"而不是"答错"；索引臂的输入 token 反而更低（50,839 对 54,356）。

这个 6/12 要读作**下界**：生产里一条正文被 withhold 的唯一条件是它此刻仍逐字留在本次请求里（`withheld = 候选 ∩ window(snapshot, covered)`），而该套件的索引臂故意把前提拿掉——候选来自历史会话，并不在读者这一轮的请求里。这条前提由回归守着，并且经过突变验证：去掉那个交集，测试立刻指名两条跨会话消息失败。前提成立时的回答质量仍待单独对照。

## 二、过去的条件参与今天的决定，而且能被纠正

主动交互不是定时打扰。新事件只提供新事实，**预算、时间、使用限制来自过去的对话**，两者合起来决定分享还是跳过，结果能追溯到实际读过的用户记录。

六组受控邮件（邮件完全相同，只改另一个会话里的个人条件）：12 次调查**全部 12/12 呈现了对应历史**，**11/12 选择了预期的分享或跳过**。误判的那一次完整保留：模型找到了原话却误读主语，跳过了本可考虑的方案；用户澄清后以新规则复查同一封邮件，得到确认投递，旧误判和原文都在。

这正是"可纠正"的证据——不是不会错，是错了能查清、能改、能复查。

## 三、知道自己花了多少，并且把它降下来

多数项目说不出自己的记忆每轮花多少上下文。本项目有可复现的开销测量，并据此做了优化：

| | 改前 | 改后 |
| --- | ---: | ---: |
| 每轮实时召回注入 | 2393 字 | **757 字**（−68.3%） |
| 学习 150 轮 | 47.66 s | **20.34 s** |
| 单次检索均值 | 47.96 ms | **11.62 ms** |
| 长会话召回整体耗时 | 14.78 s | **8.91 s** |

机制是：原文仍在当前对话里的候选不再重复注入正文，改为一行索引并保留可读回出处的 `ref`；两个判断在首次查询时冻结进回执，重渲染与重启字节一致。开销类各跑三次取中位数（`eval.recall_cost`、`eval.memory_cost`）。

## 四、来源与边界是可核对的，不是声明

这是一个基于上游 [akashic-agent](https://github.com/kachofugetsu09/akashic-agent) 的发行版，来源纪律做到逐文件：**969 个文件按哈希固定**，12 个补丁工件**逐个应用到基线后与本仓库逐字节一致**（比只比对摘要更强）。采纳了什么、拒绝了什么及理由、以及刻意与上游不同的三处，都记录在 `third_party/UPSTREAM.json` 的 `reviewed_updates` 里——拒绝是写下来的决定，不是无人过问的空缺。
[第三方来源声明](../../third_party/THIRD_PARTY.md)

工程不变量由 **489 项回归**守住，而且测的是不变量而非冒烟：scope 路由不得阻塞事件循环、v3 之前的检查点必须被拒绝而不是静默重写、索引行必须可引用可读取、关注权重必须有上下界且单调、**正文只在它仍逐字留在本次请求里时才可以被 withhold**（最后这条经突变验证：去掉窗口交集，测试立刻指名两条跨会话消息失败）。

其中 8 项守的是**评测自己**。取证代码也会错，而且错起来不会被产品测试发现：本轮查出三处——reader 输出预算被钉在 1024，把推理型模型的截断记成"协议失败"；导航夹具有一族题无法从原文确定答案，两臂因此恒为 0/4；汇总把截断与散文并成一个数。三处都修好并钉成回归（夹具答案必须能从原文确定、已发布夹具摘要锁定、截断与散文必须分开计数），详见[窗口规则](evaluations/2026-11-06-memory-window.md)。先修取证再谈结论，比直接报一个好看的数字更能说明这套评测的可信度。

## 五、和现成方案比，差别在可复现与可追责上

回答准确率上本项目与朴素向量检索**分不出差别**（p = 0.29），所以不拿它当卖点。拿得出手的是另外五条，对照"向量检索取最近邻、正文贴进提示词、不记录本轮给过什么"这一常见做法，**全部免模型、免密钥可复现**：

| 性质 | 本项目 | 对照基线 |
| --- | ---: | ---: |
| 索引增长后同一请求重渲染逐字节一致 | **25 / 25** | 16 / 25 |
| 越权读取被拒（未呈现／跨 scope／伪造 ref） | **75 / 75** | 0 / 75 |
| 合法读取仍放行（控制组） | **25 / 25** | — |
| 每次召回带可追责来源 | **25 / 25** | 0 / 25 |
| 请求里已有的原文仍被重复注入 | **0** | 89 |
| 呈现材料是真实原文的逐字节切片 | **50 / 50** | 不适用 |

读这张表要先分清性质：**后四行是结构性性质，不是抽样估计**——分母表示检查了多少次、每次都成立，出现一次反例即为缺陷而非统计波动。只有第一行基线侧存在真实波动，按配对检验为 **p = 0.0039**。

限度写在同一页：这不等于防注入——模型发起新查询仍可在同一 scope 内浮出新原文。完整论证、竞品能力对照与主动交互部分见[为什么不用现成的](../architecture/why-not-off-the-shelf.md)。

## 哪些差别是真的，哪些是噪声

对比类结论一律按配对数据处理：两个方案答同一批题，看的不是总数谁高，而是**两者结果不同的那些题**是否一边倒超过随机（McNemar 精确检验）。按这把尺子重核本项目已发布的对比，结果分成清清楚楚的两类。

**站得住的（p < 10⁻¹⁵）**：公开基准 [LongMemEval-S 的 140 题](evaluations/2026-11-06-memory-parity.md)上，120 道可回答题里**不给历史答对 0 道**，两种检索方案都在 56% 左右，逐题配对 68 比 2。记忆组件起的是决定性作用，不是边际改善；"把最近的消息塞满预算"这种朴素做法（另一轮 42 题里 7/42）同样解决不了问题。

**等价而不是没测出来**：本项目自动召回的实际配置对朴素向量检索是 67/120 对 68/120，配对 8 比 9，**p = 1.00**，差值 **−0.8 个百分点、95% CI [−7.6, +5.9]**。题量从 42 提到 140 之后，这句话从"分不出来"变成了**可以排除约 7 个百分点以上的差距**。选择模式之间（`fused` 对 `lanes`，p = 0.375）和窗口规则两臂（9/12 对 6/12，p = 0.45）仍属题量不足，照旧不下结论。

**本项目因此不声称自己的记忆方案回答得更准**——数据明确反对这个说法，写上去一问就倒。

能站住的优势在别处，而且是确定性测量、不受题量影响：原文可取证与可复核、窗口规则在材料减少 65.7% 时参考值可达性 12/12 不变、每轮注入 2393 → 757 字、以及"正文只在它仍逐字留在请求里时才被 withhold"这条经突变验证的不变量。

统计量由 [`eval/significance.py`](../../eval/significance.py) 计算（Wilson 区间 + McNemar 精确检验 + 配对差值区间，无外部依赖），回归钉住了它最该守的性质：**看起来 9 比 6 的差距必须被判为"分不出来"**。

## 读这些数字时请注意

报告中的数字属于各自的实验版本。功能回归、公开回答质量、实际投递和真实用户效果**各有自己的分母，不合并成一个"成功率"**；失败、开销与版本条件都保留在报告里，便于核对而不是便于好看。

尚未验证的部分同样写明，按"最实在的缺口"排序：

1. **题量**。主对比已扩到 [LongMemEval-S cleaned](https://huggingface.co/datasets/xiaowu0162/longmemeval) 的 **140 题**（`--per-category 20`，按 `SHA256(种子:question_id)` 在每个类别内独立抽样，数据集摘要已固定），足以给出 ±7 个百分点的等价区间。但原始集合有 500 题，而且**分类别那张表每格只有 20 题**——`multi-session` 上落后 7 对 11 值得查，却还不能当定论。选择模式与窗口规则两条线仍停在小样本（p = 0.375、p = 0.45）。`--per-category` 与 `--offset` 都是参数，继续扩大不需要改评测代码。
2. **单一 reader 模型**。全部真实模型实测只用了 step-5-preview；现有 API 配额只开放 step_plan 线路（按量计费端点返回 402），所以"换模型是否结论一致"目前无法回答。
3. **judge 不是官方口径**。公开历史这条线用同一模型、另起盲化请求、按类别 rubric 打分，并记录 `judge_valid`；这不是官方 GPT-4o 评分，不能当作榜单成绩。确定性结论（原文覆盖、可达性、开销、不变量）不经过 judge。
4. **强基线缺一个**。已有 `no-memory`（不给历史）和 `recent`（等预算最近消息）两条基线，但没有"整段历史全部塞进上下文"的对照。LongMemEval-S 单题历史约 115K token，远超本轮 reader 的 32K 上下文窗口，所以这条基线在该配置下跑不了——这本身也是记忆存在的理由，但应当写成"受限于上下文窗口"，而不是"已证明记忆更优"。

长期陪伴的实际价值、主动联系的有用与误打扰比例，仍需连续真实使用才能回答。[交付路线](../status/roadmap.md)记录仍待补齐的工作。
