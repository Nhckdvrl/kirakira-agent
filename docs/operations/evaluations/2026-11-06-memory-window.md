# 窗口规则：三分之一的材料，不丢答案；回答质量这一格现在有数了

把"原文已经逐字在请求里"的候选从正文改成一行索引之后，必须回答两个问题，本轮两个都有答案：

1. **省掉正文有没有把答案丢掉**——没有。初始材料由 2390 字降到 **820 字（−65.7%）**，而 **12/12** 的参考值仍留在回执准入可读的原文里，一次 `read_memory_source` 即可取回。这条判定不经过模型。
2. **回答质量有没有变差**——在这个夹具上变差了：严格答对 **window-bodies 9/12、window-index 6/12**。结论照原样写在这里，不往有利的方向挑。同时要读准它的量级：这个夹具不只是"答案在初始材料之外"，它还**拿掉了规则自己的前提**——索引臂 withhold 了正文，而那些原文并不在读者的请求里，生产中不会出现（[为什么这是下界](#这个-612-是下界因为它拿掉了规则自己的前提)）。所以 6/12 是下界，不是生产行为的估计。

两臂都**没有编造过一个编号**：24 道可回答题里没有任何一次答出错误凭证号，8 道无答案题里没有任何一次编出凭证号。失手都是"没答"或"答 UNKNOWN"，不是答错。

全部证据可离线复核，**不需要 API 密钥、聊天模型、向量权重或私有工作区**：

```sh
uv run --frozen --no-sync python -m eval.memory_depth \
  --verify-existing docs/operations/evaluations/artifacts/2026-11-06-memory-window/evidence.json \
  --output /local-disk/eval/window-verification.json
```

## 本轮先修的是取证代码，不是结论

上一版报告这一格是空的，理由写成"reader 不能稳定完成严格函数调用"。那个理由是错的，错在取证代码里，共三处，都已修好并钉成回归（`tests/test_eval_harness.py`，8 项）：

| 缺陷 | 后果 | 修法 |
| --- | --- | --- |
| reader 输出预算被硬钉在 1024 token | 推理型 reader 的思考占同一预算，在发出那一个函数调用之前被截断，`finish_reason` 为 `length`。13 次"协议失败"里有 **8 次**是截断 | 默认改用模型配置里的 `max_output_tokens`（4096），并新增 `--reader-output-tokens` |
| 夹具第 2 版的首部题无法从原文确定答案 | 承载答案的那行只写"归档栏"，原文里没有一句把它和问题问的"正式签收凭证号"连起来，而更早一条消息明确说"尚无正式签收凭证号"。答 UNKNOWN 比答编号更有依据，**那 4 题两臂恒为 0/4** | 新增第 3 版：保留改名（仍要导航），但每份报告开头用一句普通正文写明哪个字段登记它 |
| 汇总把截断和散文并成一个 `protocol_failures` | 把评测自己的配置失误读成模型结论 | 分出 `truncated_calls` 与 `prose_calls` |

修好前后在**同一份（有缺陷的）夹具**上的对照，说明前两处各自有多重：

| | 预算 1024 | 预算 4096 | 第 3 版夹具 + 4096 |
| --- | ---: | ---: | ---: |
| 截断调用 | 8 | 1 | 1 |
| 协议失败（bodies / index） | 7 / 6 | 2 / 2 | 3 / 4 |
| 实际作答（bodies / index） | 9 / 10 | 14 / 14 | 13 / 12 |
| 首部题答对（bodies） | 0 / 4 | 0 / 4 | **4 / 4** |

首部题那一行是判决性的：预算修好之后它仍然 0/4，**说明问题不在 reader 也不在预算，而在夹具**；换到第 3 版夹具立刻 4/4。基线臂能答对自己材料里的题，比较才成立。

旧结论里还有一处要收回：上一版写"索引臂总 token 高 22%"。那是截断预算下的数，本轮不成立——见下面的代价表，索引臂输入 token 反而更低。

## 固定条件

| 项目 | 条件 |
| --- | --- |
| 语料 | 固定生成的源导航夹具第 3 版（`fixture_sha256` 开头 `74063be1ee30`）；16 题（首部、末页、中部事实与无答案各 4 题） |
| 对照 | 两臂同一语料、同一候选集（fused，4 个）、同一初始上限 2400 字、同一读取额度（最多 2 次、总计 6000 字） |
| 唯一差异 | `window-bodies` 给片段正文（窗口规则之前的呈现）；`window-index` 把每个候选都当成已引用，withhold 正文、对放得下的花一行索引（现在的呈现） |
| 索引 | 真实 Ledger、Learning、MessageConsumer；本地中文语义向量 512 维；48 轮、96 条消息建图 |
| 模型 | step-5-preview，`reasoning_effort: low`，真实函数调用，输出预算 4096 |
| 规模 | 16 题 × 2 臂 = 32 次试验 |

两臂的初始材料逐例不同，`initial_material_sha256` 已记录，不是同一份材料换个名字。

## 结果一：可达性不变，材料减少 65.7%

"参考值可达"的判定不经过模型：参考编号必须确实出现在**这次回执准入可读**的某条原文里。它直接回答窗口规则唯一真正的风险——省掉正文是把答案推迟了，还是把它丢了。

| 方案 | 参考值可达 / 12 | 初始材料含参考值 / 12 | 初始材料均值 | 按需读取次数 |
| --- | ---: | ---: | ---: | ---: |
| window-bodies | **12** | 4 | 2390 字 | 8 |
| window-index | **12** | 0 | **820 字** | 10 |

**答案没有丢，只是不再预先摊开。** 索引臂的初始材料里一次都不含参考值（0/12，按设计如此），但 12/12 的参考值仍在准入范围内的原文中。

## 结果二：回答质量在这个夹具上变差了

| 方案 | 可回答题答对 | 其中实际作答 | 作答中答对 | 协议失败（截断 / 散文） | 无答案题正确弃答 |
| --- | ---: | ---: | ---: | ---: | ---: |
| window-bodies | **9 / 12** | 10 / 12 | 9 / 10 | 3（1 / 2） | 3 / 4 |
| window-index | 6 / 12 | 9 / 12 | 6 / 9 | 4（1 / 3） | 3 / 4 |

差距是 3 道题，分母是 12，只有一个夹具和一个模型——这不足以给出一个比值，但足以说明**方向**：在答案必须靠读取才能拿到的场景里，少给正文会掉答对率。

### 这个 6/12 是下界，因为它拿掉了规则自己的前提

生产里一条正文被 withhold 的**唯一**条件是：这条原文此刻仍然逐字留在本次请求里。代码上是 `withheld = 候选 ∩ window_message_ids(snapshot, covered)`（`plugins/akasha/runtime.py`），所以 withhold 掉的字节一个也没少，它们就在请求的历史部分。另一个会话的候选、或已被摘要覆盖的候选，都不在这个窗口里，必须保留正文。

这条不变量现在有回归守着（`tests/test_akasha_execution.py::test_recall_never_withholds_a_body_this_request_does_not_quote`），而且是突变验证过的：把那个 `∩ window` 去掉，测试立刻指名两条跨会话消息失败。

**本套件的 `window-index` 臂故意违反这个前提**：它把全部候选都当成已引用并 withhold 正文，而 reader 的请求里并没有那些原文——候选来自历史会话，不在读者这一轮的窗口里。因此它衡量的是"正文既不注入、也不在请求里"这种生产中不会发生的情形。**6/12 是把前提拿掉之后的下界，不是生产行为的估计。** 规则真正生效的条件下，读者手里本来就有那段字节，省掉的是重复注入。

那个条件下的回答质量本轮没有测——要测它就得让夹具把候选原文放进读者请求本身，这是下一步该补的对照。在补上之前，这份报告只给两个数：确定性的可达性（成立）与拿掉前提后的下界（9/12 对 6/12）。

逐题族看，差距不均匀，索引臂的失手集中在"没答"而不是"答错"：

| 题族 | bodies 作答 | bodies 答对 | index 作答 | index 答对 |
| --- | ---: | ---: | ---: | ---: |
| 首部事实 | 4/4 | **4/4** | 2/4 | 1/4 |
| 末页事实 | 4/4 | 3/4 | 3/4 | 1/4 |
| 中部事实 | 2/4 | 2/4 | 4/4 | **4/4** |
| 无答案 | 3/4 | 3/4 | 3/4 | 3/4 |

索引臂 6 次失手的构成：3 次没有返回函数调用，1 次答 UNKNOWN，1 次答 UNKNOWN 放弃，**1 次答出了正确编号却判为不成立**。最后这一次值得单说。

### 首部题的索引预览会露出答案，而"从预览作答"算不成立

索引行带 80 字预览。首部题把结论写在文档开头，于是预览里就包含承载答案的那一行——这可以直接从夹具核验，与模型无关：

```sh
uv run --frozen --no-sync python -c "
from eval.memory_depth import followup_corpus
from plugins.akasha.recalls import INDEX_PREVIEW_CHARS as N
fixture, cases = followup_corpus(4, version=3)
originals = [s[0]['content'] for s in fixture['haystack_sessions']]
for case in cases:
    if case['expected'] == 'UNKNOWN': continue
    report = [t for t in originals if case['expected'] in t][0]
    print(case['id'], '预览含答案:', case['expected'] in report[:N])"
```

首部题为真，末页题与中部题为假。`head-control-2` 就是这么答出正确编号的：`reads=0`、引用合法，但**没有任何一次原文读取**，所以 `supported_answer` 为假、判为不成立。

这是刻意的严格，不是漏洞：本项目的主张是"答案有可核对的原文出处"，从一行预览里读出的值没有这个出处。同一条规则下，首部题既不是导航题（两臂都拿得到值），也因此只衡量**答案是否仍然有出处**。真正只能靠读取拿到答案的是末页题和中部题，共 8 道。

## 代价：索引臂输入 token 更低，即使在最坏情况下

| | window-bodies | window-index |
| --- | ---: | ---: |
| 模型调用 | 24 | 26 |
| 输入 token | 54,356 | **50,839** |
| 输出 token | 10,658 | 10,606 |
| 读取后保留证据均值 | 3321 字 | 3275 字 |

索引臂多读了 2 次、多了 2 次调用，但因为初始材料小得多，总输入 token 仍然更低。**本夹具对索引臂是最坏情况**：它刻意把答案放在初始材料之外，所以几乎每题都要读。生产中窗口规则只作用于"原文仍逐字留在本次请求里"的候选——那种情况模型本来就不需要读，省下的正文是净省。真实对话的每轮注入开销由[免模型测量](../../../eval/cost_report.py)另给（2393 → 757 字）。

## 工程不变量（同一次运行内核对）

| 检查 | 结果 |
| --- | ---: |
| 查询只读、重载后逻辑状态一致 | 通过 |
| 原文窗口重读逐字节一致 | 18 / 18 |
| **图重载后再重读仍逐字节一致** | 18 / 18 |
| 越权原文读取被拒绝（非准入消息、跨范围） | 2 / 2 |
| 查询与读取未增加聊天调用 | 0 |
| 离线复核全部行 | 32 / 32，`complete: true` |

越权拒绝这一项值得单说：索引臂的回执**不呈现任何正文**，准入只来自索引行。复核确认它既没有因此放宽读取（不在准入内的消息仍被拒），也没有因此失去读取能力（索引行命名的原文可读）。

## 这份报告没有证明什么

- 没有证明窗口规则在日常对话里无损。它只测了"答案在初始材料之外、且正文也不在请求里"的情形，而规则的生效前提恰好相反。前提成立时的回答质量本轮没测，只证明了前提本身由不变量保证（withhold 的正文必然仍在请求里）。
- 12 道可回答题、3 道题的差距、一个模型、一个合成夹具——不足以给出窗口规则的质量折损比例。
- 没有证明更弱或更不愿调用工具的模型能跟上索引行。
- 首部题不衡量导航：两臂都能拿到值（一个从正文，一个从预览）。
