# 事件记忆：原文证据、独立重建与专项验证

日期：2026-10-19。Akashic 参考至 `21b38f0`，算法仍固定 `d85b00c`。本轮围绕原始经历保真、
证据展开和长期恢复升级宿主接线；固定算法文件没有修改。所有模型请求仅使用 Step5 Token Plan，
medium；BGE、Mem0 和测试共用项目 `.venv` / Python 3.14.6，没有使用现金模型或托管 embedding。

## 从原项目学习的重点

Akashic 的 [ADR0006](https://github.com/kachofugetsu09/akashic-agent/blob/21b38f0e102d9e1bdc5576725635dce29f135c0c/docs/decisions/0006-akasha-v2-is-the-canonical-explicit-memory-engine.md)
与[当前 recalls](https://github.com/kachofugetsu09/akashic-agent/blob/21b38f0e102d9e1bdc5576725635dce29f135c0c/plugins/akasha/recalls.py)
把精确回忆和联想补全分开，正文从原消息读取；学习图、显式查询和提交后的学习有不同边界。
其固定向量、重放和发布合同，是长期记忆的工程基础。README 的产品定位则是持续陪伴、主动联系
和空闲工作，并未用单一 QA 分数定义整个 Agent。

Kirakira 据此突出三项可验证能力：带关系与时间的原始经历、能继续展开的引用，以及脱离派生图
仍可恢复的学习输入。算法出处、原文事实源和本项目宿主工作分别说明，不把移植算法称为原创。

## 本轮实现

1. `fetch_messages` 直接接受召回的完整 JSON 消息 ID 列表，合并邻近窗口并标记 anchor。
   缺失任一原文时不返回部分成功，旧 `session:seq` 也必须对应实际存在的消息。
2. 一次恢复或 query 共用一份只读 SQLite 视图，校验所有命中的原文摘要。并发修改下保持单视图，
   后续读取明确发现已变化来源。
3. 新在线向量先以 float32 保存到 Session 固定缓存，键绑定消息身份、内容摘要和完整空间
   （模型、端点、声明维度），然后才学习图。学习中断后复用缓存，丢失派生图后仍有重建输入。
4. checkpoint 中已归一化向量按原值恢复，修复重复归一化引入的末位分数漂移。已有快照可读，
   旧历史不自动补算；旧 model-only 缓存兼容但单独标明身份范围。

接口与数据边界见 [ADR0013](../../decisions/0013-original-message-evidence.md)。

## 原图不可用时的恢复

使用真实 BGE 的 24 份合成历史，每份 12 个会话、48 个完整消息对，横跨约一年。
重建函数只接收 `sessions.db`，其临时工作区没有原图；保留原图仅用于最后比对。

| 验证 | 实际结果 |
| --- | ---: |
| 源库独立重建 | 24/24 |
| 重建的完整 turn | 1,152 |
| 全部学习表 + 完整 `kirakira_checkpoint` JSON 一致 | 24/24 |
| 网络连接尝试 | 0 |

验证包含 socket 连接拦截与固定输入校验，不调用模型补算缺失内容。原文展开使用实际 SessionManager，
不是伪造 source_ref。图级逻辑 hash 外还单独比较消费 cursor、binding、源 stream 和向量空间，
没有把“同样的命中数”当作状态一致。

新缓存接线后重新索引，24 题三组的 reader context 与已冻结初始输入逐字节一致，因此沿用原始
问答结果，没有重新选答案。初始与最终源码摘要、输入和恢复凭据均保留。

## 公开历史上的源库 IO

同一固定旧版本 `acbe0b9`，在先前公开语料的三张冻结图上测量；每方案三次恢复、每次五次 query，
使用缓存向量。同机串行，旧版本总是先测，存在热缓存与其他进程负载影响；计时不代表普遍加速比。

| 图规模 | 恢复源连接：旧→新 | 每次 query 源连接：旧→新 | 恢复 p50：旧→新 | query p50：旧→新 |
| --- | ---: | ---: | ---: | ---: |
| 216 turns | 649→2 | 20→1 | 473.53→229.59 ms | 97.07→84.25 ms |
| 245 turns | 736→2 | 20→1 | 523.16→245.90 ms | 69.09→58.18 ms |
| 301 turns | 904→2 | 18→1 | 595.27→256.33 ms | 62.98→53.65 ms |

来源身份、正文、证据和顺序一致，学习状态与原文文件不变。修复二次归一化后，与旧实现的最大
score 差为 `1.11e-16`；脚本明确记录该差异，最终版本自身恢复的记录则要求严格相等。
连接数降低是确定的工程改进，不代表图计算、历史分词或 embedding 已变成常数成本。

## 六类专项题

在模型调用前固定 seed、数据、答案、全部 24 个 ID 和协议：助手建议中的对象关系、精确标识、
历史更正、跨会话拼接、用户偏好、无证据弃答，各四题。每组最多十对原文或十条提取事实、
24,000 字符；真实本地 BGE，reader 使用同一 Step5/medium/8,192。

答案按严格 JSON 的精确值判定，不使用模型 judge；所有错误计入分母。七组共 168 次 reader。
两批文件分别涵盖互不重复的 arm，不挑选同题多轮答案。

| 方案 | 正确数 | 执行/格式错误 |
| --- | ---: | ---: |
| 无记忆 | 4/24 | 0 |
| 近期窗口 | 7/24 | 0 |
| Dense | 24/24 | 0 |
| BM25 | 24/24 | 0 |
| Dense/BM25 RRF | 24/24 | 0 |
| Akasha2 双通道 | 24/24 | 0 |
| Mem0 OSS 2.2.1 | 23/24 | 1 |

Mem0 唯一错误是 `{"answer": "unsweetened black tea"}`，协议要求数组。文字答案正确，保留
格式失败而不事后修分，不能据此解释为关系记忆或语义召回失败。简单专项题被多个基线同时解决，
因此这组数据支持功能合同，不证明图关联的普遍优势；与既有 72 道公开问题分开报告。

Mem0 完整写入 24/24、48 次模型响应成功，写入 input/output 为 425,337/143,949 tokens。
本图引擎写入没有生成式 LLM 调用，使用本地固定向量；仍承担原文、向量和图状态的存储与计算。
这组短历史上 reader input 为双通道 14,391、Mem0 16,196。先前公开 12 题里 Mem0 显著节省 reader
上下文的结果仍保留，不能把不同工作负载拼成整体成本结论。

## 真实 Agent 工具链与回归

原生 Step5 执行 recall→原样传递 JSON source_ref→fetch→核对更正→回答；包括重启前后、v1/v2
和显式读写工具。三轮严格断言分别为 **5/6、5/6、6/6**，不只发布最好一轮。

第二轮唯一失败的最终码与原文列表均正确，模型额外解释废弃码，违反“只输出最终码”的严格断言。
第一轮失败未留下完整过程，不能事后推断原因；后两轮已增强失败诊断，未放宽断言。

全量 **702 passed、4 subtests passed**（51.78 秒），22 条既有 Telegram 警告。
最初新增测试的探针初始化错误和真实归一化问题均保留，修复后定向 16 项及全量通过。
