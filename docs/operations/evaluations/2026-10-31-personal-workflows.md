## 明确交办与自主兴趣分开

创建邮件关注时，重要邮件可能早已落入 Junk。现在可指定文件夹，默认 `mail_initial_limit=0`，只监听之后的新邮件；用户明确选择时，回查最近 1—50 封实际存在的邮件，再接回新增邮件监听。窗口按 `UID SEARCH` 返回的实际 UID 选取，不按 UID 数字差猜测数量，也不是不断向前找满 N 封匹配邮件。

计划先持久保存文件夹 UID 身份、固定上界和选中的 UID，再每批读取最多 10 封。初始窗口读完才追赶回查期间新到的邮件。源消息与关注规则进入原有 EventMail、Wake、记忆和投递路径，没有另建一套邮件正文或任务事实库。

真实运行暴露出一个需要修正的语义：模型可能将“只提醒有行动或截止时间的邮件”配置为 `interest`。普通兴趣池可以暂不调查单条消息，但用户明确要求“现在检查最近一封”应当进入调查。修复只给持久初始窗口标记 `owner-requested`，让它逐条接受判断；**没有抬高兴趣分，也没有强制发送通知**。窗口结束后的新邮件仍保留原 `interest` 设置。工具说明也区分了“是否逐条调查”和“调查后是否通知”。

普通中文交办的验收通过本轮原始用户输入、真实创建工具回执和持久关注相互核对：文件夹、数量、会话归属及通知规则必须对应实际原话。创建成功、完成检查、发出通知和登记提醒是四件不同的事。

## 邮件与提醒的真实模型记录

每次完整计划包含两个独立内容判断：Junk 中创建前已存在的补材料要求应提醒；INBOX 中普通推广应跳过。文件夹只限定范围，不充当重要性标签。提醒登记和重启保持另列，不并入这两个判断的分母。

| 阶段 | 输出预算，含推理 | 原始结果与归因 |
| --- | ---: | --- |
| 第一轮 | 4096 | 配置 HTTP 429；0 个内容判断、0 次提醒登记 |
| 第二轮 | 4096 | 评测设置污染：自然交办已创建关注并实际分享重要邮件，评测又用 RPC 建重复关注，后者正确跳过；广告创建后最终确认回复 HTTP 429。整轮保留失败，不用于判断质量或产品延迟 |
| 第三轮 | 4096 | 重要信因 `interest` 未进入调查而超时；广告的独立 each-update 判断为 skip，通过。没有完成重要邮件通知及提醒闭环 |
| 第四轮 | 4096 | Junk 请求在创建前 HTTP 429；广告达到输出长度上限，Runtime 安全拒绝执行截断批次的工具。0 个邮件判断、0 个调度任务 |
| 第五轮，最后一次 | 8192 | 仅配置最多重试六次，全部 HTTP 429，79.057 s；两个内容判断和两项提醒步骤均未开始，整轮失败 |

第二轮的诊断来自原始账本、工具回执和来源状态：实际共有五个关注，旧评测只追踪两个手工关注；三个自然创建的关注仍启用。同一 Junk 原始邮件对应一条已结算、有 settlement 的来源和一条重复待处理来源，账本实际通知为一条。重复跳过不能解释成模型认为 Junk 不重要。广告的已提交关注在最终回复失败后被旧评测遗失，重启时开始调查，破坏了“0 新模型调用”断言；没有证据表明重要通知被重发。

## 2026-11-01：停服后的恢复与提醒修补

按用户要求停止常驻服务，确认 `inactive / dead`，本轮保持关闭。下面的测试全部使用仓库外的隔离工作区，新代码尚未部署到原工作区，不使用 Telegram 或私人邮箱作为测试收件位置。

### 已读取的邮件不会因提交失败而消失

原采集意图现在冻结实际待提交内容和当时规则。原生 TLS / EventMail 回归在首次提交前注入失败，随后删除服务器上十封已读邮件、修改关注规则并重启，仍接纳原十封内容、原时间和原规则；其余两封与随后新邮件使用新规则。

暂停期间只收尾已有回执，不提交尚未接纳的批次；恢复后继续原批次。提交后再故障、再暂停和重启，也不会重复事件。查看时间线不启动提交。旧版没有保存正文、且来源已经消失的未提交意图，无法从不存在的材料补回原文。

### 提醒的日期属于用户原话

两个固定例子让推理跨过目标时刻：14:29 交办 14:30，以及 23:59 交办 00:01。使用提交前版本的实际函数，两个目标均偏移一天；修补后偏移均为零。真实工具回归另外核对原始 Input、忽略模型自填的起算日期、持久任务与重试回执。

四个夏令时过渡下的 `after / every` 例子，要求实际经过两小时：旧计算分别得到 3600 或 10800 秒，修补后全部为 7200 秒。两个不存在或出现两次的当地时刻，从静默接受改为要求确认，明确 UTC 偏移仍被保留。这里共八个确定性反例，不是模型质量分数或速度基准；时间计算依据见 [Python datetime](https://docs.python.org/3.14/library/datetime.html) 和 [ZoneInfo](https://docs.python.org/3.14/library/zoneinfo.html)。

对话规则同时区分本轮相对时间与历史原文时间：旧邮件里的“明天”不能移到今天。用户已经明确委托且条件齐备时直接登记；发现期限、记入记忆、保存提醒和未来送达分别陈述。

### 回访停止后不自重试，新输入也不会被漏掉

子任务的 `abandon` 成为失败终态，重启不再次执行。回访被停止时显示 paused，生成失败或耗尽步数时显示 blocked；原始结果保留，等待下一条真实用户 Input。Control 不进入 Delivery，失败记录只保存异常类型，不复制供应商正文。

目录变化与回访退出共用一个可合并的唤醒事件，不增加轮询或持久队列。三条既有原生重启测试分别检查 pause、abandon、异常，并刻意先消费新 Input 的目录事件，再放行旧回访退出；不发送第三条消息，仍能接续投递。只在内存恢复旧跟随循环时，三条均因漏唤醒超时失败。另一个真实 CompositionRoot 准入测试证实：未结束的工作仍受容量限制，已经完成但待回访的结果不再占工作名额，同一效果重试也不占第二个名额。

参考源的新修补也用于网页资料读取：真实 MCP 子进程、HTTP 驱动和 Unix 控制连接验证，孤立 UTF-16 代理项替换为可读标记，中文与完整 emoji 保留，成功、错误和后续 JSON-RPC 仍能处理。它验证协议容错，没有连接真实浏览器账户；来源版本记入已有来源清单。
