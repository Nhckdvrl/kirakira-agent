# 个人助理工作流：邮件、提醒与后台回访

日期：2026-10-31。本轮实现并检查两条个人助理工作流：从指定文件夹回查已有邮件、核对行动期限并由用户确认提醒；把资料调查交给后台，继续聊天，之后接收和查询结果。完整数据集中在一份[白名单证据](artifacts/2026-10-31-personal-workflows/evidence.json)。

**真实模型的完整闭环尚未通过。** 最后一次邮件验收在配置阶段连续六次 HTTP 429 后退出，两个内容判断和提醒步骤均未开始；最后一次后台验收也遇到六次配置限流，固定六项均为 `not_run`。没有切换现金端点，没有把协议通过、工程回归或事后找到的成功工具作用替代闭环通过。

已经能够证明的是具体边界：默认不翻旧邮件；明确回查时冻结实际邮件窗口；取消和提交后故障仍沿原始回执恢复；重要性判断、实际通知、用户确认及提醒登记分别留事实。最终部署的 21 个重要插件来源核对、数据保留和健康检查通过，工程回归为 168 项通过。下面保留全部运行阶段及未完成部分。

## 明确交办与自主兴趣分开

创建邮件关注时，重要邮件可能早已落入 Junk。现在可指定文件夹，默认 `mail_initial_limit=0`，只监听之后的新邮件；用户明确选择时，回查最近 1—50 封实际存在的邮件，再接回新增邮件监听。窗口按 `UID SEARCH` 返回的实际 UID 选取，不按 UID 数字差猜测数量，也不是不断向前找满 N 封匹配邮件。

计划先持久保存文件夹 UID 身份、固定上界和选中的 UID，再每批读取最多 10 封。初始窗口读完才追赶回查期间新到的邮件。源消息与关注规则进入原有 EventMail、Wake、记忆和投递路径，没有另建一套邮件正文或任务事实库。

真实运行暴露出一个需要修正的语义：模型可能将“只提醒有行动或截止时间的邮件”配置为 `interest`。普通兴趣池可以暂不调查单条消息，但用户明确要求“现在检查最近一封”应当进入调查。修复只给持久初始窗口标记 `owner-requested`，让它逐条接受判断；**没有抬高兴趣分，也没有强制发送通知**。窗口结束后的新邮件仍保留原 `interest` 设置。工具说明也区分了“是否逐条调查”和“调查后是否通知”。

普通中文交办的验收通过本轮原始用户输入、真实创建工具回执和持久关注相互核对：文件夹、数量、会话归属及通知规则必须对应实际原话。创建成功、完成检查、发出通知和登记提醒是四件不同的事。

## 协议与持久恢复

实验使用自己的本地 TLS IMAP 服务和合成邮件，不登录私人邮箱。INBOX 中放推广；Junk 中放两封窗口外旧信和十二封近期邮件，故意留下 UID 空缺，近期 UID 为 50—61，冻结后再送入 UID 62。客户端使用正式采集器，实际建立 TLS 连接并执行认证、EXAMINE、SEARCH 和 FETCH。

| 检查 | 实际结果 |
| --- | --- |
| 默认只监听新邮件 | 14 封已有 Junk 邮件不读取正文，0 次 FETCH |
| 明确回查最近 12 封 | 冻结实际 UID 50—61，计划阶段不 FETCH |
| 分批读取 | 首批 10 封，后批 2 封，窗口外旧信排除 |
| 原文期限 | `2026-11-03 18:00（UTC+8）` 保持在实际采集结果中 |
| 回查期间新到 | 窗口清空后再读 UID 62，重复 poll 为 0 新条目 |

原生恢复另由已有综合回归检查：真实 TLS、CompositionRoot、Owner 状态和 EventMail 共同运行，在第一次 FETCH 前验证计划已保存；冻结后新到邮件，取消并销毁重建；原生提交成功后注入 `_finish` 故障，再删除上游已读邮件并重启，依照原提交回执续读。`interest` 关注的 **12 封历史邮件全部具有 requested-review，随后 1 封新邮件没有该覆盖**，13 个来源事件不重复；UID 重建也不重新回查。相关文件的 13 项回归通过，并包含在最终工程回归中。这不涉及真实模型判断或私人邮箱送达。

## 邮件与提醒的真实模型记录

每次完整计划包含两个独立内容判断：Junk 中创建前已存在的补材料要求应提醒；INBOX 中普通推广应跳过。文件夹只限定范围，不充当重要性标签。提醒登记和重启保持另列，不并入这两个判断的分母。

| 阶段 | 输出预算，含推理 | 原始结果与归因 |
| --- | ---: | --- |
| 第一轮 | 4096 | 配置 HTTP 429；0 个内容判断、0 次提醒登记 |
| 第二轮 | 4096 | 评测设置污染：自然交办已创建关注并实际分享重要邮件，评测又用 RPC 建重复关注，后者正确跳过；广告创建后最终确认回复 HTTP 429。整轮保留失败，不用于判断质量或产品延迟 |
| 第三轮 | 4096 | 重要信因 `interest` 未进入调查而超时；广告的独立 each-update 判断为 skip，通过。没有完成重要邮件通知及提醒闭环 |
| 第四轮 | 4096 | Junk 请求在创建前 HTTP 429；广告达到输出长度上限，Runtime 安全拒绝执行截断批次的工具。0 个邮件判断、0 个调度任务 |
| 第五轮，最后一次 | 8192 | 仅配置最多重试六次，全部 HTTP 429，79.057 s；两个内容判断和两项提醒步骤均未开始，整轮失败 |

第二轮的诊断来自原始账本、工具回执和来源状态：实际共有五个关注，旧评测只追踪两个手工关注；三个自然创建的关注仍启用。同一 Junk 原始邮件对应一条已结算、有 settlement 的来源和一条重复待处理来源，账本实际通知为一条。重复跳过不能解释成模型认为 Junk 不重要。广告的已提交关注在最终回复失败后被旧评测遗失，重启时开始调查，破坏了“0 新模型调用”断言；没有证据表明重要通知被重发。

第三轮的 Junk 初分约 0.404，普通兴趣池阈值为 1.5；来源已读，但没有任何 selection 或调查。22 条业务模型回执全部为 success，工作流仍然失败，说明 API 成功次数不能替代任务完成。其广告项另做只读后验核对：只有一次 selected，原始 Input、当前 investigate 阶段终态、成功 Skip 工具回执及 EventMail `released` 相互对应，0 次投递；没有使用旧选择的决定。

第四轮不是观察器误报：广告的原生失败事实明确为 4096 输出预算耗尽，截断工具批次未执行；它与 HTTP 429 分开记录。对实际 `JobStore` 只读检查为 **0 jobs、0 operations、0 fires**，并非从缺少 `deadline_reminder` 字段推断。

提醒实验要求：先确认没有擅自建任务，收到重要通知后，用户只说“刚才那封邮件，截止前 24 小时，上海时区提醒一次”，不重述期限、不点工具名。随后核对真实成功 ToolResult、同次原始输入、持久 Operation 和唯一 notify/at 任务。第四轮的冻结材料记录：

| 日期角色 | 精确值 |
| --- | --- |
| 邮件 Date，合成发送时间 | `2026-10-31T12:15:03+00:00` |
| 原文要求的截止时间 | `2026-11-03T18:00:00+08:00` |
| 预期提前提醒 | `2026-11-02T18:00:00+08:00`，即 `2026-11-02T10:00:00Z` |
| 时区 | `Asia/Shanghai` |

这些是验收条件，**本轮没有完成这条提醒登记与恢复闭环，更没有声称未来提醒已经送达**。后续入口用运行日期加三天的上海时间 18:00 构造未来期限，邮件 Date 另记实际夹具发送时间；协议原文保留实验仍使用冻结日期，不改写旧结果。

## 后台交办与完成回访

固定六项分别检查：后台任务真实接纳、调查期间仍可聊天、取得实际来源结果、完成后通知、后来询问能查到结果、重启后结果仍在。父会话说“我去查”不替代子任务回执；结果页面被读过也不替代通知和恢复完成。

| 阶段 | 输出预算 | 原始结果 |
| --- | ---: | --- |
| 第一轮 | 4096 | 等待父确认 60 s 后失败；旧观察器没有保存固定六项分母，原始 `cases=[]` 不算通过。原生审计为 Shell 两次、web_fetch 两次、0 次子 Agent 调用，实际仍在前台内联调查 |

## 失败边界、成本与观察器

本轮重试包装单独记录 **28 次配置尝试：25 次 HTTP 429、3 次通过**。它不覆盖全部配置或业务请求，也不是整个账户流量。一个错误文本的安全分类为并发限制；第二轮 30 条原生调用生命周期的重叠峰值为 2，但该计数不是 HTTP 连接跟踪，不含配置探针和其他客户端，不能据此推断供应商固定阈值或将 Runtime 全局串行化。

成本按原始业务回执保留：受污染的第二轮为 30 次调用、22 success / 8 error、170047 输入 tokens / 11917 输出；第三轮为 22 success、184758 输入 / 8686 输出。累计输入包含多轮重发，配置探针另计，失败阶段缺失用量不记为零费用。这些数值没有用于营销模型或宣称全面领先。

8192 是最后新实验的显式条件：同模型、driver、订阅端点和 32768 上下文容量，仅提高该私有评测配置的输出上限，未改生产模型配置。4096 长度失败保留；未执行截断调用来绕开安全边界，也不把不同条件下的结果直接算作优化收益。

观察器已按问题逐项修补：自然交办不再额外 RPC 建关注；原始输入对应的成功工具回执与已提交作用分开查；最终确认失败仍保留真实任务并单独计失败。超时通过既有 conversation pause/drain 停止合成父轮、排空后再查作用，不撤销已受托调查来伪称未创建。决定只取最新选择、当前已结束阶段和领域结算；日期匹配加数字边界；重启基线移到进入新 Runtime 前；后台读取复用真实 `read_async` 合同。

第三、第四轮原观察器的重启零调用基线位于 Runtime 进入之后，所以其断言只覆盖随后检查窗口，**不证明启动恢复阶段零调用**。新观察器的 AST、Ruff 与日期反例检查通过，但最后邮件运行停在配置阶段，尚未用真实模型完整执行这些修补后的判断。没有重写旧 raw 来补成新成绩。
