# 本地使用体验与会话接续

日期：2026-10-31。本轮同时检查常驻实例、SDK、CLI、真实网页、Telegram 适配器、模型连接和文件系统。功能验收、真实模型等待与确定性机制实验分别记录，完整数值见[脱敏证据](artifacts/2026-10-31-runtime-experience/evidence.json)。

调查得到两个需要同时处理的事实：常规暖请求中，模型调用占据数秒；NFS 上也确实出现了模型开始前的长时间停顿。进一步的机制跟踪证实，两次数秒等待落在 NFS WAL 文件的内核解锁调用中，不能把所有迟缓都归给远端服务。网页切换重复建立连接、旧会话需要手动复制，以及长消息片段不能继续展开，也是个人助理日常使用中可以直接改进的问题。

最终部署的健康接口和 16 个关键插件版本核对通过，164 项工程回归通过，但**最新真实回答验收未通过**：正式实例四条 SDK、两条 CLI 请求全部收到上游 HTTP 429；Telegram 验收也在六次配置探针限流后退出，没有开始场景。最新机制实验的 NFS 新工作区首轮仍为 **26.008 s**，不能宣布延迟已经解决。下面同时保留早期成功、开发中间结果和最终失败，避免用较早的 3/3 投递或偶然较快样本替代当前状态。

## 个人助理的具体改进

显式会话引用把“接着上次聊的事情”变成可操作的入口：把侧栏的旧会话拖进输入框，说明要继续讨论什么，也可只发送引用。网页与 Python SDK 使用相同的 `session.reference` 输入片段。一次最多四个引用，按会话保存草稿；重复、当前会话和无效目标受到校验。

输入只提交坐标和展示标题。模型需要资料时，通过 `read_session` 翻阅原始用户和助手正文；普通页最多 50 条、24000 字符，单条正文先展示 4000 字符。长消息提供消息 ID、原始长度及下一个偏移，可以继续展开。读取会重新核对被引用会话的当前内容，因此后来改口仍能被读到；原有记录不会被更正内容覆盖。读取权限来自当前调用前缀中的真实引用，标题和历史正文不授予附加权限，工具结果和内部推理不通过该正文入口转交。

这与长期记忆互补：用户明确知道要接哪段对话时直接指定来源，只有模糊线索时仍由记忆召回。它没有把所有历史塞进每次模型请求，也没有建立第二份历史正文库。用法见[接续其他会话](../../handbook/start.md#接续其他会话)。

同一轮还整理了几个影响持续使用的路径：网页切换保留健康 WebSocket，丢弃旧会话迟到的插件事件；主动调查读取近期上下文时从尾页取得最多 20 条实际对话；旧召回回执的兼容查找先筛选会话、来源和序列，再解码候选；Wake 状态库不再每次打开都重复执行完整性初始化。这些改动沿用现有 Runtime、原始日志、权限和投递路径。

## 测量方法与边界

生产实例上的六项基线使用新增的内部合成会话，明确排除记忆学习，没有往真实用户会话伪造输入，也没有重置已有历史。SDK 记录接纳、首次可见正文回调、最终输出和 Models 回执；CLI 使用相同的常驻实例，进程启动到退出另计。模型的 first token 可能不是公开正文，不能代替首次可见内容。

独立 Runtime 分别放在 NFSv4 和本地 XFS，使用相同模型配置与同一批只读 Markdown 快照。没有复制生产图或会话数据库；也没有将正式工作区搬到可被清理的临时目录。两个文件系统的运行顺序并未随机化，不能将不同时间的总耗时直接相减，声称是存储改进的因果收益。

XFS 对照只改变测试工作区的位置，代码、Python 环境和向量资产仍使用同一套路径；没有测量把整套服务、依赖与权重一起迁入本地盘的效果。

隔离实验中的“冷”指全新工作区刚完成模型和向量配置后的第一次请求，包含必要初始化；它不是已常驻实例每次新会话都会付出的成本。生产 SDK 基线与这些新工作区实验分开列示。

除 Telegram 外，冷暖延迟检查的每条请求使用新的合成短期会话；“暖”指宿主、编码器和连接已工作过，不表示已经覆盖真实长会话的上下文增长。长资料接续另作功能实验，不能替代长时间、多轮使用的延迟分布。

`native_driver_ms` 是实际 driver 与流式调用的墙钟时间；总耗时减去它得到的余量还包含接纳、准备、调度、持久化和观察端的开销，**不等于 CPU 时间，也不是纯磁盘时间**。阶段日志以 `reply.begin` 为相对零点。直接模型诊断在原生请求结束后顺序重放相同请求字节；供应商缓存、队列和生成内容可能变化，因此只用于确认等待存在于哪里，不计算产品 A/B 加速比。

真实网页运行编译后的界面、Chromium 和原生后端。网络 `latency_ms=80` 是浏览器模拟参数，不是实测数据包 RTT。Telegram 使用隔离实例、合成入站和实际 Bot API 投递，关闭该实例的轮询，避免抢占在线机器人。它验证适配器到实际送达回执，**不包含手机发出消息、Telegram 入站排队或手机显示的时间**。

公开文件仅保留白名单指标、阶段、调用计数、用量和源码摘要。会话正文、模型回答与推理、私聊标识、档案文件名、首次登录密码和凭据留在私有目录。

## NFS、事件循环与模型等待

### 小事务与原生 Ledger 分开测

每项每种文件系统顺序运行 24 次，只操作自己的可删除测试目录。读取为缓存读取，不是冷缓存、并发负载或吞吐基准。

| 操作，中位数 | NFSv4 | 本地 XFS |
| --- | ---: | ---: |
| SQLite FULL / DELETE 小事务，包含打开与关闭 | 16.260 ms | 0.565 ms |
| 原生 Ledger WAL / NORMAL 追加，复用 writer | 4.994 ms | 0.112 ms |
| 原生 Ledger 缓存读取，新 reader 快照 | 4.730 ms | 0.045 ms |
| 4 KiB 文件写入与 fsync | 2.986 ms | 0.249 ms |
| 小文件缓存读取 | 1.362 ms | 0.014 ms |

两种 SQLite 策略不能混用。FULL / DELETE 的差距不能直接套到正式 Ledger 的每一次提交；原生读写结果仍说明 NFS 上高频小操作值得减少和移出事件循环。

模型注册表的独立组件对照使用同一含三个模型的合成 NFS 库：`read_snapshot` 前后各顺序采样 30 次，中位数由 **4.605 ms** 降为 **1.875 ms**。读取复用空闲连接并核对版本，写事务繁忙时使用独立只读事务，保留 `default`、`fast`、`agent`、`vision` 四种角色。这条路径不按具体模型名分流。这里只比较注册表读面，没有调用外部模型；这个数毫秒收益不能直接当作整轮对话节省了多少秒。

### 去掉远端生成的机制诊断

另用确定性 loopback 模型运行正式 Runtime、插件和同样的 Markdown 快照，排除远端生成波动。这不是模型能力或记忆质量实验；夹具回报的一输入、一输出 token 是合成值，不进入真实模型费用统计。

冻结源码完成记忆、Reply 跟随、投递调度及 UI/Gateway 页读的可拆分 I/O 修补后，最新完整机制运行仍有明显的 NFS 首轮慢例：

| 存储 | 新工作区首次问候 | 后续在线确认 | 首次 driver |
| --- | ---: | ---: | ---: |
| NFSv4 | **26.008 s** | **0.902 s** | 23.28 ms |
| 本地 XFS | **0.838 s** | **0.283 s** | 2.57 ms |

四个请求都完成，自建临时工作区正常删除。NFS 首轮的材料读取 worker 为 **23.854 s**，其中 1176 个 worker 采样落在 `attachments_for` 的 SQLite 查询行。主线程的 1216 个采样在事件循环等待，但仍有 16 与 8 个采样分别在 `save_binding` 的相邻行，另有少量模型注册表读取采样；不能写成主线程完全没有同步读取。这次没有系统调用跟踪，不能断言这个慢 worker 与前次观察到的解锁调用具有完全相同的底层原因。

这组数据没有证明稳定的 NFS 首轮收益。下面保留早期与中间阶段，**4.882 s 和 15.637 s 都是中间样本，不是当前最新首轮速度**；不同 runner 还包含观察器修正，不能把数值差额全部归成产品加速。

| 存储 | 首次问候 | 后续在线确认 | 首次 driver |
| --- | ---: | ---: | ---: |
| NFSv4 | 10.866 s | 1.182 s | 31.93 ms |
| 本地 XFS | 0.840 s | 0.304 s | 10.58 ms |

NFS 冷请求的主线程采样在两条记忆后台调用链中，分别有 217 和 196 次落在 `MessageReader.snapshot_heads`，对应消费与写图路径。采样支持同步文件读取阻塞事件循环的诊断，但采样数不是精确函数耗时；并行文件任务的 `work_ms` 也可能包含锁、CPU 与文件系统等待。原始阶段和脱敏栈在证据的 `deterministic_io_before` 中保留，作为后续修复复测的基线。

先把记忆后台读取移入文件 worker 后，中间复测的 NFS 冷、暖请求为 **9.939 / 0.556 s**，XFS 为 **0.849 / 0.312 s**。主线程已不再采到 `snapshot_heads`，但 NFS 冷轮仍然很慢：前台等待的 `committed_snapshot_async` 实际工作耗时 **8.532 s**，随后模型才开始。这个阶段改善了事件循环阻塞，不能写成已解决冷请求；完整中间结果也保留在证据中。

继续避免新图启动时重复消费，并调整模型注册表的读取路径后，用可维护的 `mechanism` 命令完整复测：NFS 为 **4.882 / 0.577 s**，XFS 为 **0.828 / 0.324 s**，四个原生请求均完成，临时工作区正常清理。NFS 首次请求仍有 **3.492 s** 停留在已提交快照入口；按该次源码摘要核对，worker 的 172 个采样落在读取 `message_prefix_revision` 的 SQLite 查询行。采样不能进一步区分 NFS 锁、I/O 和 GIL 等底层原因。该阶段没有把“离开主线程”当成“前台不再等待”，也没有把这次新工作区首轮成本当成常驻聊天的普遍延迟。

第二次部署阶段的另一轮完整机制复测为 NFS **15.637 / 0.565 s**、XFS **0.820 / 0.243 s**。NFS 材料读取 worker 为 **9.287 s**，采样落在 `attachments_for`；来源查询 worker 为 **5.043 s**，采样落在 `source_names`。当时主线程 493 个采样在事件循环等待，247 个仍在 Delivery Policy 的同步消息 SQL 读取。该路径随后移入 worker；最新首轮仍出现 26.008 s，说明保持事件循环可调度和消除前台存储等待是两个不同问题。

为进一步归因，另做一次只采系统调用元数据的 `strace` 实验，不捕获 read/write 正文：

| 实际系统调用 | 文件 | 时长 | 返回 |
| --- | --- | ---: | ---: |
| `fcntl(F_SETLK, F_UNLCK)` | NFS 上的 `sessions.db-shm` | **9.402 s** | 0，成功 |
| `fcntl(F_SETLK, F_UNLCK)` | 同一文件 | **4.084 s** | 0，成功 |

两次等待分别与快照查询和附件查询中的慢 worker 对齐。它们是内核层的文件解锁调用耗时，不能再描述为模型推理或 Python 线程锁耗时；查询只是触发 SQLite 锁协议的上层位置。该跟踪仍无法区分 NFS 客户端内核、RPC 排队和存储服务端的具体贡献。`strace` 有扰动，其 NFS 首轮 **15.112 s** 仅作归因证据，不能替代未跟踪的各阶段正式机制测量；最新未跟踪结果仍是 **26.008 / 0.902 s**。

SQLite 官方明确说明默认 WAL 实现不支持网络文件系统，并单独说明网络文件系统上的同步、锁和可靠性边界。因而这里存在部署层面的限制，不能承诺仅调整 Python 就消除 NFS 尾延迟。[WAL 文档](https://sqlite.org/wal.html)、[网络文件系统说明](https://sqlite.org/useovernet.html)。本机存在本地磁盘挂载，但当前账号尚无已确认可写的持久本地位置，不能据此说“机器没有本地盘”。本轮保留正式工作区的位置，未将长期数据迁入临时 XFS 目录；持久本地位置需要单独落实。

本轮仍保留必要的同步契约边界：Delivery execution 的直接被动准入保留与活动状态的原子先后关系，`ReplyCompletion.activity` 维持其公共同步接口。没有为绕开等待而改变这两处语义，也不宣称主线程完全没有同步 SQL。移动可拆分的读取可以改善并行响应；前台必须取得的数据库结果仍会等待实际存储，所以可靠的持久本地位置不能由包线程代替。

### 连接与远端服务

独立连接检查首次 222.1 ms、复用连接后 93.6 ms；首次 TCP 与 TLS 分别约 63.8 ms、65.0 ms。真实请求的同字节重放为 1.965—6.117 s，主要落在等响应头和正文的阶段。重放时隔离 Runtime 仍在同一个事件循环上运行，已知的同步 I/O 也可能干扰调度，所以这不是完全脱离 Harness 的远端生成基线，不能将整个时长都归给服务端。服务端排队、预填充、推理、网络和客户端调度的精确比例仍未分离。

最小生成探针收到 HTTP 429，没有正文，不计作成功生成。最终配置记录快照的 **36 次尝试中，30 次为 429、6 次通过**；包含第一次完整主链在开始场景前遇到的六次 429，以及最终 Telegram 验收的六次配置失败。此前另一次完整主链成功开始，结果单独列示。这些是本轮保留的配置尝试，不是整个账户全部限流情况，也不计入任务准确率。失败时没有切换现金端点。请求成功与模型首段时延都受到共享端点状态影响。

| 六次消息可见时间 | 84.6—176.6 ms | 86.5—283.3 ms |
| 浏览器错误 | 0 | 0 |

可以确认重复重连被消除；最新复测的侧栏和最慢切换均比对照慢，**没有证明总体提速**，也不构成弱网总体速度收益。当前界面另外通过五项真实交互：重复引用拒绝、会话草稿隔离、切回恢复引用、移除引用、自引用拒绝。它验证实际 UI 与原生后端配合，不是组件快照测试。

上表采用最终 UI/Gateway 页读修补后的独立复测，没有配置或调用聊天模型。两份先前界面实验也保留在同一证据文件的 `browser_intermediate` 与 `browser_after_reply_follow`，没有挑出较快的单次切换替换原始结果。

## 长原文与后来更正的真实读取

固定合成材料含一条 **6358 字符**的历史，目标事实在首个 4000 字符窗口之外。当前会话提交引用片段，按 UTF-8 JSON 计 **151 字节**，不包含完整 SDK/RPC 请求的开销。由真实模型调用工具读取资料，再在原会话追加一条新决定，要求当前会话重新核对。

| 步骤 | 实际结果 | 工具 / 模型调用 | 完成时间 |
| --- | --- | ---: | ---: |
| 读取长历史末段 | 回答包含全部目标值；实际调用偏移 `4000` 的后文窗口 | 2 / 3 | 13.383 s |
| 原会话追加更正 | 新决定写入并得到回应 | 0 / 1 | 7.571 s |
| 当前会话重新核对 | 实际重新读取，回答包含更正后的三个目标值 | 1 / 2 | 7.004 s |

原始来源前缀保持不变。三个步骤完成，分别检查了读取、更新和再读取；不把它们包装成三个独立记忆题。最初长历史问题的首次正文回调为 2.285 s，可能只是查阅过程说明，最终答案仍需等待 13.383 s。

两次核对的提示明确要求调用 `read_session` 查阅原文，判定检查目标值、实际工具调用和窗口，不作全文的独立语义评分；它验证接续链路能否完成指定操作，不衡量模型自主选择检索策略的质量。

代价也必须保留：长历史问题的三次模型调用累计输入 **32850 tokens**，其中命中缓存 **19200**，输出 **337**；更正后的再读取累计输入 **30677 tokens**，命中缓存 **20992**，输出 **245**。这里的累计输入包含多轮重发，不能等同于唯一历史大小。151 字节只是输入坐标，不代表模型最终只读了这么少内容，更不能据此宣称同比例降低 token 或费用。

本实验支持的具体亮点是：**可以从用户指定的旧会话逐步查到长消息后文，并在用户改口后重新读取最新决定，同时保留原始依据。** 它没有比较其他记忆系统，不证明自动图召回的净增益、所有问题的正确率或跨模型质量。

## Telegram 实际投递

较早的独立隔离实验中，三个自然对话场景均无工具结果，实际发送与送达回执 **3/3** 完成。没有在提示中要求禁用工具的问候与在线确认也通过。

| 场景 | 首次公开正文回调 | 确认送达 | 模型 driver | Bot API 最终发送 |
| --- | ---: | ---: | ---: | ---: |
| 首次问候 | 5.081 s | 6.633 s | 4.650 s | 0.967 s |
| 后续在线确认 | 2.505 s | 3.153 s | 2.327 s | 0.469 s |
| 身份询问 | 2.483 s | 3.054 s | 2.222 s | 0.450 s |

三条回复均未发送流式草稿，所以“首次公开正文回调”是进程内部的正文观察点，**不是 Telegram 用户已经看到内容的时间**。最终送达由实际回执确认。它证明机器人发送链路可用，仍不能证明真实手机上稳定三秒内响应，也不能抹去前述 NFS 冷请求和端点波动。

后续换到与正式部署同类的 NFS 上，另有三条实际投递全部确认，但这轮开发数据存在**评测观察器污染**：在线确认耗时 10.798 s，245 个主线程采样停在评测自身的同步 `terminal → snapshot → scan → head`，同时 Delivery worker 的读取工作约 4.960 s，使该事件循环上的投递启动一同推迟。完整的 4.588、10.798、4.935 s 原始记录保留并标记 `latency_usable_for_product_claims=false`，不当成产品性能，也不因污染而删除这个慢例。这之后，评测读取与原生消息跟随中发现的同步消息头读取均改为可排空 worker；最终机制实验和验收结果仍分别保留。

完成上述读取修补及最终部署后，最新 Telegram 验收在配置模型时连续六次 HTTP 429 后退出，**开始场景 0、实际投递 0，整次验收失败**。这次没有产生可用的最终版本投递延迟，不能沿用较早的 3/3 宣称当前验收通过；也不能把尚未开始场景的配置失败写成三条消息都投递失败。

## 工程验证与完整主链

本轮冻结源码的本机工程回归 **164 passed，76.18 s**；该轮同时进行包文件 I/O，测试总时长不作为 Runtime 性能。前端构建、类型检查和改动 Python 文件的 Ruff F 检查通过，源码包与 wheel 构建成功，原生文件与发行插件校验分别覆盖 969 个文件、75 个插件。较早的 155、157 项回归保留在证据中。这些检查与真实模型完成任务分别报告。

一次完整 `native_runtime` 验收尝试在模型配置探针连续六次 HTTP 429 后退出，**开始场景 0，完成场景 0**，该记录保留。随后另一个完整运行完成了全部 13 项尝试，实际通过 **10/13**，三个失败仍在分母：

| 范围 | 结果 |
| --- | --- |
| 普通回复、文件读写、托管 MCP、Shell、工具错误修复、子任务、模型局部重载、附件投影、定时投递、历史恢复 | 10 项通过 |
| 执行中补充指令与撤回 | 失败，原生 Control 明确为 HTTP 429 |
| 暂停与恢复、不重放已有作用 | 失败，原评测等待工具事实超时；事后读取该原会话唯一 Control，确认为 HTTP 429 |

两项超时各为 90.001 s，是旧评测器已经有失败 Control 后仍等待预期工具的期限，不代表 Runtime 处理了 90 秒。原始失败、耗时和三条实际失败 Control 的状态提取都保留；没有重新运行来覆盖这份首轮。评测器已改成异步读取，并在看到终态失败时立即安全返回状态；新 runner 尚未重跑完整套件，所以本轮仍报告 **10/13**。

该运行记有 **33** 条业务模型回执，其中 **24 success、9 error**；已报告用量合计 **198021 输入 tokens、1467 输出 tokens**，配置探针另外计数。它们是整组业务调用累计值，不是单任务或一次成功回答的成本。此前独立会话引用、本地生成和 Telegram 投递仍按各自源码摘要、条件报告，不把这些结果与主链分母合并。

## 保留的问题与复现

本轮没有把偶然较快的请求当作目标已达成：真实模型生成有数秒波动，NFS 冷请求暴露事件循环阻塞，网页连接数改善尚未转化为可证明的总体速度收益，长资料取证还增加工具轮次和累计输入。保持人格、记忆、权限和恢复语义的前提下，应分别复测这些成本。

开发阶段遇到的失败包括旧隔离工作区缺少 supervised boot identity 而拒绝恢复、测试服务初次配置限流、只读阶段日志日期格式不被本机 journal 接受，以及最早测试临时 SQLite 连接未及时关闭而使 NFS 临时目录清理失败。没有削弱恢复检查来重启旧夹具；最终使用新工作区，连接显式关闭，已生成的 SDK/CLI 测量得到保留。长消息窗口曾因去掉尾部空白使原文偏移不一致，正式实现保留原始字符边界后再运行功能验收。

可维护入口为 `eval.runtime_experience` 的 `service`、`storage`、`mechanism`、`references`、`browser`，以及 `eval.telegram_latency` 的实际适配器与同字节重放。`mechanism` 通过 loopback HTTP 模型复用原生评测，支持在指定文件系统上建立、测量并清理自己的临时工作区，不调用外部聊天 API。命令与参数见[评测复现](../../../eval/README.md#本地使用与延迟)。只读测量、向合成会话发送消息、真实外部投递与确定性模型实验需要明确区分。
