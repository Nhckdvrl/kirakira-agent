# 工具读取边界与执行验收

整理日期：2026-10-21，最终复测延续至 2026-10-22。目标是核对当前工具链，并验证文件、网页、命令、MCP 与恢复在实际装配中的行为。本轮保留现有工具接口、绑定身份与执行架构，修复实测发现的读取开销及告警记忆工具接入缺口。

## 源码核对与修改范围

核对基线为本项目 `fe1387c`，参考版本为[固定提交 bc8cbcbc](https://github.com/kachofugetsu09/akashic-agent/tree/bc8cbcbcb3e88c5f550031b1678f7b527293c3e2)。95 个登记的 Python 文件覆盖 Tools、工具加载、文件、Shell、Host Execution、Web、MCP、托管进程、Workloads、命令、技能和子任务：改动前 90 个逐字节一致，另外 5 个是已有的发行名称或路径适配，以及 zsh 快照的别名展开修复。参考版本在这些工具后端没有新增变更；不能把界面更新当成工具执行落后。

这不是全仓升级到该提交。来源基线仍由 `UPSTREAM.json` 记录，界面 CSS 与所有可选外部账号也不在这次核对结论中。以下读取问题在两边的基线中都存在，修复记录在 `patches/tool-io-bounds.patch`。

| 修改 | 实际行为 |
| --- | --- |
| 文件读取 | 扫描全文统计行数、字节数和编码问题，但只保留呈现所需的前缀及一条溢出行，避免把全部正文和全部带行号文本留在内存 |
| 文件参数说明 | `limit` 的说明与实际 400 行、10KB 呈现上限一致，移除已失效的 80K 字符说法 |
| 网页读取 | 收到响应头后先拒绝已知超限响应；按流累计解码后的正文，缺失或错误长度也不能绕过上限；读取受整体超时控制 |
| HTTP 流失败 | 连接阶段仍可重试；响应已经交给消费者后，正文读取失败直接传递原异常，不能在同一次上下文管理中再次交付响应 |
| 告警历史核对 | Alert 可获得配置中已有的 `recall_memory`、`read_memory_source`，继承参考对话的记忆范围；不因此获得网页、Shell、写入或遗忘工具 |

没有新增工具总线、执行队列或另一套权限。读取、准备、授权、真实执行与持久结果继续属于原工具 owner 和 Ledger。

## 资源测量

入口 `eval.tool_runtime --baseline-ref fe1387c` 从 Git 读取旧组件，在同一 Python 环境、相同文件与相同输入上交替运行。两种实现共用依赖，不启动另一份项目或另建环境。

文件样本为 100,000 行、7,300,000 字节；默认读取最终返回约 10KB。记录三组交替测量、全部原始样本和输出摘要，并在空文件、中文、BOM、超长行、非法编码尾部及不同分页条件上核对旧新输出。

| 最终运行的三组中位数 | 基线 | 修复后 |
| --- | ---: | ---: |
| Python 分配峰值，字节 | 34,848,476 | 154,215 |
| 返回内容，字节 | 10,118 | 10,118 |
| 返回内容摘要 | 相同 | 相同 |

该样本的 Python 分配峰值降低 **99.56%**。20 组边界/分页组合的旧新结果也完全相同。此前两次独立运行的交替样本同样保留，主表采用与最终工具文件摘要一致的运行。

这里的峰值来自 `tracemalloc`，表示 Python 分配，不是进程 RSS。启用追踪会影响耗时，原始 `seconds` 保留作诊断，不据此宣称用户端到端加速。它不包含模型推理、宿主 Bridge 的全部成本或冷存储读取。

HTTP 使用受控 `httpx` 字节流：正文 4 MiB，上限 1 MiB，每块 64 KiB。基线先读完 4 MiB 再拒绝；修复后，明确超限的 Content-Length 在读取正文前拒绝，未声明长度的响应最多在超过上限的下一块停止。比较的是消费者实际读取的正文，不是互联网带宽测试。

| 受控 4 MiB 响应 | 基线消费字节 | 修复后消费字节 |
| --- | ---: | ---: |
| 长度明确且超限 | 4,194,304 | 0 |
| 没有声明长度 | 4,194,304 | 1,114,112 |

两侧均返回相同的超限错误，流均已关闭。错误声明长度、压缩后正文超限和读取超时另由工程回归验证。

文件仍扫描全文，不保证深分页具有恒定耗时；单条超长行也仍可能产生该行大小的临时分配。HTTP 的预算检查发生在解码块交付后，不表示解压器或网络栈的峰值被严格限制到 1 MiB。上述边界没有被包装成整体 Harness 性能提升。

## 功能验收

工具专项直接启动正式插件图并使用真实模型；外部网页由本机受控 HTTP 服务器提供，不向提示词放入页面标记答案。

| 验收 | 核对事实 |
| --- | --- |
| 深分页读取 | 100,000 行文件以指定 offset/limit 取得尾部标记，实际工具参数可查 |
| UTF-8 文件编辑 | 先读、精确替换、再读；BOM 和 CRLF 字节保持 |
| 目录续页 | 两次 `list_dir` 使用真实 `after` 游标，核对两页文件名 |
| 并行文件批次 | 同一模型输出提出两个读取，持久结果按原调用顺序提交 |
| Web 工具加载与恢复 | 实际加载工具，观察 503 失败，再跟随重定向读取有效页面 |
| PTY 与输入 | 实际启动交互进程，并用 `write_stdin` 继续同一执行 |
| 大命令输出 | 有界呈现仍保留完整输出文件，核对该文件的全部字节 |

普通主链另用 `eval.native_runtime` 检查 MCP、托管进程、子任务、工具错误修复、插话纠正、暂停恢复、抢占、附件和调度投递。工程回归单独验证文件内存开销、流式超限、压缩正文、总超时、连接重试与正文中断的关闭语义。

三次独立工具专项均为 **8/8**：每次包含 1 项组件组合检查和上述 7 项真实 Agent 场景。最终普通主链 **13/13**、记忆链 **11/11**，完整工程回归 **116/116**；这些是受控验收，不能合并成公开任务成功率。工具专项最终业务调用账记录 21 次成功调用，配置探测另计。MCP 等主链场景保留独立报告与调用计数。

工具阶段使用原有 `runtime.timing` 单调时钟标记。准备、执行、提交分别记录；执行时间包含真实文件、命令或网络工作，不直接当作纯框架开销。缺失标记保留空值，不用模型总耗时倒推工具耗时。

## 告警中的真实记忆读取

追加记忆回归的首轮为 **10/11**：Alert 只获得 `share_alert`，历史决定不在近期对话里时，只能提醒“缺少记录”。本轮沿既有 Request、工具绑定与阶段程序接入只读记忆；Alert 仍负责直接提醒，不新增兴趣筛选或外部调查。旧的仅含 `share_alert` 的归档仍可校验和恢复。

第二轮虽然生成了正确提醒，但新的读取回执断言失败：之前的确认回复已自动召回并复述答案，告警直接沿用了近期对话。这说明“文案答对”不足以证明告警实际检索，也说明该测试夹具需要改进，不能把这次失败算成工具不可用。

最终运行固定一段不含答案的关注条件和确认记录；历史决定仍由此前的四段真实渠道对话学习。事件和近期上下文都不携带“周五、林悦、匿名样本”，验收检查归档中的原事件身份、对话范围、成功检索回执、正确提醒、确认投递和事件去重。Agent 实际完成 **2 次成功记忆读取**，核对旧计划与更正后投递，整条记忆链 **11/11**。这证明 Alert 已接通记忆工具，不是图检索质量提升的实验。

wheel 与 sdist 均检查本轮工具、HTTP、Wake 和评测文件的实际字节，wheel 中 969 个可打包的登记文件与工作区一致。使用同一个 `.venv` 解释器，在仓库外导入安装包后，组件检查 **1/1**；这项不冒充安装包的完整 Agent 复测。

## 保留的失败与限制

首次主链一轮为 12/13。失败的恢复场景中，模型把要求的字符串多写了一个末尾换行；原始写入只有一次，已完成的结果也只有一条。恢复没有重放该效果。后续明确“不带末尾换行”，保持原来的严格字节断言，再做独立运行；旧失败仍在证据中，不能把该差异归因于读取性能修复。

本轮验证本机受控源和指定模型；没有验证未配置的 Exa 账户、任意浏览器登录、桌面控制或所有容器环境。工具可以执行与模型是否正确选择、填写参数是不同问题；受控验收不构成公开任务成功率。

原始源码摘要、交替样本、失败、模型条件、阶段时刻及安装包结果统一保存在[证据](artifacts/2026-10-21-tool-runtime/evidence.json)。复现命令见[评测入口](../../../eval/README.md#工具读取与执行)。
