# Telegram 响应链路实测

本轮修复的是实际回复链路：无必要的多轮工具调用、等待全文才显示、跨提供方的草稿排空、重复建立发送连接，以及共享文件系统上的记忆锁。对话、工具、记忆与持久投递仍使用同一套 Runtime；模型身份来自本次绑定，没有按模型名称分支。

在线机器人为 `@kirakira_tsukihi_bot`。运行工作区位于持久用户目录，由用户级 systemd 服务启动并随登录会话之外持续运行。凭据和原始运行日志不进入仓库。

## 原问题在哪里

实际 Ledger 中，一次询问当前底座模型的输入到最后一条 Output 提交耗时 **62.73 秒**，产生 **6 次工具调用**：一次文件读取、五次 Shell。这个数字不包含手机到轮询端的时间。问题在于模型缺少本次绑定的可信身份，转而反复检查文件；无法把这段等待全部归因于单次模型请求。

同时，渠道适配器只负责完整消息投递，模型已有的流式正文没有进入 Telegram。记忆档案锁使用只读文件描述符取得排他锁，在当前 NFS 环境报错；正式 Sender 又在每次回复时重建 HTTP 会话。原始事件与受控测量见[证据](artifacts/2026-10-22-telegram-latency/evidence.json)。

## 实现

- Reply 程序在稳定 Prompt 之后提供实际 `BoundModelDescriptor` 的模型名、配置别名和驱动。别名与底座名分开，切换绑定后随之变化；这段事实不增加工具权限。
- Telegram 通过公开的只读 `ReplyStatus` 订阅正文。每个已接纳私聊合并增量，约一秒更新一次；首段有 150 ms 合并窗口，短消息通常直接完成，不额外发送草稿。推理正文不进入草稿，内容按 UTF-16 长度截断。
- 草稿独立等待网络，不阻塞模型回调。429 按返回时间冷却；草稿网络失败只停止预览，正式回复继续投递。群聊保持完整消息投递。
- 正式回复走独立 Sender，因此它和直接适配器投递都进入同一草稿协调机制。先排空较早的草稿，再发送完整消息；按 bot 身份、私聊和精确 Output 身份区分，避免旧草稿覆盖完成消息，也不抑制下一轮。
- 订阅属于显式依赖 Reply 服务的可选子 Fiber。卸载 Reply、重新激活、取消网络请求和关闭 Root 都经过真实排空；没有长期借用服务而阻塞关闭。
- Sender 按插件代持有惰性 HTTP 连接池，每次调用仍单独取得凭据和记录投递回执；排空后关闭连接。记忆锁改用可写但不截断的描述符，保留原排他语义。
- 通用兼容驱动修复工具流的身份拼接：同一 index 的 ID/name 保持不变，只累加 arguments；重复身份不被当成新进展，冲突身份明确失败。处理方式依据[官方函数流协议](https://developers.openai.com/api/docs/guides/function-calling#streaming)，不是特定模型分支。

Telegram 的草稿是临时展示，最终仍需普通消息持久投递；正常消息会清除同一对话中的临时草稿。实现依据 [Bot API](https://core.telegram.org/bots/api#sendmessagedraft) 与[流式展示及限流说明](https://core.telegram.org/api/bots/ai)。草稿成功不计作最终投递成功。

## 怎样测量

`eval.telegram_latency` 在全新隔离工作区运行完整插件图，启用同一语义记忆和工具。Telegram 模式把受控 Update 送入实际适配器和 Core ingress，使用真实草稿、发送接口及原生 Delivery 回执；关闭隔离环境的 getUpdates，在线机器人继续独占轮询。目标来自操作者明确指定的私聊文件。

它没有模拟手机操作，也不把构造 Update 的测试叫作手机到手机端到端测量。表中“完整投递”截至本地确认 Delivery 回执；“草稿确认”截至 Telegram API 返回，不是客户端画面刷新的时间。

每次原生调用结束后，另用 HTTP 传输重放**完全相同的最终模型请求字节**。只保存摘要与大小，不保存请求正文或凭据。原生请求先运行，可能预热供应商缓存；这是归因诊断，不是随机化速度 A/B 实验，也不能用两次生成的差异计算产品加速比。

## 真实 Telegram 结果

所有成功队列均为四个独立场景，全部完整投递。单位为秒：

| 实现队列 | 首次短回复完整投递 | 后续短回复完整投递 | 模型身份完整投递 / 工具数 | 长回复首次草稿确认 / 完整投递 | 正常关闭 |
| --- | ---: | ---: | --- | --- | --- |
| 订阅生命周期修复后 | 9.06 | 3.28 | 4.13 / 0 | 9.09 / 14.45 | 是 |
| 加入连接复用后 | 7.22 | 3.41 | 3.64 / 0 | 18.32 / 20.80 | 是 |

这两个队列每项只有一次采样，历史与生成结果不同，不能据表宣称第二行整体更快。首次请求的冷开销波动保留在表内。

连接复用队列中，正式投递阶段首次约 **957 ms**、随后短消息约 **461 ms**。本地真实 HTTP 回归另外确认两次独立 Sender 调用只创建一条连接，配置阶段没有打开连接，所有者退出后连接关闭。这证明复用路径生效，不等于已经建立网络延迟的统计分布。

长回复仍会慢：最后队列的原生模型调用耗时 **18.62 秒**，同字节后续直连重放耗时 **8.94 秒**，重放首段约 **3.74 秒**。顺序、缓存和生成随机性不同，不能把这个差值归为 Runtime 开销。追加的独立流观察队列核对了原始 SSE 正文与公开 `content_delta`：四个场景的首次正文转发差均低于 **0.1 ms**，没有发现驱动缓冲整段正文的问题；推理字段不算用户可见正文。该队列的长回复约 **3.50 秒**出现正文。

因此，本轮有依据确认消除了身份问题中的无必要工具链，并打通了持续显示、正常关闭和连接复用。供应商首段生成存在明显波动，当前证据不能承诺任意问题固定几秒完成，也不能把慢样本删掉后宣布 Telegram 已无延迟问题。

### 新消息到来后的慢回复复查

实际新消息“你好啊”到最终投递确认耗时 **104.59 秒**：第一轮模型调用约 61 秒，
随后还读取了人物与记忆档案、搜索目录，共产生四个工具结果，最后才完成问候。

这两个观察属于不同消息，不能相加。

对话规则现在明确区分当前请求与历史资料：已注入的称呼、人物表达和稳定偏好直接用于措辞，
普通闲聊不自行转成新闻搜索或文件检查；真正的执行任务仍取得工具证据。
Sender 的纯文字路径跳过附件查询；确需附件时在线程中取得引用，再保持准备全部附件后发送的顺序。

使用实际 Markdown 快照和冻结召回文本作隔离复测，修改前三条问候也均未调用工具，
所以此次并没有确定性重现线上绕行，不能据复测宣称提示词改动带来固定加速。

### 重复绑定读写与实时材料

后续检查发现工具菜单每轮会为已提交的不可变绑定重新开启写事务、核对描述，再重新读取。
现将完整规范化描述与已提交结果一起缓存；同 ID 的描述漂移仍拒绝，写入失败不进入缓存，
重启以数据库为准，关闭后不接受写入。缓存上限 4096 条，淘汰只影响命中，不影响原始记录。
同一 NFS 上的 20 个真实工具绑定、连续五轮组件测量中，重复写事务从 **100 次降至 0 次**，
每轮复用从 **85–151 ms** 降为约 **2.9 ms**。它是组件结果，不是 Telegram 整体加速比。

回复材料的附件引用查询移到受控文件线程；当前时间、模型身份和表达设置改用既有实时材料通道，
每次仍注入，不再额外写入本轮 replay。历史原文、长期记忆和已有出处不删除。
工具协议需要的推理内容保持原样，不能为缩短输入任意移除；例如 [DeepSeek 的工具协议](https://api-docs.deepseek.com/guides/thinking_mode/#tool-calls)要求回传这些字段。

新的受控 Telegram 工作区放在生产同样的 NFS 上，保留实际 Markdown 快照，关闭额外同字节重放：
两条自然输入分别 **5.30 秒、22.85 秒**最终投递，均为零工具、一轮模型调用，正常关闭。
其中模型调用分别约 **2.68 秒、20.35 秒**；第二条约 90.8% 输入命中供应商缓存，仍出现慢调用。
其余接纳、材料、提交和发送合计分别约 **2.62 秒、2.50 秒**。
这是新的隔离历史，不能当作线上完整历史的速度保证。

另用复用连接直接发送四次极短请求，去掉 Runtime、记忆、工具和数据库，完整响应仍分别为
**1.12、7.94、2.32、2.43 秒**。本地记录能证明远端请求存在波动，不能区分供应商排队、
服务内部计算或网络中的各项成本。当前不能承诺稳定秒回。
完整本地回归 **136/136**，真实主链 **13/13**（29 次业务模型调用成功），缓存淘汰、失败重试和重启另有回归。

### 回答前的上下文压缩

再次核对线上消息发现，另一条真实输入从接纳到投递耗时 **104.75 秒**。
其中 **97.58 秒**用于同步压缩旧上下文，正式回答约 **3.49 秒**。
摘要调用产生 6270 个输出 token，最终摘要正文只有 1985 字符；其余大量生成在内部推理中。
这次卡顿的主要原因在 Runtime 的压缩安排，不能用供应商一般波动解释。

压缩请求此前没有实际输出上限；通用兼容连接又在请求“关闭推理”时删除已配置的推理强度，
但没有对应的已确认关闭协议，结果使用了服务端默认值。现在摘要生成实际限制为最多 4096 token，
同时服从剩余容量和模型声明的更小上限；若返回长度截断，则不发布不完整摘要。
没有关闭协议的连接保留原配置的推理强度，有对应协议的连接仍发送真实关闭指令。

上下文达到窗口估算的 60% 后，仍满足硬容量的本轮先回答，摘要 owner 在回复完成后处理已经结算的旧前缀。
后台只带冻结的原生尾部投影和材料，独立取得本次模型绑定，不持有前台工具菜单、预览回调或执行句柄。
发布仍核对父记录与不可变原文前缀；更晚的压缩或显式新对话可以使旧候选失效。
每个会话只安排一份候选，全局队列上限 64，单个受控 worker 执行。
硬容量不足时复用已经运行的摘要；尚在等待本轮结束的候选会撤销，避免等待自身完成。
关机取消并排空后台调用，重启后原文保留，未来请求可重新安排整理。

显式检索和按回执展开原文继续保留原有预算，原始消息与检索记录不改写。

旧轮次也可以缩小请求展示：用原检索记录与固定绑定重建当时材料，只替换一次精确匹配的记忆正文。
模型投影再次校验整个提醒的 SHA-256、字符范围、重叠和所属历史输入。
没有可核验出处的旧材料保持原样；其它提醒、用户正文、工具调用身份和协议需要的推理内容保持原样。
请求展示改变后不续用不兼容的 opaque continuation。缓存只保存不可变历史的核验结果，有界为 512 项。
