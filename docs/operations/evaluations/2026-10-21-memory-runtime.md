# 记忆与持续工作：2026-10-21 实测

本轮实现了程序/工具共用的记忆查询、可重试的查询出处、时间筛选、预算内原文片段和沿来源展开。历史决定已经贯穿到事件调查与实际投递；记忆效果另用公开历史和等预算基线验证。原始记录中的时间使用 UTC，所有工作区均为隔离测试目录。

本报告保留原记忆实验的版本和结果；后续集成与最新回归见[验证入口](../verification.md)。本次材料整理只重新统计已有记录，不重跑模型、不覆盖旧结果。

后续工具复测另外发现并补齐了 Alert 的只读记忆接入。新的事件验收排除近期确认回复提前复述答案的可能，并检查实际检索回执、事件身份与投递；该独立运行的 11/11 和两次先前失败见[工具报告](2026-10-21-tool-runtime.md#告警中的真实记忆读取)。它不修改本报告的公开质量实验，也不把原来的文案断言追认为记忆读取证明。

## 最有依据的亮点

**当前值得突出的是：预算内的历史证据覆盖、能够展开原文核对、历史条件实际参与行动，以及记忆状态可以恢复。** 图式联想提供另一条找回经历的路径；现有实验尚未证明它的回答总分普遍优于向量检索。

| 亮点 | 量化证据 | 适用范围 |
| --- | --- | --- |
| 固定预算下尽量保留关键历史 | `fused + excerpts` 标签消息覆盖 **91.20%**；原通道 **78.24%**，增加 **12.96 个百分点** | 36 道可回答题的消息级标签覆盖均值；9 方案共用 15 个候选、12,000 字符上限，不代表片段包含完整答案 |
| 能处理历史更新和时间条件 | 同一方案知识更新 **6/6**、时间推理 **5/6**；原通道分别 **5/6、3/6** | 两类各 6 题，属于小样本；向量加片段同样达到 6/6、5/6，不作为独有优势 |
| 记忆不足时回到原始证据 | **20,320 字符**记录，实际进行 **1 次**原文读取，取得 `[18320:20320]` 的签字信息；恢复前后已完成的原文结果数量均为 **1** | 两个独立运行场景，证明读取与恢复机制；不是固定检索预算内的回答成绩 |
| 历史会参与之后的行动 | 邮件首轮带历史条件的 **12 次判断有 11 次符合预期**，12 次均呈现原始条件；空闲学习流程 **10/10** 受控验收 | 邮件判断与空闲流程分别计分；没有记忆消融，不能估计记忆净提升或真实用户满意率 |
| 长期状态可恢复 | **300 回合**，第 **87 回合**崩溃，补学 **7 回合**尾部后，与逐回合发布和完整重建的状态摘要一致；另核对 **3 处**发布故障边界 | 合成向量的工程状态实验，不是语义质量或大规模部署测试 |
| 情景图学习不需要聊天模型抽取事实 | 按 42 次题目构建累计学习 **10,248 个闭段**；图学习本身不调用聊天模型抽取事实 | 历史可能重复，本地编码、图计算及 Markdown 档案提炼另有成本；未做其他记忆产品的同配置成本对比 |

91.20% 和 6/6、5/6 属于显式 `fused + excerpts` 实验配置，默认仍是 `lanes / whole`。前者回答为 **28/42**，原通道 **26/42**；候选融合不加片段为 **29/42**，向量加片段为 **30/42**。因此项目介绍应强调可核对、可接续的记忆能力，不写成“图记忆回答最准”。完整条件、对照和失败见后文。

量化摘要可由公开的 [findings.json](artifacts/2026-10-21-memory-runtime/findings.json)复核；它记录原始报告与重算代码摘要，排除 236 行探索记录，没有发起新模型调用。实际行动的后续证据分别见[邮件实验](2026-10-21-mail-followups.md)和[空闲思考实验](2026-10-21-idle-reflection.md)。

## 本轮交付

- Akasha 2 保持唯一学习与发布 owner，原始消息不被摘要或图覆盖。图读取、反馈提交、向量补算和重建分别验证。
- `memory/recall` 与 `AsyncClient.memory_recall` 共用正式召回链路，返回入选消息、时间、作者和片段偏移。不可变 key 的并发重试与重启返回同一出处。
- `read_memory_source` 与 `memory/source` 只展开同一记忆范围中、父查询已经入选的消息；返回有界原文和下一页位置，不重新检索或学习。
- 原通道保持兼容，另有显式 `fused` 候选融合与 `excerpts` 材料模式。公开实验没有证明它们在所有场景更好，默认值继续保留 `lanes` / `whole`。
- 记忆界面区分候选与入选内容，显示真实片段、作者、记录时间和范围。它不把“编入材料”显示成模型已使用或用户已阅读。
- 模型配置与评测入口接受独立的模型、驱动、端点和预算；首页保留原有视觉样式，来源与许可证集中维护。

实现与边界见[记忆架构](../../architecture/memory.md)，外部机制研究和设计取舍见[设计依据](../../architecture/design-direction.md)。

## 公开质量实验

使用 [LongMemEval-S cleaned](https://huggingface.co/datasets/xiaowu0162/longmemeval) 的 42 题均衡子集。参考[官方仓库](https://github.com/xiaowu0162/LongMemEval)的任务划分与评分思路，本轮采用独立实现的 judge，不能作为官方榜单成绩。

| 条件 | 本轮设置 |
| --- | --- |
| 数据文件 SHA256 | `d6f21ea9d60a0d56f34a05b609c79c88a451d2ae03597821ea3d5a9678c3a442` |
| 预先取题 | seed `kirakira-memory-v1`；类别内 SHA256 排序，三个分区 offset 0 / 2 / 4，各类别每区 2 题 |
| 类别 | 用户事实、助手事实、偏好、多会话、知识更新、时间推理、无法回答，共七类各 6 题 |
| 历史 | 每题完整 haystack，保留干扰会话；参考答案与答案标签不进入索引 |
| 编码器 | 固定 `BAAI/bge-small-en-v1.5`，384 维，本地 ONNX；资产摘要存于 manifest |
| reader / judge | 同一配置的 `step-5-preview`，独立请求；context 32768、output 4096、reasoning low |
| 调用端点 | 订阅端点 `https://api.stepfun.com/step_plan/v1`，不使用现金端点 |
| 候选 / 材料 | 每方案最多 15 个闭段候选、12000 个 Unicode 字符，包含标题、时间及来源说明 |
| 实验规模 | 42 题 × 9 方案 = 378 个回答，756 次 reader/judge 业务模型调用 |
| 计分 | 一题一次回答；无效 judge 留在分母按失败计；保留截断和调用错误 |

组件实验离线生成真实 Ledger 消息，调用正式 Learning、MessageConsumer、查询与材料呈现；reader/judge 使用正式 Models。它不包含实时渠道接入；实时链路在后文独立验收。数据只提供会话日期，消息微秒偏移仅表达顺序，不声称拥有原始消息的精确时间。

按题累计导入 20,645 条消息、2,003 个会话次，学习 10,248 个闭段；每题保留 41–53 个会话、444–560 条消息。背景历史可能重复，这些累计量不是独立事实的数量。

### 总体结果

“标签消息覆盖”是在 36 道可回答题中，对呈现的消息 ID 覆盖 `has_answer` 标签的比例逐题求平均。它不证明取出的片段包含完整答案，更不等同于回答正确率。

| 方案 | 回答正确 | 正确率 | 标签消息覆盖 | reader 截断 |
| --- | ---: | ---: | ---: | ---: |
| 无记忆 | 6/42 | 14.29% | 0.00% | 0 |
| 近期历史 | 7/42 | 16.67% | 2.78% | 0 |
| 向量检索 | 29/42 | 69.05% | 85.19% | 5 |
| 向量 + BM25 排名融合 | 27/42 | 64.29% | 78.01% | 0 |
| Akasha 原通道 | 26/42 | 61.90% | 78.24% | 1 |
| Akasha 候选融合 | 29/42 | 69.05% | 81.02% | 1 |
| Akasha 融合 + 片段 | 28/42 | 66.67% | 91.20% | 1 |
| 向量 + 片段 | 30/42 | 71.43% | 89.81% | 1 |
| 向量/BM25 融合 + 片段 | 27/42 | 64.29% | 84.26% | 0 |

最后一行有一次无效 judge，已经按失败计入 42 题。无记忆答对的 6 题均为无法回答题；这不是它完成了有历史依赖的任务。

相同题目的配对结果更能说明差异：原通道相对向量为 1 胜 4 负；候选融合相对向量为 2 胜 2 负；融合加片段相对向量加片段为 0 胜 2 负；融合加片段相对原通道为 5 胜 3 负，其余为同对或同错。样本不足以作显著性或普遍优越性结论。

| 题型，每类 6 题 | 原通道 | 候选融合 | 融合 + 片段 | 向量 | 向量 + 片段 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 用户事实 | 6 | 6 | 5 | 6 | 6 |
| 助手事实 | 4 | 4 | 2 | 4 | 2 |
| 偏好 | 0 | 3 | 2 | 2 | 2 |
| 多会话 | 3 | 3 | 3 | 2 | 4 |

片段模式增加消息覆盖，在更新与时间题上有所改善，也损失了助手事实等题的必要上下文。候选融合保留更多向量尾部，回答总分追平本轮向量基线；它没有证明图补全贡献了稳定的额外收益。应继续把候选、呈现与回答分别定位，不用“图更复杂”推导“图更强”。

### 补全通道究竟补回了什么

逐题重算发现，36 道可回答题中，**6 道题的补全通道候选包含带答案标签的消息**。对这些特定消息，原通道最终呈现于 2/6 题，候选融合及融合加片段均为 6/6；完整向量方案为 4/6，向量加片段为 5/6。

原始字段 `completion_only_gold_messages` 指“标记为补全通道的标签消息”，不表示这些消息在完整向量检索中一定找不到。不能把 6/6 写成图独有命中或回答全对。两个有信息增量的例子是：

| 题目 ID | 相对向量整段方案多呈现的证据 | 最终回答情况 |
| --- | --- | --- |
| `75832dbd`，偏好 | 融合方案呈现补全通道的标签消息，向量整段方案未呈现 | 融合答对、向量整段答错；但向量加片段未呈现该标签也答对，不能据此单独归因于图 |
| `gpt4_a56e767c`，多会话 | 融合方案呈现另一条标签消息，向量整段方案未呈现 | 两者均答错；向量加片段也找回这条消息，仍未正确综合全部经历 |

这说明联想路径和呈现策略确实影响进入模型的历史，但“新增关键消息”与“回答变好”需要分别验证。全部六题及各方案的呈现身份和判断结果保存在 `findings.json`，包括未带来回答收益的题。

三个分区分别为 14 题。前两组曾用于探索和开发复查，第三组在检索与呈现方案冻结后运行；42 题总分包含开发题，不能称为 42 道全新保留题的成绩。原通道得分 10 / 10 / 6；候选融合 12 / 10 / 7；融合加片段 12 / 8 / 8；向量 12 / 10 / 7；向量加片段 12 / 9 / 9。探索题目上看起来有帮助的策略，在另一分区并不总是更好，因此没有根据首组结果自动切换默认模式。

### 证据完整性与实验限制

最终代码重新检查了全部 378 行的候选顺序、入选消息与材料长度，并重建原文范围和材料摘要；检查期间未重跑 reader/judge。原始主实验当时没有保存材料字节摘要，不能倒推证明原始材料与重建材料的字节身份；新运行直接记录摘要。

主实验共记录 1,331,267 个输入 token、416,853 个输出 token，均来自业务调用账本；配置探测和本地向量编码另计，不据此推算现金成本。756 次业务模型调用均完成，应用层仍有上述一次 judge 格式无效。

还保留了五组 JSON reader 探索记录，共 236 行，其中包含供应商并发错误、格式错误和未完成方案。它们没有混入 378 行主实验；共享并发槽随后限制跨进程请求，避免多个实验各自限流却共同超限。数据中重复会话 ID 以 occurrence 身份保留，评分仍映射原始会话；没有丢弃那段背景历史。

本轮是均衡子集、同模型 reader/judge、单次采样，题目分区可能共用背景历史；没有完成 Mem0、Hindsight 或其他产品的同配置运行对比。来源 ID 合法也不证明每句话的引用蕴含关系。完整 manifest、逐题回答、错误、来源范围和分项见 [memory-quality.json](artifacts/2026-10-21-memory-runtime/memory-quality.json)。

重新核对还区分了两个容易夸大的分母：36 道可回答题中，候选融合答对 **24/36**、融合加片段 **23/36**、原通道 **21/36**，无记忆为 **0/36**；无记忆总体的 6 个正确答案均来自无法回答题。融合加片段有 **38 个带引用的回答，38 个引用 ID 合法**，另外 4 个无引用回答不计入该比例；合法 ID 不证明答案正确或引用支持全部表述。

378 条主实验记录全部满足候选和字符上限；这是预算核验，不是 378 次任务成功。重算命令见[已发布记忆报告重算](../../../eval/README.md#已发布记忆报告重算)。

| 当时的完整单元与集成回归 | 97/97 | 原记忆交付版本的回归集，不等同于用户任务成功率 |

| Web 集成 | 通过 | 认证工作台/聊天、import map 顺序、项目作用域与真实文件写入，10 个界面插件 |

| 安装包中的完整主链 | 13/13 | wheel 以 `--no-deps --target` 安装到临时目录，从其中启动，仍使用同一 Python 环境和依赖 |

一条已跑通的项目流程：历史先有旧发布计划，随后更正日期、负责人，并确认演示只能用匿名样本；另一个相似项目作为干扰。新事件不含这些答案，Agent 找回青禾项目的最新决定，提醒 2026-10-23 发布、负责人林悦、使用匿名样本；本地投递获得成功回执，同一事件重投没有增加通知。

原文展开另有两个真实场景。短记录验证读取凭据与分页结果不改变图；长记录为 20,320 字符，召回片段没有完整呈现结尾，Agent 调用原文工具读取 `[18320:20320]`，回答签字人为顾予安。它验证按需读取能力，额外原文读取的预算没有混入上面的固定预算成绩。

显式遗忘通过真实成功工具结果进入学习提交，后续查询不再带回目标经历；原始消息仍可读。显式记住恢复该节点。重启后保存的查询与原文读出保持一致，不重复学习。

实际测试发现过两类实现问题：公共 DTO 与 generation 私有类型身份不一致；记忆原文范围字段被误传入通用 Content 引用合同，导致回复失败。分别通过公共序列化边界与字段归属修复。后者的既有失败会话在升级后成功恢复，已经完成的原文读取仍只有一次，没有重放已完成结果。初始失败、恢复和最终记录一并保存在 [runtime.json](artifacts/2026-10-21-memory-runtime/runtime.json)。

安装包验收还发现评测脚本丢失执行位。修复发生在可写的评测资源复制阶段：恢复入口权限，再交由插件管理器冻结制品；保留宿主对 Python runtime 与 artifact 路径的约束，没有放宽执行权限或另建 Python 环境。wheel 与 sdist 均包含新记忆模块、前端资源和许可证，逐项核对打包 Python 源码与当前文件一致。

## 学习与恢复的一致性

- 272 回合合成状态场景：增量发布与完整构建的所有逻辑表一致，查询不改变图；覆盖 file-sync、replace、directory-sync 三个发布故障边界。
- 300 回合、每 16 回合发布，在第 87 回合崩溃：7 回合未发布尾部重新学习后，状态摘要与逐回合发布、完整重建一致，均为 `1d71308c30a632523ba88b912418fb6ecdf439269ad8faaec4169cfe8ffc1b86`。
- 派生向量恢复：3 个闭段、6 条向量补算，非空召回一致，热查询不重新编码，原始消息与图字节不变，非法消费进度明确失败。

这些场景证明状态约束，不使用真实语义向量，不能代替质量实验。原始结果见 [state.json](artifacts/2026-10-21-memory-runtime/state.json)。

## 可以据此展示什么

目前有依据展示的是一条可追溯的长期工作流程：历史更正进入记忆，新事件引发调查，片段不足可展开原文，结果完成投递，重试与恢复沿用已发生的事实。它的价值由完整行为支持，不依赖插件数量或某个聊天模型的名字。

记忆质量仍有明确短板：原通道没有胜过简单向量，片段覆盖提升没有完全转成回答收益，偏好与多会话推理仍需改善。下一步先测按需扩展的总材料/调用预算、片段上下文完整性及独立更大数据，再决定是否改变默认策略。空闲思考的后续交付见[跨会话主动行动](2026-10-21-idle-reflection.md)；多日自主探索、真实用户通知有效率和外部账号部署仍见[后续路线](../../status/roadmap.md)。

源码覆盖、构建和回归清单见 [distribution.json](artifacts/2026-10-21-memory-runtime/distribution.json)。运行命令见[评测说明](../../../eval/README.md)。既有数据导入与恢复见[启动和迁移](../../handbook/start.md#既有-kirakira-数据)。
