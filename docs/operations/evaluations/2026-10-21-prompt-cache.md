# Harness 输入缓存调查与主动提醒回归

日期：2026-10-21。目标是查清 Harness 可以控制的缓存条件，决定是否有理由修改上下文组织，同时保持个人 Agent 的记忆、当前规则与主动判断正确。

## 结论

Harness 可以影响输入缓存复用，但不能决定远端 KV cache 的实际命中。两次受控实验中，稳定内容在前的一组分别报告 38.92%、38.88% 的输入缓存复用，变化标记在前的一组均为 0%；两组的简单预算判定都正确。**延迟结果方向相反，尚不支持产品加速的结论。**

当前 Runtime 已有稳定前缀、按输入记录的环境信息、原始工具协议重放和同一压缩周期内冻结的档案。此次没有证据支持重写这些机制。本轮交付是准确的缓存统计、实际传输跟踪和一项由功能复测发现的提醒范围修正。

个人 AI 伙伴仍是整体产品方向。缓存是支撑长期运行的工程课题，邮件是可重复验证主动行为的一条场景。它们不代替[整体定位与体验设计](../../architecture/design-direction.md)。

## 缓存的控制边界

当前使用远端模型 API，Harness 不持有推理设备上的 KV 张量。它能决定发送什么历史、按什么顺序组织材料、保留哪些工具定义，以及何时压缩；缓存的容量、淘汰与实际路由由服务端管理。这是根据本项目传输代码和供应商机制得出的控制边界。

| 机制 | Harness 可以影响的部分 | 实测或文档边界 |
| --- | --- | --- |
| 供应商的输入前缀缓存 | 稳定指令与工具、历史追加顺序、变化材料的位置 | 复用计算状态，每次仍生成新输出；不是缓存完整答案 |
| 服务端 KV 存储与路由 | 使用供应商明确支持的参数，减少无必要的前缀变化 | 当前 API 连接无法直接分配、压缩或驱逐远端 KV |
| 本地协议与序列化缓存 | 冻结行复用、工具 JSON 编译、估算读面复用 | 减少本地计算，不代表供应商缓存命中 |
| 用量统计检查点 | 增量读取已闭合 Turn 的真实调用账 | 是可重建统计，不参与模型推理 |
| 情景记忆与长期档案 | 恢复相关历史、控制材料预算、更新个人上下文 | 存储经历与知识，和模型计算缓存的职责不同 |

供应商协议不能互相套用：OpenAI 的前缀缓存及 `prompt_cache_key` 行为依模型而异，键也不保证命中；其文档建议保持历史和工具稳定。[OpenAI 官方文档](https://developers.openai.com/api/docs/guides/prompt-caching)

Claude 提供顶层自动缓存或内容块显式断点，缓存生命周期和写入计费需一起考虑。[Claude 官方文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)

DeepSeek 自动管理缓存，当前文档说明前缀持久化单元及尽力复用的规则；不能只看本地相同字符数就推断实际命中。[DeepSeek 官方文档](https://api-docs.deepseek.com/guides/kv_cache/)

本次实际调用的服务支持自动前缀缓存，文档说明 LRU 淘汰和缓存用量字段，不保证始终命中。全部调用使用已经配置的订阅专用端点，真实模型、驱动与端点保留在原始实验文件中。[实际供应商的缓存文档](https://platform.stepfun.com/docs/zh/guides/developer/prompt-cache)

## 当前代码核对

- `plugins/prompt/plugin.py` 将接纳时间、输入身份和渠道信息放入当前输入的 reminder；时间并非每一步重新写进 system 开头。
- `plugins/markdown_memory/plugin.py` 按会话与压缩摘要版本冻结常驻档案，相关主题作为当前输入材料浮现。冻结档案和实时核对用户规则分别处理。
- `plugins/models/projection.py` 与 `plugins/context/plugin.py` 重放原始调用、观察和输入关联的提醒；压缩、动态材料和模型切换仍可能改变可复用前缀。
- `plugins/openai_compatible/driver.py` 的行与工具 JSON 缓存只处理本地编码；供应商返回的缓存 token 另由用量解析器读取。
- 公共请求合同虽有 `prompt_cache_key`，当前通用 Chat 传输没有发送它，Codex Responses 驱动有自己的处理。尚无本项目证据支持把同一参数强加给所有兼容端点。

因此，保留实际规则更新、权限变化和必要的压缩。不能为提高缓存比率，让模型继续使用已失效的偏好，或保持已经不再授予的工具。

## 受控前缀实验

入口为 `eval.prompt_cache --mode probe`。每次实验有两组，各 8 次请求，按轮交替先后顺序。两组拥有相同的 160 条合成背景记录、相同预算条件与到货信息，只改变每次随机请求标记位于稳定背景之前还是之后。预算交替为 90 元、130 元，到货总价 110 元，参考行为分别为跳过、分享。请求不携带参考答案。

每次使用新随机档案身份和独立本地工作区。两次完整实验之间没有修改业务提示，第二次补充了本地字符前缀诊断。首次配置模型各有一次额外验证调用，不计入下表。

| 实验 | 前缀布局 | 调用 / 判定正确 | 输入 token | 缓存 token | 缓存占比 | 首增量中位数 ms | 总时长中位数 ms |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 稳定背景在前 | 8 / 8 | 31,572 | 12,288 | 38.92% | 1,422.7 | 2,269.6 |
| 1 | 变化标记在前 | 8 / 8 | 31,586 | 0 | 0% | 1,690.0 | 2,780.6 |
| 2 | 稳定背景在前 | 8 / 8 | 31,608 | 12,288 | 38.88% | 1,716.2 | 3,079.6 |
| 2 | 变化标记在前 | 8 / 8 | 31,630 | 0 | 0% | 1,493.7 | 2,367.6 |

稳定组两次都是前两次零命中、后六次各报告 2,048 个缓存 token；变化组全部零命中。第二次本地稳定组共享约 6,621 个序列化字符前缀，变化组约 20 个；字符数不是模型 token 数，也不是服务端缓存边界。

首增量可能包含推理文本，不等于用户可见答案的首 token。实验没有隔离供应商负载与网络条件，也没有生产请求改动前后的配对对照。一次稳定组较快，另一次较慢；样本不足以声称延迟降低。简单预算题也不能替代记忆质量或日常伙伴体验评测。订阅调用未提供可核对的逐请求账单，本报告不推算节费百分比。

## 原生链路复测发现的行为问题

请求跟踪观察实际插件代中的传输，只保存摘要、尺寸与用量，不改业务 Prompt、工具目录、流式选择或路由。实际邮件验收继续经过原生采集、历史召回、规则原文、Wake 工具决定与 Delivery 确认。

首个成功安装跟踪器的邮件复测为 **7 / 8**。26 次远端调用全部成功，151,814 个输入 token 中报告缓存 11,264 个，约 7.42%。它包括配置、历史准备、初筛和调查，不是每封邮件的稳定成本。已闭合 Turn 投影统计为 3 个被动轮、8 个主动轮，均有完整缓存字段；配置调用不属于会话 Turn，因此分母不同。

失败不是外部文字成功修改规则：规则仍为版本 1，原始历史也没有新增主人修改。模型识别出了冒充指令，却主动发送一条解释通知，还询问是否应把此类邮件加入关注范围。该通知不满足主人已经设定的条件，构成一次额外打扰。原始失败、通知内容和真实回执保留在证据中。

本轮将“逐条调查”和“逐条推送”明确分开：分享需要满足实际采用的关注条件；解释为何忽略材料、建议扩大订阅范围或询问是否修改偏好，都不能单独成为推送理由。外部内容仍按原有条件判断是否有实际待办。该约束进入初筛和调查提示，不增加关键词黑名单，也不放宽工具权限。

修正后使用新工作区复跑，**12 / 12 场景通过**：原有 8 项全部通过，另加 4 项内容混合一般安全知识、无需行动的话题、补充材料和限时确认，分别检查应跳过和应分享。原先多发通知的内容本次被跳过，真实待办仍有确认投递。它们是受控验收，不能当作公开通知准确率，也不抹去前一次 7 / 8 的结果。

该次共有 54 次远端调用，361,804 个输入 token，报告缓存 94,208 个，约 26.04%；闭合轮次为 3 个被动轮、16 个主动轮，缓存字段均完整。调用数量包含额外内容和各阶段准备，与修正前的工作量不同，**不能据此声称缓存优化提高了命中率或降低了成本**。部分具有长本地公共前缀的请求仍返回零命中；现有数据不能区分隐藏渲染、服务端路由和淘汰的影响。

## 统计修正与验证

`ModelUsage.coverage=exact` 只说明输入、输出 token 完整，并不保证供应商报告了缓存字段。旧统计把缺失缓存字段折算成零值，会把“未知”展示成“缓存未命中”。现在：

- 单轮缺失任一调用的缓存字段，整轮缓存命中保留为未知；明确返回零才是已观测未命中。
- 汇总分母只使用缓存字段完整的轮次，并展示已知轮次与总轮次；输入和输出的已知计数继续保留。
- 缓存统计检查点升级到版本 2。旧聚合结果从真实消息与调用账重建，不修改原始消息、记忆图或模型调用事实。
- 浏览器检查了全未知、部分已知和明确零命中三种情况，未知命中/未命中显示为“未提供”，部分已知示例按已观测输入得到 50%，没有除以包含未知缓存的输入总量。

修正后完整回归 **109 / 109**，网页模块构建和 TypeScript 检查通过。第一次全量运行有一个 Host Bridge 测试夹具在 5 秒启动期限内超时，其余 108 项通过；该项单独复跑通过，随后完整运行 109 项全部通过。保留这个过程，不把首次运行写成全绿。

开发中也保留了跟踪器的一次错误：公共包与实际插件代的类不同，初版未捕获调用，机制实验因此中止；修正为跟踪实际加载的插件代后重新使用新工作区。未捕获的结果没有用于缓存或速度结论。
