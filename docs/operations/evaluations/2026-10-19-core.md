# 主链功能、并发与性能验证

日期：2026-10-19。Python 3.14.6，项目唯一 `.venv`。
参考 Akashic `21b38f0e102d9e1bdc5576725635dce29f135c0c` 的 reply_program、tools、
来源检查和 ReAct 性能实验方法。本轮没有新增记忆算法或迁移用户 workspace。

## 当前实现

- 独立读取由工具提供者显式声明，默认最多四个并发；写入、工具加载和终结调用形成屏障。
- 结果按模型顺序进入下一请求，子调用持有 execution 与快照；普通子 task 不隐式取得权限。
- 同步工具取消等待实际线程结束；流式/非流式模型重复取消不能打断 provider 清理。
- Runtime 关闭统一排空直接、渠道、控制、Scheduler 及其等待者，再关闭存储。
- 流结束通过完成通知唤醒，未结算检查只解码必要日志字段。
- 已中断轮次在下一请求有明确控制提示；未知窗口不再执行无效的压缩复制。

接口、持久化差异与限制见 [ADR0014](../../decisions/0014-main-chain-batches-and-physical-drain.md)。

## 功能与真实模型

最终全量 **721 passed、4 subtests**，58.51 秒；22 条既有 Telegram 弃用警告。
新增边界覆盖并发上限、空槽复用、写入屏障、授权/hook/循环保护、终结互斥、代际热更新、
日志失败、重复取消、直接入口关闭、中断状态重启投影与大量流片段的完整顺序。

真实生成全部使用 `https://api.stepfun.com/step_plan/v1`、`step-5-preview`、
`reasoning_effort=medium`；未使用现金接口。密钥仅从仓库外文件读入内存。
生产 build_runtime/Pipeline/SQLite 承担实际执行，只有模型供应方是真实外部服务；文件、
通知回调和故障 fixture 全部在隔离目录，不把本地投递回调说成真实渠道已读。

| 最终场景 | 通过 | 验收 |
| --- | ---: | --- |
| 原生并发读取 | 4/4 | 模型一次发出八个读取，峰值四个；读取完成后保存总和且只保存一次 |
| 已写入后恢复 | 4/4 | 工具结果落盘后注入生成失败；仅重试当前请求，写入次数始终为一 |
| 延迟工具加载 | 4/4 | search → 新 schema 可见 → 实际调用 |
| 工具报错修正 | 4/4 | 读取 v1 返回明确错误，模型改用 v2 |
| 文件与重启 | 4/4 | 生产文件工具写入、读取，关闭重建后再次核实 |
| 流式中断与新请求 | 4/4 | 真实流启动后中断，排空后同会话处理新输入 |
| 上下文压缩与重启 | 4/4 | 40 组原始交互触发摘要；80 条原文不变，摘要与 generation 重启后保持 |
| Scheduler / 渠道矩阵 | 52/52 | 13 类各四次：排队、原会话、触发、取消、回执、重启、重复触发与未知结果 |
| 中断控制专项 | 8/8 | 补入控制提示后，沿用原严格断言验证真实取消及新请求 |

主链最终批次记录 88 次模型尝试：80 个完整响应、4 次预期注入、4 次取消；返回 usage
216,607 tokens。场景延迟 p50/p95 为 9.05/26.64 秒，尝试耗时为 2.84/10.60 秒。
四次取消排空为 3.15、3.36、3.22、3.24ms，是本地取消请求到 owner 释放的时间。
Scheduler 最终批次为 133 个完整响应、209,596 返回 tokens。两批运行时存在其他实验负载，
这些数字不用于推断 provider 性能变化；取消后未返回的用量不计入 usage。

## 本地开销

同一解释器、同机、同输入，基线为 `f808b40` 的独立基线工作树。每项预热两次、记录 30 次，
保留全部样本与源码摘要。模型由协议 fixture 替代；以下单位为 ms，绝非真实网络请求延迟。

| 工作负载 | 基线 p50 / p95 | 当前 p50 / p95 |
| --- | ---: | ---: |
| 无片段流完成 | 100.42 / 100.47 | 1.11 / 1.13 |
| 四片段短流 | 100.76 / 100.81 | 1.24 / 1.38 |
| 2,000 片段流 | 46.65 / 46.97 | 44.90 / 45.64 |
| 十步日志检查 | 0.411 / 0.418 | 0.041 / 0.044 |
| 五十步日志检查 | 2.072 / 2.078 | 0.200 / 0.205 |
| 一百步日志检查 | 4.855 / 5.169 | 0.397 / 0.404 |
| 八个独立 25ms 读取，含耐久 journal | 212.99 / 214.28 | 57.43 / 58.92 |

短流收益来自移除 100ms 轮询；大量片段主要受事件分发成本限制，收益很小。并发工具工作负载的
请求结果、顺序和结算检查相等，活跃调用峰值从一变为四；其收益依赖工具确实独立且模型发出批次。
日志工作负载包含每步 32KiB 请求正文；小请求不应套用同一倍数。

## 千轮压力与请求等价

压力 fixture 使用真实生产 Pipeline/Session/journal、64 个会话、1,000 轮、5,000 次工具调用，
每十三轮注入一次当前生成错误。最终实查均有 5,000 条 intent 和 result，77 次注入恢复，
每个 ticket 只发生一次 counter 效果，1,000 个 run 全部 completed，无未结算操作。
重启后 2,000 条原始消息保持，单会话同时运行的 turn 峰值为一，单轮并发读取峰值为四。

Profile 显示历史 deepcopy、JSON 编码、SQLite 耐久事务仍是热点。未配置窗口时压缩器不会
产生摘要，却仍复制并校验历史，因此取消这条无效工作。固定时间、工具和请求内容后，对照仅
`agent/core/reasoner.py` 不同，**1,000 个 ticket 的 2,077 次模型尝试摘要逐项完全相等**。

| 单次匹配压力实验 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 总耗时 | 12.67s | 10.72s |
| 吞吐 | 78.90 轮/s | 93.32 轮/s |
| admitted→结束 p50 / p95 | 768 / 1,162ms | 651 / 919ms |
| 事件循环 lag p50 / p95 / p99 | 76 / 229 / 385ms | 68 / 205 / 235ms |

这是单次匹配观察，不是 provider 吞吐，也不是“93 个真实智能任务每秒”。所有轮次同时入队，
排队耗时本来就高；优化后事件循环 lag 仍明显，不能称为高并发延迟问题已解决。Profile 带来的
开销只用于定位热点，其运行耗时不与正常压力测试混作提速证据。

## 复现

```bash
uv run --frozen pytest -q
uv run --frozen python -m eval.benchmarks.core --repeats 30 --output /tmp/core-micro.json
uv run --frozen python -m eval.benchmarks.runtime \
  --workspace /tmp/core-pressure-new --output /tmp/core-pressure-new.json \
  --turns 1000 --sessions 64
uv run --frozen python -m eval.scenarios.core \
  --key-file /path/outside/repo/step-plan.key \
  --workspace /tmp/core-online-new --output /tmp/core-online-new.json \
  --repeats 4 --concurrency 3
uv run --frozen python -m eval.scenarios.scheduler \
  --key-file /path/outside/repo/step-plan.key \
  --workspace /tmp/scheduler-online-new --output /tmp/scheduler-online-new.json \
  --repeats 4 --concurrency 3
```

仍调用项目同一 `.venv` 的 Python，不另建解释器或依赖环境。
