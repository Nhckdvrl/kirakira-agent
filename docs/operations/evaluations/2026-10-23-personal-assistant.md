# 从聊天交办到持续行动

日期：2026-10-23。目标是验证个人 AI 伙伴怎样完成普通助理工作，并让过去的相处背景参与之后的行动。这里记录受控功能实验，不把工具数量、回归数量或两个合成场景当成公开任务成功率。

## 这轮交付

普通聊天现在可以创建跟进、查询处理依据与送达情况、修改规则、暂停和恢复。Web 与 Telegram 继续使用同一个工具和执行入口。一次性读网页、整理文件和定时提醒沿用各自的原有工具；持续关注由用户明确交办。

操作直接绑定当前会话与本轮用户原话。规则修改保留原始输入和版本，同一次调用的回执与修改在同一事务提交；旧暂停调用重放不会覆盖后来的恢复。后台调查不能自行增加关注。启动前读取实际主动联系状态与通知位置，不自动启用或更换收件人。

查询结果同时呈现外部变化、调查实际读取的历史、决定和确认送达记录。历史节选优先呈现用户原话，标注作者、时间和截断；不会因为助手的过程说明排在前面，就把关键更正挤出紧凑视图。保存规则、完成调查与确认送达分别说明。

这使已有特点落到一条可操作的路径：**聊过的条件能够参与后续帮助，用户改口能够改变之后的行为，处理结果还能回头核对。** 个性组合、空闲接续和长原文导航仍是整个个人伙伴体验的一部分，相关实验见[验证入口](../verification.md)。

## 实验方法

运行正式 Runtime、工具目录、模型 driver、Akasha、跟进采集、Wake 和 Delivery。用户请求不含工具名称，由模型自行选工具；状态、原文引用、实际文件和投递回执用于判定。网页和收件会话是隔离的本地夹具，没有向真实 Telegram 用户发送测试通知。

两个预先固定的生活场景使用不同名称和金额：

| 条件 | 展览 | 陶艺体验课 |
| --- | --- | --- |
| 最初预算 | 100 元 | 80 元 |
| 另一个会话中的预算更正 | 150 元 | 200 元 |
| 第一次新公告 | 周末开放，120 元 | 周末开放，160 元 |
| 后来明确修改的通知规则 | 周末且不超过 90 元 | 周末且不超过 120 元 |
| 第二次新公告 | 周末开放，110 元 | 周末开放，150 元 |

首次新公告本身没有用户预算，需要历史支持分享；第二次价格仍符合先前预算，却不符合新规则，应当跳过。首次采集只建基线，重复页面不再入队，暂停后检查不访问网页，重启后恢复仍沿用已修改的规则。

普通能力同时覆盖严格格式的计算回答、网页到 CSV 的实际写入与读回，以及一分钟提醒的登记和真实投递。提醒检查实际触发时刻相对用户输入的差值，工具回执按用户选择的时区呈现。

单次普通对话截止为 180 秒；最终事件调查截止为 600 秒。逐项耗时随结果保留，截止时间用于功能验收，不是响应速度指标。模型配置、源码摘要、每次运行及原始失败见[完整证据](artifacts/2026-10-23-personal-assistant/evidence.json)。最终两组聊天实验和普通主链的实现文件摘要均与 `85035b5` 一致。

## 实际结果

| 验收 | 实际结果 | 判定依据 |
| --- | --- | --- |
| 展览与陶艺完整交互 | 各 **12/12**，合计 **24/24** | 自然语言选工具，检查真实文件、规则、事件和回执 |
| 更正后的历史参与行动 | **2/2** 呈现预算更正原话，**2/2** 分享 | 新价格高于旧预算、低于更正后的预算；各确认送达一次 |
| 用户收紧条件之后保持安静 | **2/2** 跳过，确认投递 **0** | 新价格仍低于历史预算，却超过本轮明确规则 |
| 查询为什么收到通知 | **2/2** 返回原始预算更正、外部变化及确认回执 | 同时检查实际工具观察内容，不能只靠回答说“查到了” |
| 重复采集与暂停 | 相同页面重复入队 **0**；暂停后 HTTP 请求 **0** | 读取实际采集结果和本地服务器请求记录 |
| 重启后恢复 | **2/2** 保留修改后的规则与历史 | 用户从聊天恢复，沿用既有规则版本 |
| 一分钟提醒 | 两次均从真实输入后 **60.0 秒**起算，并有实际投递 | 登记时刻、所选上海时区和持久送达记录分别检查 |
| 通用执行主链 | **13/13** | 文件、Shell、MCP、子任务、错误修复、插话、撤销、附件、定时任务与恢复 |
| 本轮较早的独立记忆回归 | **13/13** | 并发查询、重复请求、出处展开、历史条件参与行动、忘记与恢复；保留当时源码摘要 |

一次提醒登记正确与实际按时送达是不同问题。这里的 60.0 秒是保存的计划时刻相对原输入的差值，送达由回执另行确认；没有把两者混成零延迟承诺。

最终展览普通对话耗时为 7.6—50.0 秒（计算题 16.7 秒），陶艺为 3.6—134.9 秒；四次事件调查为 26.9—52.3 秒。两工作区共记录 77 次远程聊天调用，包含档案学习和后台调查，不能视为单轮任务成本。慢请求仍然明显，这轮结果不证明响应速度达标。

工程检查：改动相关合同 **21/21** 通过；[云端完整检查](https://github.com/Nhckdvrl/kirakira-agent/actions/runs/39819720256)为 **131 passed、1 skipped**，缺少 zsh 的用例已在本机单独通过。原生源码、文档、前端构建、类型检查、源码包和 wheel 构建均通过。最终本机 wheel 中六个改动模块与当前源码逐字节匹配。

## 开发失败也保留

| 阶段 | 已运行检查 | 问题 |
| --- | --- | --- |
| 最初开发 | 7/10 | 事件调查超过 240 秒、规则修改所属作用域授权失败，以及依赖该规则的恢复失败 |
| 工具接通后的展览 | 8/10 | 状态查询与修改回复超过 180 秒；完整 Turn 加档案超过声明的模型窗口，排空时学习器报错，未执行重启检查 |
| 工具接通后的课程 | 11/12 | 查询状态绕过专用工具，读取配置文件，专用入口验收失败 |
| 证据视图修正后的展览 | 3/5，提前返回 | 提醒相对输入延迟到 92.871 秒；沿用旧未就绪状态，拒绝已经配置好的跟进 |
| 证据视图修正后的课程 | 12/12 | 保留独立结果；不能替换同阶段展览的失败 |
| 最终固定版本 | 展览 12/12、课程 12/12 | 同一场景完整重跑，没有重写早期结果 |

另有两次 DNS 故障发生在模型配置阶段，未开始场景。第一次和第二次本机全量回归分别出现 3 个、4 个共享 NFS 上的子进程启动超时；保留日志摘要，云端检查使用相同源码和测试期限。没有放宽启动期限来取得通过。

## 已发现并修复的问题

- 工具子作用域直接调用跟进服务时，规则写入拿不到所属服务的 Ledger 授权。改为通过服务所属作用域的入口执行，保持原有权限检查。
- 查询主动联系状态的工具入口描述不完整，模型绕去读取配置。补充工具组和读取工具的用途说明，保留修复前的失败。
- 配置变化后，模型可能沿用先前的未就绪状态。现在明确要求每次新交办和恢复都重新查询，工具在实际提交前也再次核对。
- 紧凑证据视图原先只截取前三条，可能全部是当前对话或助手说明。现在同时返回原始变化，并优先呈现用户历史与更正，明确截断范围。
- 主动功能开关开启但未选通知位置时，就绪状态可能误报。就绪检查现在要求真实通知目标。
- 调查模型曾猜错筛选参数，或在读取历史前提交决定。补全参数与执行顺序的说明，继续由现有合同检查拒绝不合法调用。
- 相对提醒曾从推理完成后起算，实际比用户所说的一分钟更晚；模型提供的时间也可能包含时区换算错误。现在从不可变调用前缀中的真实输入时间起算，提交时冻结计划；回执转换到任务所选时区，同时显示偏移与时区名称。

## 证明范围

这些场景验证的是完整交互能否用起来：普通工具完成交办，历史更正参与新判断，显式规则能够调整之后的行为，实际结果可检查。预算也可能写入 Markdown 档案；本实验要求调查呈现对应原始历史，但没有关闭其他记忆来源，因此不能据此推断图召回相对其他记忆系统的净增益。

同一个模型、两个合成场景没有覆盖真实邮箱服务商、登录网页、跨对话管理、跨模型质量或连续多日使用。暂停不撤回已经进入调查的事件；聊天里的按新规则复查和反馈仍需补齐。已有延迟失败也不能因后来功能通过而改写成性能达标。

自然语言回复也没有逐句全部判定正确。例如最终展览恢复时，模型把暂停前完成的调查说成“暂停期间”；工具中的时间与决定仍可核对，但功能状态检查通过不代表所有时间叙述都准确。

超出声明模型窗口的完整 Turn 仍可能使 Markdown 档案学习报错，并在停止时传播；该问题没有通过删掉原始工具内容来规避，需要后续独立处理有界学习和失败恢复。本轮最终受控场景没有再次触发它。
