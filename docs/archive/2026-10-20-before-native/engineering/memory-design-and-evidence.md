# Kirakira 事件记忆：设计与表达

## 核心定位

Kirakira 面向持续运行的个人助手，把过去的对话当作可追溯的经历保存。
精确语义召回与图式联想补全协作，把相关经历连同日期和原文引用交给 Agent；需要核实时，
继续展开当时的上下文。图是能够恢复、重建的派生状态，原始消息拥有事实。

这一定位学习 Akashic 的“精确回忆与联想补全”、单一学习周期和原文事实源设计。
算法来源见 `plugins/akasha2/UPSTREAM.json` 与 MIT 许可证；本项目的工程工作是宿主的提交、
消费、回源、恢复与工具闭环，不把移植算法描述成独立发明。

## 三个可以展开讲的设计点

**经历包含关系。** 召回材料保留原始 user/assistant 对话及时间，能够核对是谁提出建议、
哪个对象对应哪个标识、旧结论什么时候被更正。`source_ref` 可以直接展开邻近消息。
人物或技术名词出现在摘要里，并不能单独证明它们之间的关系；模型需要具体证据。

**读取与学习有边界。** 对话先提交，publication 再驱动学习。重复通知不重复强化；显式
recall/fetch 保持只读。一次召回的全部原文在同一 SQLite 视图校验，外部修改不能导致同一
回答混用新旧读取版本。恢复和重放使用稳定消息身份、内容摘要与固定向量空间。

**记忆服务长期运行。** 图、消费 cursor、原文绑定与向量空间同一 checkpoint 发布；未发布
尾部按同一周期恢复，故障后停止使用脏状态。批量读取把恢复的源库连接从随历史增长降为两次，
同时保留逐条原文验证。该优化不替代图算法、分词或 embedding 的成本。

## 实验如何支持这些表述

公开 LongMemEval 回答质量、关系与细节保真的合成合同、原文引用闭环、故障恢复和成本分别测量。
完整结果连同失败保留在[记忆复测报告](../operations/evaluations/2026-10-19-memory-followup.md)
与[本轮专项报告](../operations/evaluations/2026-10-19-episodic.md)。

双通道不是每道题都比 BM25 或提取式记忆好。Mem0 的事实提取可以明显缩小 reader 上下文，
偏好与更正也有优势；本项目重点说明原始经历的保真、引用可验证和恢复一致性。
当前没有证明图关联在全部公开任务上更优，也没有移植上游完整 scope/feedback/查询 receipt。

## 项目介绍用语

构建具备主动交互与事件记忆的 Agent Runtime，将精确语义召回与关联补全接入统一执行链。
以原始消息为可追溯事实源，支持跨会话经历检索、邻近上下文回源与历史更正核验；通过提交后
消费、原子 checkpoint 和固定向量重放维持长期运行的恢复一致性，并以公开 QA、专项保真、
真实工具链和故障实验验证质量与工程成本。
