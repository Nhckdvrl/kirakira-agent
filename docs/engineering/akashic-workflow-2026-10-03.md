# 从 Akashic 提炼的开发工作流

这份文档修订原《从 akashic 提炼的 Vibe Coding 工作流》，保留“明确项目语义、区分回归与验收”的主线，更新已经退役的流程，并给出适用于 Kirakira 的执行方法。

核对日期为 2026-10-03，上游固定到 `7cf10136932d5fe0205727c803c00861272db0b8`。以下“当前”都指这个提交。依据包括工作手册、有效 ADR、目录与实际代码、CI 和验证脚本；没有执行上游的完整运行验收，也没有读取其私有 submodule 或维护者线上数据。原稿中的作者对话由用户提供，不能据此独立确认对话时间、完整语境或作者原意。

核心变化发生在 2026-10-01：上游接受了 [ADR 0083](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/decisions/0083-short-workflow-preserves-design-intent.md)，主动缩短工作流，保留设计意图和真实行为证据。旧九阶段、固定表格、强制 agent 概念评审与通用变更门禁，已经不能代表作者当前的方法。

## 一 原稿哪些保留 哪些需要改

| 原稿判断 | 本次核对结果 | 修订后的表达 |
| --- | --- | --- |
| 长期维护一套项目语义 | 仍成立，而且被放到必读设计原则中 | 写清允许改变什么，保护什么；沿行为和状态找条款与 ADR |
| 回归和验收是两件事 | 仍成立 | 同时证明目标达成和受保护结果仍成立 |
| 当前采用九阶段流程 | 已被 ADR 0083 替代 | 理解边界 → 修改并验证 → 交付 |
| 每次必填 `semantic_delta` 和完整任务合同 | 已取消强制要求 | 普通任务说明目标和完成标准；高风险任务补改变、保持、依据、验证 |
| `docker/debug/gate.py`、`tests_scenarios/contracts/` 是当前通用门禁 | 当前提交中没有这些路径，TST-006 明确退役 change-impact Gate | 阅读现存 CI、专项脚本和真实行为证据，不能照抄旧命令 |

| agent reviewer 是必要的第二裁判 | 当前由维护者负责架构与概念评审 | agent 自查有用，但不是授权来源，也没有指定评审模型 |
| 本地每次跑全量测试和全套 Gate | 已简化 | 本地做相关静态检查与实际行为验证，完整既有检查由 CI 执行 |

| 源码隔离后仍要统一打包备份 | 已按风险收窄 | 源码靠 Git，保留未提交内容；不可可靠重建的数据按实际风险备份 |
| 每次交付都新增 ADR | 过重 | 普通修复理由留在 PR，只有可复用设计取舍写 ADR |
| 热重载等同于整套 runtime snapshot 换代 | 不足以描述现状 | 单张运行图与局部插件换代已成为当前方向，沿有效 ADR 核对实际 owner |

这并不意味着早期做法没有价值。它说明作者后来发现：重复写合同、增加检查层和评审回执，仍可能掩盖对用户意图的误解。因此学习时要保留解决的问题，重新判断采用的机制。

## 二 从目录读出实际工作方法

目录的作用在于找到事实的责任人和验证入口。当前应这样阅读，而不是一次读完所有历史文档。

| 目录或文件 | 它回答的问题 | 读完以后应该知道什么 |
| --- | --- | --- |
| `docs/INDEX.md` | 本次任务该去哪里找依据 | 按行为、状态和 owner 路由，不只按准备修改的文件名 |
| `docs/projectneed.md` | 哪些结果必须保持 | 数据、权限、生命周期和外部行为的长期规则 |
| `docs/decisions/` | 为什么如此设计 | accepted / superseded 状态、勘误、替代方案与重议条件 |
| `docs/NOW.md` | 哪些工作尚未完成 | 当前缺口、接手限制与验收范围；不能从源码存在推断已经交付 |
| `docs/design/` | 一个复杂问题怎样落地 | 实际调用链、状态变化、失败、取消、迁移与验收 |
| `docs/writing-rules.md` | 哪个事实应写到哪里 | 一个事实一个权威位置，其他地方引用 |
| `agent/plugin_composition/`、`agent/plugin_contracts/` | 能力如何装配和获授 | 资源、作用域、消息读写和工具合同的边界 |
| `plugins/` | 业务行为由谁拥有 | React、Reply、Wake、Drift、Akasha 等普通插件的职责 |
| `session/`、`migrations/` | 哪些事实跨重启保留 | 权威数据、迁移入口及其写入责任 |
| `scripts/`、`.github/workflows/` | 哪些检查真的执行 | 检查命令、比较基线、触发条件与已知覆盖边界 |
| `docker/debug/` | 怎样在运行边界观察结果 | 按问题选择的隔离 probe、重放与互操作场景 |
| `tests/`、`docs/refactor/` | 既有回归资产如何保留 | 历史测试仍在，不能把“禁止新写单测”理解为删除回归 |
| `sdk/python/`、`schema/`、`frontend/` | 外部消费者怎样使用能力 | 公开入口、生成协议和用户实际看到的行为 |
| `private_runtime` | 公开仓库之外还有什么组合 | 这里只能确认 submodule 引用；不能声称私有组合已经检查通过 |

[阅读索引](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/INDEX.md) 明确区分了几类信息：用户当前指令决定本次授权；长期需求定义语义；有效 ADR 解释理由；代码证明现状；草案和旧会话提供线索。代码和意图冲突时，要报告差距，不能让当前代码反过来定义“正确”。

一个实际例子是“缩小模型窗口”。任务表面上像 prompt 优化，但索引要求继续读消息保留和非破坏性投影的决定，因为窗口变化可能越过历史存储边界。读目录的目的正是发现这类隐藏影响。

## 三 当前 Akashic 的三步流程

### 1 理解边界

普通任务先说明目标和可以观察的完成标准。涉及持久状态、owner、生命周期、公开接口或外部效果，再补四句话：改变什么、保持什么、依据什么、怎样验证。

例如：

> 缩小模型请求携带的历史窗口，降低输入开销。既有消息正文、身份、顺序保持；上下文模块仍没有删除历史的权限。依据非破坏性投影的决定。通过实际请求观察输入缩小，再关闭并重开会话核对原历史。

这比只写 `semantic_delta: none` 更容易判断对错。语义变化可以合法发生，但要明确它属于新功能、修复还是经确认的规格变更。

与现行规则一致、且已经得到授权的实现继续推进。只有会改变数据保留、权限、公共行为或现行设计，而现有授权不足的选择，才需要先交给维护者决定。这里没有“遇到任何不确定都停下来”的要求。

### 2 修改并验证

非简单修改用独立 worktree，记录目标分支和基线，保护原 checkout 的未提交内容。同一 worktree 同时只有一个 writer。交接记录分支、HEAD、dirty state、下一位 owner；不能靠 reset 清理掉不明改动制造“干净状态”。依赖改变时使用独立环境，避免污染共享虚拟环境。

验证选择能直接观察本次行为的最小入口：CLI/API、浏览器、真实组件集成，或隔离运行实例的重放。E2E 是工具之一，不是每次任务必走的仪式。除了目标行为，也要核对相关受保护状态，尤其是失败、取消和重新加载之后的结果。

Akashic 当前明确禁止新增或改写单测；既有测试和 CI 继续保留。这个选择属于该项目的协作政策，不能推导为所有项目都不应该写单测。它针对的问题是：实现者与自己写的函数级断言一起误解需求，最终得到没有意义的绿灯。

正式数据和验证数据分开。只换工作目录未必足够，还要核对实际 workspace、plugin home、config、HOME、连接目标和外部副作用。备份按实际写入与可恢复性决定，文件存在、指针回退或进程重启均不能单独证明数据恢复。

### 3 交付

交付前检查完整 diff 和目标分支的新变化。架构和概念由维护者评审，没有强制 agent reviewer、固定模型或概念 Gate。

当前默认每张 PR 新增约 500 行以内，删除不限；大任务优先 stacked PR，每层保持一个可理解、可验证的变化。按真实新增行数计算，不能用大量删除抵消新增，也不能靠压缩格式规避。这个上限是上游的阅读成本控制策略，不是项目质量定理。

PR 主要说明问题与结果、方案与理由、实际验证。数据、兼容性、外部效果或部署风险存在时，再展开相关合同和恢复方式。普通修复不必额外新建 ADR；可复用的设计选择才进入 decisions。完成事项从 NOW 删除。

以上为当前 [WORKFLOW](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/WORKFLOW.md) 与 [PR 模板](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/.github/pull_request_template.md) 的归纳，不是本文重新发明的九阶段。

## 四 流程缩短以后 靠什么防止失控

### 1 用窄接口落实 owner

“告诉 AI 不要删历史”只是一层约束。更强的设计是：上下文模块只拿到读视图和本轮投影能力，根本不需要持有任意 SQL 或删除接口。

当前 React 的实现位于 `plugins/react/plugin.py`，通过组合合同使用模型、工具和消息能力；Wake、Reply 等来源负责自己的业务语义。这个安排让普通业务插件不因“内置”身份获得特殊权限。目录迁移本身并不证明完成，仍要沿实际装配、执行和收尾路径验证。

学习点是先问“谁有权做这个动作”，再讨论类名和文件位置。[ADR 0065](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/decisions/0065-plugin-boundary-checks-do-not-grant-core-ownership.md) 专门纠正了“静态 import 清零等于架构完成”的推理。

### 2 对每类状态说明增 改 减

只列“这张表由谁拥有”不够。还要知道正常增加路径、允许的更新、逻辑失效、物理删除条件，以及恢复依据。

例如消息历史、上下文摘要和检索图不是同一类状态。消息是原始事实；摘要或图虽然派生自消息，也不因此自动获得删除权限。重建是否可靠，还依赖完整来源、固定参数、模型空间和消费位置。

当前 Akasha 的 `MessageConsumer` 明确校验消费进度与已发布学习图的一致性；已有消费记录却缺失学习图时，不默默从头重学。这里值得借鉴的是让不一致暴露出来，并把重建作为显式操作。

来源：[持久化状态地图](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/design/persistence-state-map.md)、[MessageConsumer](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/plugins/akasha/application/consumer.py)。

### 3 保留有明确目标的机械检查

当前 `.github/workflows/ci.yml` 仍执行 Python 类型检查、生成协议检查、Yoyo 迁移检查、Python SDK 检查、既有 pytest 回归和前端类型检查。另有 `plugin-boundary.yml` 检查依赖边界。不能把退役通用 change-impact Gate 理解成删除所有自动检查。

插件边界脚本既读取当前欠账清单，也在 `--base` 模式读取目标基线的真实源码。新增违规依赖，即使同时写入当前清单，也会被拒绝。这个机制比“告诉 AI 不要改白名单”更具体。

但代码和 CI 文件仍是版本化文件。仅凭公开源码无法证明仓库启用了何种 branch protection、谁有 bypass 权限，或候选分支绝对不能修改检查脚本。因此原稿“AI 改不了、骗不过”应改为：让具体违规可重复地被发现，并由独立的评审和仓库权限保护判据。

来源：[CI](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/.github/workflows/ci.yml)、[插件边界工作流](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/.github/workflows/plugin-boundary.yml)、[脚本实现](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/scripts/plugin_boundary.py)。

### 4 验证直接观察要保护的结果

| 要证明的事 | 不够的证据 | 更贴近目标的证据 |
| --- | --- | --- |
| 缩小窗口没有丢历史 | 回复成功，行数没变 | 原记录完整内容、身份和顺序不变；重开后仍可读；核对写入尝试 |
| 插件能替换 | import 检查通过 | 实际加载独立实现，依赖缺失明确失败，旧资源正确收尾 |
| 主动决策不会过期发送 | share 工具返回成功 | 判断期间推进会话或候选版本，观察旧草稿确实停止投递 |
| 记忆重建能恢复 | 创建了新数据库 | 同一来源和参数重放、重新加载并比较消费位置和检索行为 |
| 取消处理正确 | Task 标记 cancelled | 实际 worker、进程和租约收束；未确认外部效果保持未知 |
| 发布成功 | wheel 构建成功 | 独立环境安装后，经公开入口完成目标功能 |

本表前两行来自上游长期约束；其余是将同一方法用于 Kirakira 的验收建议，不能据表声称已经执行。确定性模拟 provider 可以用于观测真实 runtime 链路，但应如实说明模型是模拟的；它不能证明真实模型质量或外部渠道行为。

### 5 证据分层 绑定实际输入

静态检查、既有回归、隔离集成、真实设备、线上部署和模型质量各自证明不同事实，不能互相替代。未运行的层次就写未验证。

高风险“行为保持”改动，可以在 base 和 candidate 的隔离实例回放同组输入，对比持久写入、事件、外部调用、错误分类和用户结果。**两侧 passed 数量相同不构成行为等价证明**；测试全绿也只说明被观察的场景未发现差异。

跨仓库组合需固定参与方的 commit、协议、制品、运行环境和场景身份。任何输入改变都会形成新组合。源码 digest 只能把报告绑定到输入，不能证明断言正确、环境无污染或场景覆盖完整。

当前 [NOW](https://github.com/kachofugetsu09/akashic-agent/blob/7cf10136932d5fe0205727c803c00861272db0b8/docs/NOW.md) 对真实资源、外部组合、发行与 Akasha 线上切换仍列有未完成项。理解这种“实现存在，但运行验收未完成”的区分，比复制一份全绿报告更重要。

## 五 原对话更准确的解释

**“维护一套语义”**：让新会话知道用户意图、数据边界和失败含义。当前上游还补上理由与反例，避免只背一句 append-only，却在“压缩”“重建”中做了同样的删除。

**“通信架构”**：可以把它理解为接口、所有权、数据流、时序和失败协议。这是本文的工程解释，不能断言作者原话只指某种特定架构。人需要参与关键取舍，AI 可以自主完成已授权的局部实现，并用资料补齐未知。

**“成熟实践与 websearch”**：搜索帮助确认外部事实，但一个库成熟，不代表它适合当前 owner 和生命周期。要求 AI 给出来源、适用前提和代价，并回到本项目的实际链路验证；不是搜到一个常用库就结束设计。

**“静态语义”**：更适合理解为提前确认、相对稳定的规则，而不是“静态检查能证明一切”。原对话中的“不为 0”存在歧义，无法仅凭转述断定是笔误。可单独明确：声称保持行为的重构，不应产生未声明的可观察差异。

**“subagent 自审”**：能增加检查视角，但不会自动获得独立的正确性标准。当前 Akashic 不再要求强制 agent 概念评审。若选择委派，交付给执行者的应是相同基线、明确边界和可观察结果，并处理好 writer 交接；不必为每次任务机械地增加 agent。

**“组合语义”**：很多错误发生在组件连接、重启、取消和外部效果处。并非只能通过某个名为 Gate 的框架验证，真正重要的是实际经过这些边界，并观察目标状态。

## 六 Kirakira 可以直接采用的轻量流程

以下是本文建议，不把上游所有偏好自动变成 Kirakira 的规定。继续沿用已有的 `docs/INDEX.md`、`docs/status/current.md`、`docs/architecture/`、`docs/decisions/` 和 `docs/operations/verification.md`，避免再建立一套重复的事实中心。

### 开工

先读索引，再沿真实入口追到状态 owner。普通任务用一段话说明目标和完成标准；高风险任务加上保持项、已确认依据和验证方式。已有授权范围内自主推进，只对会改变设计或授权范围的未知进行澄清。

可以复制这个说明：

> 本次解决【具体触发和问题】，完成后【可观察结果】。改变【行为或结构】，保持【相关数据、权限和外部行为】。依据【已有决定或本次需求】，通过【实际入口与观察对象】验证。尚不覆盖【明确范围】。

不强制填不适用项，不把这段话再复制到多个文档。

### 实现

每次围绕一个完整行为改动，优先让模块只获得它需要的能力。迁移职责时检查输入、排队、取消、提交、通知、恢复、资源关闭是否都被接走。新旧入口统一以后删除重复执行逻辑，不能只把旧代码搬到新文件。

大改动先拆可审阅切片。500 行可以作为阅读成本提醒，但是否合适取决于行为能否独立理解与验证；上游的数字不会自动成为本仓库硬约束。

### 验证

既有回归检查继续保留。新增验证优先选择能观察实际风险的层次：纯算法适合确定性测试，持久化和生命周期适合真实组件集成，公开用户链路适合 CLI/API 或 E2E。Kirakira 不机械引入上游“禁止单测”的政策，也不为每个简单修改增加测试。

测试预期来自已确认需求。可以在一个功能改动中合理增加测试，但不能为让退化通过而悄悄降低已有不变量。关键失败路径必要时核对修复前确实失败、修复后通过；不要求为每个条款建立 mutant 框架。

验证结果写清命令、源码范围、隔离环境、实际观察和限制。复用已有的专项检查，不因为这篇分析额外造一套通用 Gate。收费 provider、外部发送和正式部署按实际授权执行，离线回归不冒充线上质量结果。

### 交付

报告结果、理由、验证和重要限制。更新被改变的文档事实，明确未完成范围；普通过程不进入长期规则。提交、推送、合并和部署按本次已有授权分别处理，已经明确授权的动作不重复请示。

这轮用户已经授权直接推送 `main`，因此无需为了模仿上游而临时改成强制 PR 审批流程。

## 七 用当前重构检验这套流程

以“统一 agent core”为例，文件更整齐只是中间结果。完成标准应该落到真实路径：

1. 对话、直接调用、控制调用、Wake、Drift、子任务及兼容 API 是否都经过共享推理器；是否还存在另一套独立工具循环。
2. 同一会话不同入口是否会同时改写状态；取消是否关闭实际 worker 并记录中断事实。
3. 工具执行后模型报错，是否会重跑整轮并重复副作用。
4. 进程中断后，是否能够区分未执行、已确认结果和结果未知；未知不能伪装成失败后直接重试。
5. 持久历史是否保持，内部任务是否意外污染长期记忆。
6. 新的执行日志和检查脚本是否进入实际 bootstrap 装配，而非只在测试中出现。

这是一组针对本次工作的验收问题，不是“已经与 Akashic 完全对齐”的声明。Kirakira 当前实现与剩余差距统一看[当前状态](../status/current.md)，实际运行过的证据看[验证记录](../operations/verification.md)。

对于双主动和记忆，还要再区分两种完成：运行合同正确，以及实际效果更好。前者检查过期决策、重复发送、消费原子性和重建一致性；后者需要固定数据、预算、基线、重复实验与误差分析，测量召回、延迟、成本和打扰率。不能用更复杂的算法或更多测试数量替代质量证据。
