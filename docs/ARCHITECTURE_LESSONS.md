# 架构与系统设计：用这个项目里的真实决策来讲

这份文档不讲抽象的"高内聚低耦合"。它把**这个仓库里真实发生过的决策**拆开，讲清楚每一个决策
在权衡什么。架构能力不是记住模式名字，而是能在具体场景里说出"为什么是这个而不是那个"。

读法建议：每一节先看"场景"，自己想 30 秒会怎么做，再往下看。想错了比直接看答案记得牢。

---

## 0. 一个前置观念：架构是关于"变化"的

如果需求永不变、规模永不涨、依赖永不挂，那所有架构都是多余的——一个 `main.py` 全写完最省事。

架构存在的唯一理由是**某些东西会变，而你希望变化的代价是可控的**。所以每次做架构决策，先问：

1. 这里**什么会变**？（工具会增加？模型会换？MCP server 会改配置？）
2. 变的时候**谁应该被迫改代码**？（理想情况：只有变的那部分）
3. 变的过程中**系统处于什么状态**？（这一条最容易被忽略，也最容易出事）

第 3 条是本项目最贵的一课，第 4 节会详细讲。

## 1. 分层：为什么 ToolRegistry 不只是一个 dict

**场景**：模型返回 `{"name": "read_file", "arguments": {...}}`，你要执行它。最直接的写法：

```python
TOOLS = {"read_file": read_file_impl}
result = TOOLS[call.name](**call.arguments)
```

这行代码能跑。它的问题不是"不优雅"，而是它把**六件事**压成了一件：

| 隐含的职责 | 出问题时的现象 |
| --- | --- |
| 工具是否存在 | `KeyError`，整个循环崩了 |
| 参数是否合法 | `TypeError`，模型不知道自己错在哪 |
| 是否允许执行 | 没有这个概念 |
| 同步还是异步 | 阻塞 event loop，所有 session 一起卡 |
| 异常怎么办 | 冒泡出去，turn 直接死 |
| 结果长什么样 | 每个工具各写各的 |

本项目拆成两层，边界是这么划的：

```text
ToolExecutor   ——  "能不能执行、执行前后要做什么"
    pre hook（可改参数、可拒绝）→ 派发 → post hook → 归一化
ToolRegistry   ——  "怎么执行"
    查找 → schema 校验 → 同步/异步分派 → 异常转 ToolResult
```

**为什么这样切**：因为这两件事的**变化频率和变化原因完全不同**。新增一个工具，只动 registry
里的一条注册；新增一条安全策略（比如"禁止对 /etc 写入"），只动 hook，不碰任何工具实现。

> **可迁移的判断**：想知道该不该拆，问"这两部分会因为**不同的原因**、在**不同的时候**被改吗？"
> 会 → 拆。这就是单一职责原则的实际含义——不是"一个类只做一件事"，而是
> **"一个模块只有一个改变它的理由"**。

**反过来也要会判断**：`ToolResult` 里为什么不给每个工具单独定义结果类型？因为它们变化的原因
是一样的（协议要求回填 tool message），拆开只会让调用方到处 isinstance。**没有独立变化原因的
东西，拆开是负债。**

## 2. 依赖方向：为什么 MCP 要"适配"进 ToolRegistry

**场景**：接入 MCP。它是外部进程、JSON-RPC、schema 运行时才知道。看起来跟本地 Python 函数
完全不同，很容易写成一套独立的 `McpExecutor`。

如果那样做，你会得到：

```text
Reasoner
├── 本地工具：schema 校验 / hook / 超时 / 错误归一
└── MCP 工具：另一套 schema 校验 / 另一套 hook / 另一套超时 / 另一套错误归一
```

于是每加一条策略（比如工具调用要记 lifecycle 事件），你要写两遍，而且**迟早会漏一遍**。

正确做法是让 MCP **适配到已有抽象**：远端 schema 转成 `ToolSpec`，远端调用包成一个 handler。
对 Reasoner 来说，MCP 工具和本地工具**没有区别**。

```text
Reasoner → ToolExecutor → 统一的 Tool 抽象
                              ├── 本地 handler
                              ├── 插件 handler
                              └── MCP handler（内部是 JSON-RPC）
```

> **可迁移的判断**：新接一个外部系统时，先问"它能不能表达成我已有的抽象？"能 → 适配它
> （Adapter），别开新路。**抽象的价值与共用它的实现数量成正比**：只有一个实现的接口是浪费，
> 有三个实现的接口是资产。

**什么时候不该硬适配**：如果强行适配需要在抽象里开一堆 `if is_mcp:` 特例，说明抽象错了。
适配的标志是"新实现填空即可"，不是"新实现逼着抽象长出分支"。

## 3. 命令式 vs 声明式：本项目最大的一次推翻

**场景**：用户要配置 MCP server。两种做法：

```python
# A. 命令式：提供动词
mcp_add(name="fitbit", command=[...])
mcp_remove(name="fitbit")

# B. 声明式：提供事实
# workspace/mcp/servers/fitbit.toml
```

A 更直观，也是我们最初抄过来的版本。Reference 后来把它整个删了。理由值得记住：

| | 命令式 | 声明式 |
| --- | --- | --- |
| 真相在哪 | "谁调用过什么"的累积结果 | 文件内容 |
| 重启恢复 | 要把历史操作回放一遍 | 读一遍当前内容 |
| 幂等 | 需要自己保证（重复 add 会怎样？） | 天然幂等 |
| 改配置 | 记得 remove 再 add | 改文件 |
| 部分失败 | 三个成功一个失败 → 半完成 | 整批拒绝 |
| 谁负责收敛 | 调用方 | watcher |
| 能不能 diff/review/版本控制 | 不能 | 能 |

**核心区别**：命令式描述 **how to change**，声明式描述 **what should be**。

只要"应该是什么"能被完整写下来，声明式几乎总是更好，因为它把"当前状态"变成了**可读、可比
对、可重放**的东西。收敛逻辑（reconcile）集中在一处，而不是散在每个调用点。

Kubernetes 的 YAML、Terraform 的 `.tf`、Nix 的 derivation、CSS（声明样式而非绘制指令）——
都是同一个思路。Reference 只是把它用在了 MCP 上。

**什么时候该用命令式**：当"事实"本身就是事件而不是状态时。"给用户发一条消息"是命令，不是
声明——你没法说"应该存在一条已发送的消息"。**状态用声明式，动作用命令式。**

我们的实现把三件事分开，正好对应声明式的三个环节：

```text
declarations.py   期望状态是什么（解析 + 校验 + 内容 revision）
host.py           实际能不能达成（整批连接）
watcher.py        什么时候去收敛（轮询 + 串行发布）
```

一个细节值得注意：`revision` 是**内容哈希**而不是文件 mtime。`touch` 不触发重连，真改内容才
触发。**用内容而不是元数据判断变化**，这是幂等的基础。

## 4. 状态机与中间态：架构最容易漏掉的一维

前面说过"变化过程中系统处于什么状态"最容易被忽略。这一节讲透。

**场景**：MCP 声明变了，要换新 server。朴素实现：

```python
for name in old_tools:
    registry.unregister(name)      # 先卸旧
await old_client.disconnect()
new_client = await connect(...)     # 再上新
registry.register(new_tools)
```

看起来没问题。但把时间轴画出来：

```text
t0  turn 开始，模型准备调用 mcp_fitbit__today
t1  watcher 卸掉旧工具、断开旧连接
t2  模型真的发出 mcp_fitbit__today
    → "Unknown tool"（或更糟：用已断开的连接去调）
```

**一个 turn 可能跑几十秒、十几轮工具调用。在这段时间里，世界会变。**

加锁行不行？让换代等 turn 结束？不行——高并发下永远有 turn 在跑，换代可能永远等不到窗口；
而且这会让"改个配置文件"阻塞在一个跑了 5 分钟的 turn 上。

真正的解法是**把"当前能力"从可变对象改成不可变代际序列**：

```text
                    ┌─ compiled（候选已就绪，还没生效）
                    ├─ published（current，新 turn 用它）
                    ├─ retired（不再接新 turn，但老 turn 还在用）
                    └─ drained（最后一个租约释放，资源真正销毁）
```

配合租约（lease）：

- turn 开始 → `lease()`，`lease_count += 1`
- 换代 → 只切 `current` 指针，**不动任何在途 turn 看到的东西**
- turn 结束 → `release()`，`lease_count -= 1`
- `lease_count == 0` 且状态是 retired → 才真正 `drain`（断开进程）

结果：新 turn 立刻用新能力，老 turn 用完旧能力，**两者都是自洽的**，没有中间态。

> **可迁移的判断**：只要一个资源**可能在使用期间被替换**，就需要"引用计数 + 延迟回收"。
> 这不是新东西——它就是 RCU（read-copy-update）、MVCC（多版本并发控制）、Java 的
> GC roots、Rust 的 `Arc`、数据库连接池的优雅换池。**共享可变状态 + 长事务 = 必然的竞态**，
> 而解法总是"让读者看到一个不会变的版本"。

这也解释了为什么我们把 MCP 工具**移出**共享 ToolRegistry：

```text
基础 ToolRegistry   启动即固定的东西（内置工具、插件工具）
RuntimeSnapshot     会变的东西（MCP 工具、phase 模块）
SnapshotToolView    把两者组合成"本轮的只读视图"
```

**把不变的和会变的分开存放**，是让"不可变代际"这个方案成本可控的关键——你不需要为每一代
复制整个注册表。

### 4.1 一个隐蔽的坑：ContextVar 会被继承

快照通过 ContextVar 绑定到 turn。但：

```python
if binding.owner_task is not asyncio.current_task():
    return None
```

这个检查看着多余，实际上防的是真问题：**`asyncio.create_task()` 会自动复制当前 context**。
父 turn 派生的后台子任务会"免费"继承父任务的快照绑定——但它没有自己的租约。于是父 turn
结束、`lease_count` 归零、资源销毁之后，子任务还拿着一个已经 drained 的快照在跑。

规矩：**想跨任务用，必须 `fork()` 自己的租约。** 因为 `lease_count` 是资源回收的唯一依据，
任何"白嫖"都会让计数说谎，而计数一旦说谎，回收就会提前。

> **可迁移的判断**：任何"隐式传播"的机制（ContextVar、ThreadLocal、隐式事务、AsyncLocalStorage）
> 都要问一句：**它传播出去之后，生命周期还对得上吗？** 传播的是引用，但引用不会自动延长寿命。

## 5. 错误边界：fail-loud 与 fail-soft 的分界线

**场景**：向量服务挂了。要不要报错？

标准答案"看情况"等于没答。本项目给出的分界线很锋利，看这两段**处理同一个异常**的代码：

```python
def _embed_for_query(self, text):      # 检索
    except Exception:
        logger.exception("falling back to lexical recall")
        return None                     # 降级

def _embed_for_store(self, text):      # 写入
    except Exception as exc:
        raise RuntimeError(...) from exc  # 报错
```

同一个 `embed()`，同一个异常，两个相反的处理。分界线不是"错误严不严重"，而是：

> **降级之后，系统状态是否还是自洽的？**

- 查询失败 → 这次答案差一点，向量服务恢复后自动变好。**没有留下痕迹。**
- 写入失败 → 这条记忆永远没有向量，索引里一半有一半没有。**损坏被固化进了数据。**

第二种最阴险的地方在于：**它当时不报错，半年后你发现"某些记忆搜不到"，但已经无法追溯是哪
一次写入时向量服务抽风了。**

实用判断法：

1. 这次静默降级，**会不会留下痕迹**？不会 → 可以降级。
2. 留下的痕迹**能不能自动修复**？能 → 可以降级（但要有日志）。
3. 不能自动修复 → **必须报错**，让人当场知道。

再问一句更狠的：**"如果我在这里 `return None`，半年后谁会为此调试到凌晨三点？"**

### 5.1 "整批拒绝"是同一条原则

`host.prepare()` 里，一个 server 连不上就把已连上的全断开。直觉上很浪费，但：

**"部分可用"是最难排查的状态。** 留下三个 server 的话，模型看到一个残缺工具集，给出一个
**看起来正常、其实基于不完整能力**的回答。用户不知道第四个没连上，只觉得"agent 今天有点笨"。

整批拒绝 + 旧代际继续服务 → 要么全新要么全旧，**永远是一个自洽的集合**。

> **可迁移的判断**：**一致性通常比可用性更值钱**——尤其当"部分可用"会产生看似正常的错误
> 输出时。这是 CAP 里选 C 的场景：不是所有系统都该选 A。

### 5.2 什么时候该 fail-soft

本项目也有故意不 fail-loud 的地方，比如 EventBus 的观察者：

```python
except Exception:
    logger.exception("observer error for %s", type(event).__name__)
```

一个观察者（比如某个统计插件）挂了，不应该让用户的回复发不出去。**观察者是旁路，不是主路。**
判断依据还是同一条：观察者失败不会让主链路状态损坏，所以可以隔离 + 记录。

## 6. 派生优于硬编码

**场景**：

```toml
memory_window = 40    # 为什么是 40？
```

没人知道。换个 1M 上下文的模型，40 是不是太小了？换个 8k 的，40 是不是会爆？

改成派生：

```python
memory_window = 按 1M 基准等比例缩放(context_window)，对齐到 4，下限 20
```

现在配置里只需要写 `context_window = 128000`，一个**客观事实**，而不是一个**拍脑袋的结果**。

> **可迁移的判断**：**一个硬编码常数背后，往往藏着一个没写下来的公式。** 把公式写出来，
> 常数就变成了它的一个取值，而且"为什么是这个值"自动有了答案。

顺带一个真实数据点：Reference 在 #117 里把基准从 640 调到 160。如果当初是每个模型硬编码，
这次调整要改 N 处；有了派生公式，只改一个基准值。**派生的收益不在第一次写，而在第 N 次改。**

### 6.1 上下文降级为什么要按语义，而不是按字符串

旧实现遇到 context overflow 时对 messages 做 microcompact。它能变短，却回答不了三个问题：

1. 丢掉的是 skills 目录、检索记忆还是用户历史？
2. 为什么先丢这一部分？
3. 下一次模型或插件变更后，裁剪结果还能不能复现？

现在 prompt 先被拆成具名 block，再由 `ContextTrimPlan` 表达降级顺序。每个 attempt 都从原始 turn
输入重新执行 hooks 和 render，记录 disabled sections、history window、section estimate/cache hit。
这不是为了“类型更多”，而是把不可解释的字符串操作变成可审计的策略决策。

预算也分两层：Runtime 提前估算并给 UI/插件可观察事件；Provider 在网络请求前根据最终 messages
和实际暴露的 tool schemas 再预检。只有第一层会漏掉 ReAct 中途解锁的工具，只有第二层又无法解释
是哪个 section 把请求推过阈值。两层职责不同，不能互相替代。

这里仍有真实 tradeoff：外层 retry 会重新执行 Reasoner；如果 overflow 发生在有副作用的工具之后，
模型可能再次选择该工具。因此工具幂等性仍是合同的一部分。所谓“完整上下文管理”不是宣称没有风险，
而是让预算、丢弃顺序、重试和剩余风险都有明确记录。

## 7. 装配与依赖注入：为什么 build_runtime 那么长

`cli.py::build_runtime` 有一百多行，全是 `X(a, b, c)` 的拼装。看起来很笨，甚至像"坏味道"。
但它是刻意的：

```python
snapshot_store = RuntimeSnapshotStore()
mcp_publisher = McpCatalogPublisher(snapshot_store)
snapshot_store.set_drain_handler(mcp_publisher.drain_snapshot)
```

**所有组件都不知道自己是被谁装配的**，也不去全局变量里找依赖。好处直接体现在测试上：

```python
# tests/test_runtime.py
_bus, loop, _sessions, _memory = build_test_runtime(
    Path(tmp), model, snapshot_store=store
)
```

测试能塞进一个假模型、一个自己控制的 store，是因为**生产代码从不自己 new 依赖**。如果
`PassiveTurnPipeline` 内部写死 `self.store = RuntimeSnapshotStore()`，那个 mid-turn 热重载
的测试根本没法写。

上面那段 `set_drain_handler` 还展示了一个实用技巧：`store` 和 `publisher` 互相需要（循环依赖）。
解法不是让它们互相 import，而是**构造完再注入回调**——把循环打在装配层，不带进模块依赖图。

> **可迁移的判断**：**装配（assembly）应该集中在一个地方，而且这个地方应该很无聊。**
> 如果装配散落在各个模块的 `__init__` 里，你就再也没法在测试里替换任何东西了。
> "长而无聊的装配函数"是特性，不是缺陷。

## 8. 什么时候不要抄

本轮最重要的一个决定，其实是**没做什么**：

Reference #111 是 236 文件、18000 行的 fail-loud 全仓重构。照抄它需要好几个星期，而且其中
大半是 proactive、dashboard、peer-agent——这些是本项目明确排除的范围。

我们做的是：**读懂它的原则，应用到自己的范围**。最后落地成 4 处修改和 5 个测试。

> **可迁移的判断**：抄一个成熟项目时，要分清 **它做了什么（what）** 和 **它为什么这么做（why）**。
> what 依赖它的规模、团队、历史包袱，你多半不需要；why 才是可迁移的。
>
> 判断标准很简单：**"它解决的那个问题，在我的项目里存在吗？"**
> - 存在（工具会在 turn 中途被换掉）→ 抄，哪怕实现要简化。
> - 不存在（我只有一个模型后端，不需要统一两类后端）→ 不抄，写进"有意未跟进"。

第三种情况最微妙：**问题现在不存在，但快了**。这时候正确做法通常是**先写进文档，别写进代码**——
因为你对未来问题形状的猜测，准确率远低于你的想象。`docs/DIFFERENCE_AUDIT.md` 第 5 节存在的
意义就在这里：**它让"暂时不做"变成一个有记录的决定，而不是一次遗忘。**

## 9. 一页速查

| 场景 | 问题 | 判断 |
| --- | --- | --- |
| 该不该拆模块 | 会因不同原因、不同时候被改吗 | 会就拆；不会就别拆 |
| 接外部系统 | 能表达成已有抽象吗 | 能就适配，别开新路 |
| 配置怎么设计 | 状态还是动作 | 状态用声明式，动作用命令式 |
| 判断"变了没有" | 用内容还是元数据 | 内容哈希，不用 mtime |
| 资源可能被热替换 | 有没有长事务在用它 | 有就要不可变代际 + 租约 |
| 隐式传播的上下文 | 传出去后生命周期对得上吗 | 对不上就要显式 fork |
| 异常要不要吞 | 降级后状态自洽吗 | 自洽可降级，否则必须报错 |
| 部分失败 | 部分可用会产生假象吗 | 会就整批拒绝 |
| 又一个魔数 | 它背后有公式吗 | 有就写出来 |
| 依赖怎么给 | 测试能替换它吗 | 不能就说明装配写错了 |
| 要不要抄 | 那个问题我有吗 | 没有就记进文档，不写进代码 |

## 10. 延伸阅读

按对本项目的相关度排序：

- **Designing Data-Intensive Applications**（Kleppmann）第 5、7、9 章——多版本、事务、一致性。
  第 4 节的租约机制本质上是 MVCC 的一个小型特例。
- **A Philosophy of Software Design**（Ousterhout）——"deep module"（窄接口、厚实现）正是
  `ToolRegistry` 想做到的；书里对"战术编程 vs 战略编程"的区分，跟第 8 节是一回事。
- **Release It!**（Nygard）——稳定性模式。第 5 节的 fail-loud/fail-soft 分界在这里有系统讨论。
- Kubernetes 的 reconcile loop 设计文档——第 3 节声明式思路的工业级样本。
