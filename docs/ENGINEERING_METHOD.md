# 工程方法:怎么把一个 MVP 养成一个不塌的系统

> 这份文档不讲这个项目**有什么**,讲的是把它从 200 行养到 3.4 万行的过程中,
> 哪些判断是对的、哪些是错的、以及**下次遇到同类问题该怎么判断**。
>
> 本文只保留可复用的方法论。过期的阶段编年史已删除；真实选择由 `decisions/`、`design/`
> 与 Git 历史保存。每一条方法后的 commit 可以用 `git show` 检查当时代码。

---

## 1. 复杂度不是行数,是耦合面

3.4 万行本身不难。难的是这样一件事:

> 你想加一个"记忆检索"的能力,结果发现要改模型客户端、要改 turn 流程、
> 要改插件接口、还要改三个测试的构造函数——**而这四处逻辑上跟记忆无关**。

这就是耦合面。它的度量不是行数,是"改一件事要碰几个不相关的地方"。

本项目最早的真实症状,是我在接记忆引擎时反复卡住,当时的原话是:

> "他们随便接的一个记忆接口我们要搞半天。"

那不是记忆的问题。记忆的算法零件当时**已经全部搬进来了**,卡住的是接口的形状:
引擎是 async 的,而我们的模型客户端只有同步 `complete`,runtime 里满地
`asyncio.to_thread(...)`。每接一个 async 组件,都要在缝上再裹一层线程。
**症状出现在记忆,病根在模型运行时。**

> **可迁移的判断**:当"接一个本该简单的东西"反复困难时,先怀疑地基,
> 不要在接口处加适配层。适配层会让病根更难被发现,因为它把症状消掉了。

## 2. 加代码,还是动地基?

这是全过程最重要的一个判断。判断错了,要么过早抽象(做了没人用的框架),
要么该重构不重构(适配层越堆越厚)。

三个可操作的信号,命中任意一个就该考虑动地基:

### 信号一:接口在缝上别扭

不是"写起来麻烦",是**类型或生命周期对不上**。同步裹异步、对象里塞配置、
需要传一个"暂时用不到但接口要求有"的参数——这些都是缝错了。

- 实例:`asyncio.to_thread(model_client.complete)` 遍地都是 → 地基① 异步原生
  model runtime([0f448f1](https://github.com/Nhckdvrl/kirakira-agent/commit/0f448f1))。

### 信号二:同一件事在三个地方手写

两处可以忍(可能真是巧合),**三处就是缺抽象**。

- 实例:主动推送的投递,在 alert / content / drift 三条路径上各写了一遍
  "发送 → 成功就写 session → 失败就回滚"。抽成 `TurnResult` 的副作用提交单点后,
  三处分支收敛成一处([f29fd52](https://github.com/Nhckdvrl/kirakira-agent/commit/f29fd52))。

### 信号三:加新功能要改无关模块

如果"插一个新的主动数据源"必须改主循环,那扩展点就不存在,只是看起来存在。

- 实例:主动 tick 原本是一个扁平的大函数,插件想在中间插一步做不到。
  改成模块流水线 + slot 依赖图后,插件声明 `requires` 就能插进任意位置
  ([179ab28](https://github.com/Nhckdvrl/kirakira-agent/commit/179ab28))。

**反过来,不该动地基的情况**:功能确实是"加法"——它坐在现有抽象上,不需要改
任何既有模块的签名。这类东西越晚做越好,因为地基还在变。本项目把
control plane、Dashboard、peer-agent 一直押后,就是这个理由。

## 3. 什么是"地基抽象"

判断标准只有一条:

> **它的形状决定了别人怎么接。改它要动很多处;不改它,别人接进来都会别扭。**

按这个标准,本项目识别出四个,并且是**先做完这四个才做上层加法**的:

| # | 地基 | 它决定了什么 | 不做的后果 |
| --- | --- | --- | --- |
| ① | 异步原生 model runtime | 所有 LLM 调用的调用约定 | 每个 async 组件都要裹线程 |
| ② | 依赖注入(Services/Ports) | 模块拿到的是"服务"还是"整个世界" | 单测一个模块要构造整个 runtime |
| ③ | Turn 抽象 + lifecycle slot DAG | 一轮的结果与副作用如何提交、模块如何排序 | 副作用散落,插件无法插队 |
| ④ | 记忆 seam | 检索智能藏在引擎后面还是漏给 runtime | runtime 被迫理解 HyDE / RRF |

**顺序原则**:上层加法依赖下层地基。先地基后上层,才不会"接个东西搞半天"。

值得注意的是地基②的形状:

```python
# 配置(值) 与 服务(对象) 分开,是两类东西
LLMConfig / MemoryConfig       # 值:可序列化,可比较,进得了配置文件
LLMServices / SessionServices  # 对象:有生命周期,要关闭,不可序列化
```

把它们混在一个 dict 里传,是最常见的 DI 退化形式——一旦混了,你就没法回答
"关停时该释放什么"。本项目正是因为分开了,才发现引擎的 `closeables`
从来没被关过([0db880f](https://github.com/Nhckdvrl/kirakira-agent/commit/0db880f),
这是一个真实的资源泄漏)。

## 4. 复杂系统的五种腐坏方式

这一节是本文最实用的部分。每一种都配本项目的真实实例、**当时是怎么发现的**、
以及**下次怎么更早发现**。

### 4.1 死代码:声明了,但没通电

写了一个模块/函数,它看起来完整、有测试,但**生产路径上没有任何调用点**。

- **实例**:`compile_proactive_sources` 把插件声明编译成主动数据源。我写完它、
  测了它、并在文档里写下"插件主动源缺口已闭合"——但它的引用数是 **0**。
  自查时才发现([62e6d2c](https://github.com/Nhckdvrl/kirakira-agent/commit/62e6d2c))。
- **第二次犯**:控制面把工具调用投影成 `toolCall` item 的那段代码,读的是
  `outbound.metadata["tool_chain"]`——而我们的 `outbound.metadata` **从来没写过这个字段**。
  单测是绿的,因为测试里的 metadata 是我自己构造的
  ([0e5471e](https://github.com/Nhckdvrl/kirakira-agent/commit/0e5471e))。

> **怎么更早发现**:写完一个能力,别问"测试过了吗",问 **"谁调用它?生产入口在哪一行?"**
> 一条 `grep -rn "<函数名>" --include=*.py | grep -v test` 就能证伪。
> 本项目现在把这条做进了 doctor 的漂移审计。
>
> 更狠的一条:**消费方的测试不要自己造上游数据**。我两次都栽在这上面——
> 我造的 metadata 里有 `tool_chain`,真实上游没有。测试于是变成了"我的想象自洽",
> 而不是"系统自洽"。

### 4.2 幽灵资源:创建了,但不释放

对象持有 SQLite 连接、子进程、HTTP client,关停时没人调它的 `close`。
本地跑不出问题,长跑就会积累。

- **实例**:`DefaultMemoryEngine` 有一个 `closeables` 列表,里面是 store 和 embedder。
  移植时把这个列表搬过来了,**但没有人遍历它**。修法是 `MemoryServices.aclose()`
  逆序释放,且单个失败不掩盖其余([0db880f](https://github.com/Nhckdvrl/kirakira-agent/commit/0db880f))。
- 同期发现的关联问题:`coremem.db` 被打开了**两次**(引擎一次、Dashboard 一次),
  造成锁竞争和不一致视图。修法是引擎作为单一 owner,把 store 暴露出去共享连接。

> **怎么更早发现**:任何 `__init__` 里出现连接/进程/文件句柄,当场问
> "**谁在什么时候关它**"。答不上来就是泄漏,不是"以后再说"。

### 4.3 移交丢行为:换了驱动方,顺手丢了一个不起眼的职责

把一件事的驱动权从 A 移交给 B 时,A 顺带做的小事很容易被忘掉。

- **实例**:consolidation 的驱动权从 `MemoryRuntime` 移交给
  `MarkdownMemoryMaintenance` 时,丢掉了"**等上一轮归档收口**"这个 guard。
  丢了以后不会报错,只会在并发时产生错乱的归档
  ([ec97257](https://github.com/Nhckdvrl/kirakira-agent/commit/ec97257))。
  这次移交一共丢了两个行为,都作为**勘误**写进了
  [decisions/0003](./decisions/0003-consolidation-handover.md) 而不是悄悄补掉。

> **怎么更早发现**:移交前先把 A 的**全部职责列成清单**(包括它顺带做的),
> 逐条勾对 B 是否接住。清单本身要留在 decision 记录里——因为丢的往往是
> "当时觉得不值一提"的那一条。
>
> **勘误要写进原记录,而不是新开一条**。读者是顺着记录找答案的,
> 让他在原地看到"这里当初错了"比让他自己发现要好。

### 4.4 文档与代码漂移

文档写的是当时的意图,代码后来变了,没人回头改文档。**过期文档比没有文档更糟**,
因为它会让接手人做出错误决策。

- **实例**:`DIFFERENCE_AUDIT.md` 里有四处断言与实现冲突——它们在写下时是对的,
  后来实现推进了([5272541](https://github.com/Nhckdvrl/kirakira-agent/commit/5272541))。

> **怎么更早发现**:两条硬规则。
> 1. **一个事实只设一个权威位置**,其余文档用链接引用。同一个数字写在三处,
>    就一定会有两处过期。
> 2. **未完成事项只写在 `NOW.md`**,完成即删除,历史交给 git 和 decisions。
>    没有"Done"章节——一旦有,它就会变成一个只增不减的许愿池。

### 4.5 过渡态沉淀:临时方案活得比预期久

迁移期的兼容层、旧路径、双写,做完迁移后没删,变成永久债务。

- **实例**:旧的 consolidation 路径在新路径上线后仍然留着"以防万一"。
  真删掉时([4d915e1](https://github.com/Nhckdvrl/kirakira-agent/commit/4d915e1))
  才确认新路径确实承重。`memory.py` 也从 1039 行降到 823 行。

> **可迁移的判断**:留着旧路径不叫"稳妥",叫"不敢确认新路径是否真的在工作"。
> 真正的稳妥是**删掉旧路径,让问题立刻暴露**——它暴露得越晚,代价越大。
> 本项目的原则是:**不保留过渡阶段后面不会再用到的东西。**

## 5. 测试绿 ≠ 系统能跑

这是本项目代价最大的一课,值得单独一节。

454 个测试全绿,只证明**单测口径下**的行为成立。它系统性地抓不到两类问题:

1. **跨组件的真实交互**——测试用 mock provider 和替身渠道,组件之间真实的
   数据形状从未被走过;
2. **真实模型的输出偏差**——mock 永远按约定返回,真实模型不会。

### 三次实弹,三个 mock 抓不到的 bug

| 何时 | Bug | 为什么单测抓不到 |
| --- | --- | --- |
| 记忆实弹 | `PostResponseMemoryWorker` **整条路抛 ValueError**:deepseek 返回 `{"intent": []}`,而解析器要求裸数组 | mock 不会这样返回;且这条路要配好 embedding 才会走到([1970b34](https://github.com/Nhckdvrl/kirakira-agent/commit/1970b34)) |
| 自查 | `compile_proactive_sources` 零调用点 | 它自己的测试是绿的 |
| 控制面实弹 | toolCall 投影拿不到数据 | 测试里的上游数据是我自己造的 |

修第一个时有一条**边界纪律**值得记:容错写在 Kirakira 自己的
`plugins/default_memory/compat_worker.py`，上游只提供设计依据。运行时和 doctor 不读取上游 checkout；
差异由开发期审计和本地合同测试记录。

### 落到制度上

本项目现在有一份 [design/live-verification.md](./design/live-verification.md),
逐项标注 **F(真跑过)** / **G(只测过)**,并且明确列出仍未验证的边界。

> **可迁移的判断**:"测过"和"跑过"是两个词,不要混用。
> 报告状态时说"429 测试通过"是诚实的,说"功能已验证"就不是——
> 除非你真的跑过。**把没验证的部分明确列出来,比笼统说"已完成"更有价值**,
> 因为接手人据此知道该先验什么。

## 6. "照抄"和"照着做"的区别

本项目是照着 `akashic-agent` 重建的。这里面有一个反复出现的判断:

**直接复用**适用于:纯算法、纯协议、纯数据结构——复用后也必须成为 Kirakira 仓库内的本地源码，
不能在运行时 import 或读取外部 checkout。

- 实例:`coremem/*.py` 的算法文件、控制面的 `errors/ids/events/models/ports`。
  本地合同测试验证行为；上游差异只在开发审计中核对。

**照着做**(理解语义后重写)适用于:与本项目结构耦合的部分。

- 实例:Reference 把 turn 表放在 `session/store.py`,和会话共用连接。
  我们的 session 是 JSON + FTS,**没有那个位置**。于是单开 `control.db`,
  但**表结构、状态机、CAS 条件与错误语义逐条对齐**——只有连接归属不同。

**关键在于:偏离必须是显式的、有理由的、写下来的。** 控制面的参数校验是本项目
唯一一处有意偏离(手写校验器而非 pydantic,因为全项目没有这个依赖),
这条偏离写在 [design/control-plane.md](./design/control-plane.md) 第 6 节,
并且明确了"线上契约逐字一致,只有校验器实现不同"。

> **可迁移的判断**:抄一个系统时,危险的不是抄不像,是**不知道自己哪里不像**。
> 建立一个机械的漂移检查(本项目是 doctor 的 16 文件字节比对),
> 比靠记忆维护"我们和它的差异"可靠得多。

另一条更深的:**搬一个子系统,意味着搬它的持久状态和恢复合同**,不只是算法。
记忆系统的移植之所以要分 M0→M1→M2→Stage3/4/5 六步,就是因为
"迁移 / 回滚 / 唯一 owner / 资源释放"这些才是真正难的部分,算法反而是最容易的。

## 7. 让改动可回溯

系统长大以后,最贵的不是写代码,是**半年后回答"当初为什么这么定"**。

本项目的做法是四类文档各管一件事,一个事实只设一个权威位置:

| 类别 | 回答什么 | 位置 |
| --- | --- | --- |
| 现状 | 现在是什么形态、还差什么 | README、`NOW.md`、子系统专题 |
| 方法 | 哪些判断可以复用 | 本文 |
| 判断 | 与参考实现差在哪、哪些是有意取舍 | `DIFFERENCE_AUDIT.md` |
| 依据 | 某个选择的理由、某次重构的验收 | `decisions/`、`design/` |

**决策记录(`decisions/`)的三条规矩**,都是踩过才立的:

1. **按编号只增不改**。被推翻时新建一条并**双向标注**(0002 标 superseded by 0003,
   0003 标 supersedes 0002),不删原文——因为"当初为什么选 A"和"后来为什么改成 B"
   是两个都要回答的问题。
2. **写下被否决的替代方案**。[decisions/0004](./decisions/0004-delivery-dedup.md)
   记的是"用内容指纹+时间窗做跨崩溃去重,**不做两阶段 outbox**",并写清代价:
   语义是"至多一次 + 窗口内不重复",不是 exactly-once。
   只写选了什么,读者半年后会重新纠结一遍已经纠结过的事。
3. **勘误写进原记录**。见 §4.3。

## 8. 一个可复用的工作循环

把上面所有条目压缩成一个循环,这是本项目实际在跑的:

```text
① 对照参考实现,列出差异
      ↓
② 判断每条差异:是"加法"还是"地基"?(§2 的三个信号)
      ↓
③ 地基优先,按依赖排序;加法押后
      ↓
④ 实现。抄能抄的(§6),重写必须重写的,偏离要写下来
      ↓
⑤ 自查:每个新能力,生产调用点在哪一行?(§4.1)
        每个新资源,谁在什么时候关?(§4.2)
      ↓
⑥ 离线回归 + 漂移审计
      ↓
⑦ 实弹:真模型、真渠道、真进程(§5)——这一步不能省
      ↓
⑧ 删掉过渡态(§4.5),更新 NOW.md,记 decision
      ↓
回到 ①
```

第 ⑤ 步和第 ⑦ 步是最容易被跳过的,而本项目**每一次跳过都付了代价**。

---

## 9. 如果只记三句话

1. **接一个简单东西反复困难时,病根在地基,不在接口**——别加适配层,去改地基。
2. **"谁调用它"比"测试过了吗"更能证伪**——测试可以自洽于你的想象,调用点不会。
3. **测过 ≠ 跑过**——把没验证的部分明确列出来,比笼统说"已完成"更有价值。
